# 金币寄售业务接入规范

> 适用范围：`Server/DfoServer` 内金币寄售（上架金币、售出后返代币券）的协议、数据、事务与测试。
> 关联文档：`服务端业务开发规范.md`、`新版背包架构业务接入规范.md`、`拍卖行业务与持久化.md`。

## 1. 定位与边界

金币寄售是**独立功能**，不是普通金币拍卖行的子功能：

- 它复用 `0x00B6` / `0x00B7` 两个 opcode，但使用**更短的包体**，与物品拍卖靠 body 长度分流。
- 它有自己的开关 `GOLD_CONSIGN_ENABLED`，不依赖 `AUCTION_ENABLED`；即使拍卖行关闭，寄售也应当可用。
- 它有自己的数据表 `gold_consignment_listings` / `gold_consignment_settlements`（schema v42），不写拍卖库。
- 它有自己的业务规则（费率、期限、笔数、额限），不继承拍卖行的 5%/3%、10000 押金、5/30 件。

二者的唯一共享点是"同一条 HANDLER 入口 + 同一套 owned `InventoryLease` 与提交协调器"。

## 2. 协议证据

证据来源：当前 A21 客户端 `DNF.exe`（SHA-256 `1F8244D3F7309BBE2FDE4299E1863A894F6B28D5707BF01732980585B20B00DD`）实机抓包，2026-10-30。

### 2.1 服务可用标志 `0x00B7`（NOTI）

客户端 handler `0x01189FB0` 读取 `u8 serviceType, u8 state`：

```
0x01189FB6  call ReadU8   -> [ebp-1]
0x01189FC7  call ReadU8   -> [ebp-5]
0x01189FCF  cmp  byte [ebp-1], 1
0x01189FD3  jne  0x118A02F        ; != 1 走"服务关闭"分支（dstr 0xa490 / 0xa491）
```

**`serviceType` 必须为 1** 才能打开窗口。旧实现发 `{0, state}`，恒走关闭分支，玩家看到"金币寄售系统暂时关闭"。

`AuctionServiceNotificationBuilder.BuildPackets(enabled)` 发 `{1, state}`，`state` 只表示可用形态。

### 2.2 成交价查询 `0x00B6`（CMD → ACK）

请求（C→S，body 6 字节，比物品拍卖的 8 字节短）：

```
body[0]      分发器成功标志（客户端 dispatcher 消费）
body[1]      attrA
body[2..6)   itemKey = 0x0028EB7D
```

ACK 由 handler `0x0112CBB0` 消费，`ReadU8 → ReadU32 → ReadU32 → 6×ReadU32 → 6×ReadU32`：

| 偏移 | 字段 |
|---|---|
| `[1]` | ctrlId 选择：`cmp al,1` → 1 走 ctrlId 8，否则 ctrlId 7 |
| `[2..6)` | 建议价（标量一），写入控件模型 |
| `[6..10)` | 标量二，**客户端读取后不使用** |
| `[10..34)` | 6 档单价 |
| `[34..58)` | 6 档数量 |

> ⚠️ `body[0]` 是分发器标志，**不是** ctrlId 选择字节。改 `body[0]` 对 ctrlId 没有影响；要切换 ctrlId 必须改 `body[1]`。

**帧结构**（抓包核对）：S→C 为 **15 字节头 + body**，`GamePacketEnvelopeBuilder` 写入
`command(1) + type(2) + length(2, = body+15) + 8 字节保留`，不修改 body。
因此 `0x00B6` 回包总长 = 15 + 58 = **73**，与抓包的 `len=0x0049` 吻合。

> ⚠️ **抓包时效性**：`capture_logs/consign/pvfproxy_20261031_014244.log` 是 01:44 的记录，
> 早于 05:10 对 `AuctionOrdinaryBodyBuilder` 的修改。该记录里 `body[0]` 读到 `00`
> （按 handler 契约 `0x0112CBD8 cmp [ebp+0xc],0 / je` 会走失败分支），**但这不是当前代码的行为**：
> 当前 `AveragePriceSuccess` 明确写 `body[0] = 1`。
> 结论：**不得用 01:44 的抓包判断当前 `body[0]`**，需要用新抓包复核。

循环次数已由反汇编确证：loop A 入口 `0x0112CC8D lea edi,[ebx+6]`（`ebx=0`）→ 6 次；
loop B `0x0112CDDE cmp ebx,6` → 6 次。因此回包固定 **58 字节**，与服务端构建器一致。

写路径按 ctrlId 互斥：

| 条件 | setter | 实际行为 |
|---|---|---|
| 控件 `0x16c` 存在 | `0x02366F90` | 写入 `[obj+0x1a0]` |
| `ctrlId == 7` | `0x02335F20` → `0x0232F280` | 见下 |
| `ctrlId == 8` | `0x01456910` → `0x01456240` | 见下 |

**两条 ctrlId 路径的实际行为（反汇编确认）**：

`ctrlId 7` → `0x0232F280`：

```
0x0232F296  cmp dword [esi+0x1d8], 0
0x0232F29D  je  0x232F395        ; 标签控件为空 -> 直接跳到函数出口，价格完全不显示
0x0232F2A7  cmp edi, -1          ; 价格为 -1 -> 走清空分支
0x0232F2B7  mulss xmm0, [0x307B574]   ; * 0.8
0x0232F2CF  call 0x27BACC0            ; sprintf
```

`0x307B574` 的浮点值是 **0.8**，即该路径显示的是 `int(price * 0.8)`（抽成后的卖家实收）。

`ctrlId 8` → `0x01456240`：

```
0x01456259  cmp  eax, -1         ; -1 -> 清空
0x0145625E  mov  [esi+0x1a4], eax      ; 存原始价格
0x0145626E  call 0x27BACC0             ; sprintf(price) —— 无 0.8 缩放
0x01456298  call [ecx+0xe4]            ; 写入控件 [esi+0x184]
```

**关键差异**：`ctrlId 8` **没有** `[+0x1d8]` 存在性门禁，且写入的 `[esi+0x184]` 正是
发包函数读取金额的**同一个输入框控件**；`ctrlId 7` 写的是带 `[+0x1d8]` 门禁的显示标签，
并额外乘 0.8。

**已实测结论**：`body[1]=0`（ctrlId 7）时界面"最新成交价"仍显示 0。这与
`[esi+0x1d8]==0 → 跳到出口` 的静态结论一致：该标签控件在此窗口未创建时，任何价格都不会显示。
`body[1]=1`（ctrlId 8）是另一条无此门禁的分支，当前默认取 1。

> 若两者都不改变该标签，则说明标签**不由 `0x00B6` 回包驱动**，需另找数据源——
> 此时不得声称"成交价已修复"。

### 2.3 上架 `0x00B7`（CMD）

抓包 body 28 字节：

```
01 00 00 00 7D EB 28 00 01 00 00 00 FF FF FF FF
FF FF FF FF 00 00 00 00 18 00 00 00
```

它与物品拍卖的 37 字节上架布局**同构**，恰好少了末尾 3 个 filter tuple（9 字节）。

字段布局已由客户端发包函数 `0x01456F50` 静态确认。该函数按顺序写入：

```
B(1) B(0) C(0) D(ebx) D(1) D(-1) D(edi) D(0) D([esi+0x1dc])
```

各 writer 的宽度由函数体自身证明（`add [ecx+0x2bcc2c],N` 紧跟 `push N`）：

| writer | 地址 | 宽度 |
|---|---|---|
| B | `0x0274D2E0` | 1 字节 |
| C | `0x0274D310` | 2 字节 |
| D | `0x0274D340` | 4 字节 |

`1 + 1 + 2 + 6×4 = 28`，与抓到的包体**逐字节吻合**：

| 偏移 | 类型 | 字段 | 抓包值 | 来源 |
|---|---|---|---|---|
| `[0]` | u8 | 标记 | 1 | 发包函数硬编码 |
| `[1]` | u8 | space | 0 | 常量 0 |
| `[2..4)` | u16 | slot | 0 | 常量 0 |
| `[4..8)` | u32 | itemKey | `0x0028EB7D` | `ebx` |
| `[8..12)` | u32 | quantity | 1 | 常量 1 |
| `[12..16)` | u32 | 常量 | -1 | 发包函数恒写 -1，**不是** UI 值 |
| `[16..20)` | u32 | **金币金额** | -1 | `edi` = `atoi(金额输入框)`，空则 -1 |
| `[20..24)` | u32 | reserved | 0 | 常量 0 |
| `[24..28)` | u32 | durationHours | 24 | `[esi+0x1dc]` |

`space=0` + `slot=0` 正是主背包虚拟槽 0（金币），这是"金币寄售"而非"物品拍卖"的判据。

### 2.4 金币金额字段（`[16..20)`）

这是本功能最关键的字段，链路已完整确证：

```
0x01456F53  mov  ecx,[esi+0x184]      ; 金额文本控件
0x01456F5B  call [eax+0xdc]           ; 取文本缓冲
0x01456F70  cmp  cx,0x30 / 0x39       ; 逐字符校验必须是 '0'..'9'
0x01456F9A  call 0x2C65A29            ; 十进制解析
0x01456F9F  mov  edi,eax              ; edi = 解析结果
0x01456FA4  test edi,edi
0x01456FA6  jne  keep                 ; 非零 -> 保留
0x01456FA8  or   edi,0xFFFFFFFF       ; 零/空 -> 强制 -1
0x01457048  push edi ; D write        ; 写入 body[16..20)
```

`0x02C65A29` → `0x02C65A34` 的实参为 `push 0xA / push 0 / push str`，即
`strtol(str, NULL, 10)`，**十进制**解析，证实该字段是玩家输入的金额。

因此：

- `[16..20)` 是**金币金额**，单位金币。
- 抓包里是 `-1`，因为当时金额输入框为空（`atoi` 返回 0 后被强制成 `-1`）。
- 真实上架时客户端会在这里写**正整数**。

> ⚠️ `[12..16)` 的 `-1` 是发包函数**常量**，不是 UI 值，不要与金额混淆。
> 两者相邻且都为 `-1` 时极易误判——必须按"谁来自 `edi`、谁是常量"区分。

### 2.4 ACK 错误码白名单

拍卖家族的两个 ACK 处理器使用**同一套**结果码约定：

`0x00B7` ACK `0x01126CD0`（及相邻 `0x01126E50` / `0x01126FB0`）：

```
cmp bl, 0xd2 / 0x69 / 0x7e / 0xce / 0x7b / 0x89   ; 接受
jne ...                                            ; 其他值不返回结果并断链
```

`0x00B6` ACK `0x0112CBB0` 的失败路径 `0x0112CF7D`：

```
cmp bl, 0x7e / 0xd2 / 0x69 / 0xce / 0x7b / 0x89   ; 完全相同的六个值
```

实测两者集合**完全相同**，是拍卖家族共用的结果码契约。

**这 6 个码虽然会被接受，但都不显示任何提示。** 寄售控制器 `0x1455D60` 按码查跳转表：

```
index  = byte[0x14560D0 + (code - 11)]      ; 只处理 code ∈ [11..214]
target = dword[0x1456074 + index*4]
```

`0xd2 / 0x69 / 0x7e / 0xce / 0x7b / 0x89` 全部落在 index 22 → `0x01456061`，
该地址**直接返回、不弹提示**。所以玩家点被拒的上架时看不到任何反馈。

只有 **22 个码**有专属文案，其中 `0x8C..0x9E` 是一段连续的消息集合。实机已确认
**`0x9E` = 「当前拍卖行服务器的处理量过多，请稍后再试」**，即"繁忙"语义。

> ⚠️ 更正早期结论：旧文档写过"客户端没有任何代码认识 `0x9E`"，这是**错的**。
> `0x9E` 确实有专属提示（只是语义是繁忙，不是金币不足）。
> 该区间其余码的文案**尚未确定**：dstr 资源已加密，且这些数字在整个镜像里
> 被复用约 2000 次（属通用错误码），无法从静态分析推断语义。
> 因此**金币不足目前故意保持静默**，不冒用"繁忙"文案——宁可没有提示，
> 也不能给玩家错误信息。可用 `GOLD_CONSIGN_FAIL_CODE` 指定 `0x8C..0x9E` 内的码
> 做实机比对，确认后再固定。

`AuctionMutationReplyBuilder.Failure` 使用 `GenericFailure = 0x7B`、`BusyFailure = 0xCE`。

### 2.5 实机验证结论（2026-10-31）

以下均由当前客户端实机抓包确认，取代早期的推断：

**已闭环**

- **`body[1]` 是寄售/物品的分流字节**。`0x00B7` ACK `0x01126CD0` 成功分支：
  ```
  0x01126D98  read u8 → body[1]
  0x01126DA6  cmp al,1
  0x01126DA8  jne 0x1126E20        ; ≠1 → 控件 7 → 0x2345CB0（物品拍卖）
  0x01126DB5  push 8 ; 0x1458960   ; =1  → 控件 8（金币寄售）
  ```
  早前发 `{1,0}` 会让客户端弹「拍卖物品的上架」；改为 `{1,1}` 后实机出现正确的寄售成功提示。
- **上架主链路可用**：`[GoldConsign] listed id=N gold=... unit=...`，
  `gold_consignment_listings` 落库，金币按 `gold_amount` 从主背包虚拟槽 0 扣除。
  金币账目可对平：手存 + 在挂 = 上架前余额。
- **金币金额 = 一口价**：`[16..20)` 实测跟随「一口价」输入框
  （1000→`0x3E8`，2000→`0x7D0`，10001→`0x2711`）。

**仍未闭环**

- **金币档位来自 PVF，不再靠推算**（已更正早期错误结论）。`body[4..8)` 是玩家选中的
  **档位道具 ID**，取自 `stackable/cash/chn_trade_gold`：

  | 档位 | itemId | 档位 | itemId |
  |---|---|---|---|
  | 1百万 | 2681725 (`0x0028EB7D`) | 1千万 | 2681734 |
  | 2百万 | 2681726 (`0x0028EB7E`) | 2千万 | 2681735 |
  | 3百万 | 2681727 | 3千万 | 2681736 |
  | 4百万 | 2681728 | 4千万 | 2683069 |
  | 5百万 | 2681729 | 5千万 | 2683070 |
  | 6百万 | 2681730 | 1亿 | 2683071 |
  | 7百万 | 2681731 | 1.5亿 | 2683072 |
  | 8百万 | 2681732 | 2亿 | 2683073 |
  | 9百万 | 2681733 | 代币券 | 2681762 (`0x0028EBA2`) |

  > 早期文档曾判断 `0x28EB7D` 是"固定金币标记"、`7D→7E` 是"递增游标"，并据此认为
  > "档位不上传、只能按兑换率反推"。**三条全部错误**：`0x28EB7D` 就是 1百万 的 itemId，
  > `7D→7E` 是玩家切换了档位，档位一直都在 `body[4..8)`。
  > 按兑换率反推会**扣错金币**，相关代码与 `GOLD_CONSIGN_GOLD_PER_CERA` 已移除。

  `GoldLadder` 持有完整映射：`GoldForItem(itemId)` 取金额、`ItemForGold(amount)` 反查 id。
  非档位 id 一律拒绝（`UnknownLadderItem`），不凭空造数。

- **`0x00B8` 取消上架已实现**（实机可撤单并退回金币）。请求体 9 字节：
  `01 | listingId:u64`。ACK 期望 `body = 01 01`（标志 + 寄售 selector）。

  > 该请求必须在**解析器的寄售分支**里识别。否则会撞上 `body[0] != 0` 的普通闸门、
  > 解析失败并回 `CE`，玩家表现为"取消上架无反应"。

  撤单与到期退款同一事务形状：先在在线钱包加回金币，再用一次 `TryCommit` 同时持久化
  背包与状态；`LoadRefundAmount(id, characterId)` 校验**挂单归属**，防撤他人单。

- **`0x00BC` 挂单列表已实现**（实机显示成功）。客户端在上架后会立刻发 `0x00BC`，
  ACK `0x0111FC90` 期望 `body[0]=标志 | body[1]=1(寄售selector) | body[2]=条数 | 条数×151 字节`。
  151 字节记录的布局直接复用了项目既有的 `AuctionMyListingsRecordWire` +
  `AuctionRecordBodyBuilder`（原生 `0232DDC4..0232E02F`），**无需自行逆向**：
  `[0..8)` 身份、`[8..12)` 单价、`[12..16)` 总价、`[16..29)` 卖家名 13B、
  `[29]` 期限、`[30..147)` 物品快照 117B、`[147..151)` Arg21。
  物品快照用金币虚拟货币项（`itemId=0`、count=托管金币），界面因此显示为「金币」。
  **竞拍位必须写 `0xFFFFFFFF`（无竞拍哨兵）**：金币寄售是纯一口价，`[8..12)`
  （当前/最低竞拍）只有写哨兵值，客户端才会**整行隐藏**「当前竞拍」标签；
  写 `0` 会渲染成「当前竞拍 0 点券」（两种取值均已实机验证）。
  `GoldConsignmentSearchBuilder.NoBidSentinel` 是唯一出处，挂单列表与搜索列表共用。
  （早期文档误判为「固定模板列、服务端无法去掉」，已纠正。）
  两条踩过的坑：①`characters.name` 是 BLOB，必须按原始字节使用，经字符串转换会得到
  `"System.Byte[]"` 而超出 13 字节；②该分支必须放在 `runtime.EntryEnabled` **之前**，
  否则 `AUCTION_ENABLED=0` 时会被闸门拦成 `CE`。

- **`0x00BA` 金币搜索已实现**（实机看到 3 条挂单）。这是"别的玩家能看到我的挂单"的关键。
  请求体只有 **14 字节**（物品搜索是 22 字节）：
  ```
  01 | 00000000 | 00 | 1F | 01(count) | A59C(u16) | 7DEB2800(金币 key)
  ```
  回包 `body[0]=标志 | body[1]=1 | [2..6)总数 | [6..8)条数 | 条数×168 字节`。

  > ⚠️ **`body[1]` 是窗口选择器，必须写 1**。ACK `0x0111F970` 末尾：
  > ```
  > 0x0111FB7E  mov  al,[ebp+0xf]     ; body[1]
  > 0x0111FB81  cmp  al,1
  > 0x0111FB91  push 8 ; 0x1458970    ; ==1 → 寄售窗口（控件 8）
  > 0x0111FBC7  push 7 ; 0x23009B0    ; ==0 → 物品拍卖窗口（控件 7）
  > ```
  > 写 0 会让所有行送到**未开启的物品拍卖窗口**，界面恒显示"搜索出 0 个"，
  > 即使回包的 3 条记录字段完全正确。这与 `0x00B7` 的成功回包是同一套约定。

  168 字节记录同样复用 `AuctionSearchRecordWire` + `AuctionRecordBodyBuilder`：
  `[0..8)` 身份、`[8]` wire8、`[9..13)` 竞拍、`[13..17)` 一口价、`[17..21)` Arg21、
  `[21..34)` 卖家名 13B、`[34..42)` wire34、`[42]` 期限、
  `[43..160)` 物品快照 117B、`[160..164)` 警告、`[164..168)` wire164。

  物品快照的**字段偏移必须照 `AuctionNativeDisplayProjection`**，不能照背包 `item_core`：
  | 字段 | 背包 `item_core` | 拍卖 `native83` |
  |---|---|---|
  | ItemId | `[1..5)` | `[1..5)` |
  | Attr | `[9]` | **`[5]`** |
  | Value/Count | `[5..9)` | **`[6..10)`** |

  两者差一个字节。把 Count 写到 `[5..9)` 会覆盖 Attr 且让客户端读到 0 数量，
  于是整行被丢弃（客户端过滤逻辑 `cmp dword [ebx],0 / jg keep`，`[ebx-5]` 与 `[ebx]`
  正好相隔 `ItemId(4)+Attr(1)=5` 字节，可作为偏移自检依据）。

  卖家名同样必须走 `AuctionSellerNameTag13.TryEncodeFrozenRoleName`：
  名字从**偏移 0** 开始、尾部补 0，终止符在索引 ≥ 1；手写 2 字节前缀会让终止符落在
  索引 0，客户端 `if (terminator < 1) return false` 直接解码失败并丢弃该行。

- **上架后背包金币数字不即时刷新**（撤单会刷新）。
  实机观察：撤单成功后金币数字立刻恢复，而上架成功后不变。两次回包形状相同
  （`01 01`），且撤单之后**没有任何背包/金币同步包**，说明刷新发生在客户端内部。
  已排查但未证实：`0x00B8` ACK `0x01126E50` 比 `0x00B7` ACK 多调用 `0x01102C30` /
  `0x01102B00`，但追踪 `0x01102C30 -> 0x1637C60` 发现是**单例初始化**
  （`or dword [0x3a5b34c],1` once-flag），不是金币刷新。
  因此**不能确认**服务端能通过改包让上架也刷新；`UPDATE_GOLD_ONLY (0x022E)` 项目中
  从未使用，包体格式无既有实现可参照，未接入。该项保持未闭环，不凭猜构造包体。

## 3. 数据所有权

| 数据 | Owner | 说明 |
|---|---|---|
| 寄售挂单 | `GoldConsignmentRepository` | `gold_consignment_listings`，state 0 活跃 / 1 成交 / 2 撤单 / 3 到期 |
| 结算台账 | `GoldConsignmentRepository` | `gold_consignment_settlements`，`UNIQUE(listing_id, outcome)` 保证幂等 |
| 金币余额 | `InventoryService`（主背包虚拟槽 0） | 不新建第二套金币状态 |
| 代币券 | `accounts.token_cera` | 售出时用 `CurrencyService.GrantTokenCera` 记账到卖家账号 |

`GoldConsignmentRepository` **不自己开连接**，所有写入都使用调用方传入的 `SqliteConnection` / `SqliteTransaction`。

## 4. 事务边界

上架：

1. 持有 owned `InventoryLease`，在 `lease.SyncRoot` 内校验余额与在挂笔数。
2. 先在在线模型上扣金币（`SetMainVirtualCount(slot 0, 余额 - 金额)`）。
3. 通过 `OnlineInventoryMutationCommitCoordinator.TryCommit(..., immediate: true)` 在同一事务里写入挂单行并落库背包 dirty。
4. 提交成功才返回成功 ACK；失败由协调器回滚在线模型并返回白名单失败码。

成交：

`TrySettleSold` 在同一事务里完成：校验挂单仍为 active → 置为 sold → 投递一封附带
**代币券凭证**（`itemId = 2681762`，数量 = 税后实得）的系统邮件 → 写结算台账。
`UPDATE ... WHERE state = active` 影响行数必须为 1，否则整笔回滚，因此重复结算不会二次发券。

> **代币券走「凭证 → 账户货币」的转换链，不能直接进背包了事。**
> 客户端在 `0x0117E503` 处硬编码比对凭证 ID `0x28EBA2`（2681762），命中后按**自己的
> 货币对象**报「获得 N 代币券」。实测把该道具当普通材料塞进附件时，数量取 1 / 7 / 12345
> 三档，弹窗**一律显示 0**（已实机验证），并在背包里留下无法使用的死道具。
>
> 正确的链路（与既有的 2681917 → `happy_token_cera` 一致）：
> 1. `SpecialRewardRouter` 把 2681762 识别为 `SpecialRewardKind.TokenCera`；
> 2. 领取时 `InventoryRewardGrantService.TryPlanAccountCurrency` 排队
>    `InventoryService.TryQueueTokenCeraGrant`；
> 3. `InventoryPersistenceService` 在**同一背包事务**内 `GrantTokenCera` 写
>    `accounts.token_cera`；
> 4. `MailboxHandler` 在领取成功后补发 `NOTIPACKET_CERA (0x0035)`，包体
>    `u8 0x01 | int32 cera | int32 tokenCera | int32 happyTokenCera`（`CeraUpdateBuilder`），
>    客户端的货币对象才会更新，弹窗数量才正确。
>
> 成交时**不**直接改 `token_cera`；余额在**领取**那一刻入账，所以不会双发。

> **邮件窗口底部「代币券 N」读的是 `mailbox_messages.gold`，不是附件数量。**
> 实机确认：`gold` 填税后实得时该行显示正确；填 0 时恒显示 0（附件图标的数字是对的，
> 但底部那行仍为 0）。因此成交邮件的 `Gold` 必须写 `token_cera_paid`。
>
> 该字段**仅用于显示**：`MailboxRepository` 在领取时若发现邮件带「账户货币凭证」附件
> （`SpecialRewardRouter.TryResolveAccountCurrencyReward` 命中），会把 `gold` 视为
> 纯显示、不再按金币发放，避免同值双发——真实入账仍走附件凭证 → `accounts.token_cera`。
>
> 另外 `MailType` 必须为 **1**：`MailType = 0` 会被客户端渲染成「玩家邮件」，
> 与官方样式不符。
>
> ⚠️ **「全部接收」会把附件和邮件 gold 拆成两次 claim**：先按附件 claimObjectId 领附件，
> 再按 messageId 领金币。因此「gold 仅显示」的判定**不能看本次待领附件列表**——
> 第二次进来时附件已标记领取、查不到，判定会失效并把 gold 当金币发一遍。
> 正确做法：`MailCarriesAccountCurrencyVoucher` 按 `mailbox_attachments` 的**历史**判断
> （不看 claimed_flag）。
>
> 同时「仅显示」的 gold 也必须走完整的「预留 → 标记已领」两步：
> `ReserveClaimState(received_gold_flag: 0→2)` + `MarkMailClaimed(2→1)`。
> 漏掉预留会让 `MarkMailClaimed` 的 CAS 失败但无人察觉，邮件永远停在
> `received_gold_flag = 0`，表现为：**领完代币券邮件仍留在邮箱、像多出一封金币邮件，
> 且删除请求被 `InvalidRequest` 拒绝**。
>
> 邮件窗口里凭证附件的**显示数量写 0**（金额由 `gold` 承载），但数据库
> `mailbox_attachments.item_count` 必须保留真实数量——领取换算读的是数据库值。

撤单/到期：同一模式，状态改为 2/3，`token_cera_paid = 0`，不产生代币券。

**托管金币必须退还**，且退款与状态变更必须在**同一个事务**里完成：

1. `GoldConsignmentRepository.LoadRefundAmount` 读出仍为 active 的挂单托管金币。
2. 服务层先在在线模型上加回金币（`SetMainVirtualCount(slot 0, 余额 + 退款)`），与 `Place`
   的扣款严格对称。
3. 用**一次** `OnlineInventoryMutationCommitCoordinator.TryCommit(..., immediate: true)`
   同时持久化背包 dirty 与挂单状态变更。
4. 失败时协调器会 `ReloadOnlineInventory` 丢弃上一步的临时加款，不会出现"状态已结算但金币没退"。

> ⚠️ **不得**在 Repository 里直接 `GrantGold` 写库。金币的真源是在线 `InventoryService`
> 模型，直接写 SQL 会让模型与库漂移，随后背包保存又会把退款覆盖掉（本实现早期版本
> 就是这样，被 SelfTest 的 `expiry returns the escrowed gold` 断言捕获）。
> 也**不得**拆成两次 `TryCommit`：中间失败会让挂单已结算而金币不退回。

到期由持久化的 `expires_at_unix` 驱动（不是进程内定时器），因此跨重启正确。
`GoldConsignment.SettleExpired(lease, nowUnix)` 负责扫描并结算，调用点是寄售报文入口
（`AuctionHandler` 的寄售分支），玩家下次操作寄售时即可看到已结算的到期挂单。

## 5. 业务规则

### 5.1 手续费（官方规则，已实现）

手续费**不是固定值**，按「一口价 ÷ 平均价格」的比例分档（来源：官方活动页
「金币寄售系统」）。实现见 `GoldConsignmentFeePolicy`：

| 价格 ÷ 平均价格 | 手续费 | 用拍卖行优惠券 |
|---|---|---|
| 低于 40% | **无法上架** | — |
| 40% ~ 150% | **5%** | **1%** |
| 150% ~ 160% | 30% | 优惠券无效 |
| 160% ~ 170% | 40% | 优惠券无效 |
| 170% ~ 180% | 50% | 优惠券无效 |
| 高于 180% | 95% | 优惠券无效 |

- **平均价格**：该金币档位近 7 天的成交均价（`LoadAveragePriceCera`，只统计
  `state=1` 已售且 `settled_at_unix` 在窗口内的行）。没有历史时退回运营配置的
  `GOLD_CONSIGN_REFERENCE_PRICE`（默认 1000）。
- **档位锁存**：手续费百分比在上架时写进 `gold_consignment_listings.fee_percent`（v43
  迁移），结算只认这个值。否则事后均价变动会改掉卖家已成立的收益。
- **优惠券**：读 `account_premiums` 的 `premium_type = 29`（`AuctionEntitlementReader`），
  只影响 40%–150% 正常档。
  拍卖行优惠券是**商城售卖的持续型道具**（780 点券，生效期内一直有效），
  **不是一次性消耗品**，所以实现里只读生效期、不扣减、不销号。
  官方对该道具在金币寄售上的作用只有一条：「金币寄售时手续费由 5% 降至 1%」
  （其余权益属于普通拍卖：5%→3%、可同时上架 30 件、可上架喇叭类商城道具、
  附赠同期限的阿拉德商贸许可证）。因此惩罚档不受影响，也不需要额外的 `1%` 特判。
- **边界**：用 `price*100` 对 `avg*阈值` 做整数比较，避免 180.1% 被截断成 180%。
- 卖家实得 = `一口价 × (100 − 手续费%) / 100`（向下取整），`NetProceeds`。

### 5.2 「近期交易价格」参考（`0x00B6`）

官方规则是「选定金币值后显示近期交易价格」，所以参考价**按档位**返回：该档位近 7 天
成交均价，无历史时用运营参考价（`GoldConsignment.ResolveReferencePrice`）。

### 5.3 其余暂定值

以下集中定义在 `GoldConsignment`，标注**待确认**，等正式数值确定后统一替换：

| 项 | 取值 |
|---|---|
| 上架时长 | 无券 **24** 小时；持拍卖行优惠券 **48** 小时 |
| 单角色在挂笔数上限 | **3**，拍卖行优惠券**不放宽** |
| 单笔最小金币 | 1000000（跟随档位下限） |
| 单笔最大金币 | 200000000（跟随档位上限） |

> **时长必须由服务端按持券状态夹取。** 客户端按勾选框发 24/48，本身不可信：
> `TryPlaceConfirmed` 先读优惠券生效期，再 `maxHours = couponActive ? 48 : 24`，
> 超出即回到 24。时长写进 `duration_hours` 并落到 `expires_at_unix`，结算只认这个值。
>
> **笔数恒为 3**：`ProvisionalListingCap = 3`，判定在扣金币之前，超限回 `0x97` 且不动钱包。
> 拍卖行优惠券在金币寄售上只放宽**时长**与**正常档手续费**（5% → 1%），
> 不放宽笔数——不要照搬普通拍卖「5 件 → 30 件」的关系。

**`[16..20)` 的一口价就是整笔总价**，不再乘任何"计价块"系数。
实机验证：玩家填 1000 点券挂 100 万金币，界面「价格(点券)」显示 100,000——
说明界面渲染的是 `total_price_cera`，而早期实现用 `unitPrice × (goldAmount/10000)`
把价格放大了 100 倍。现 `total_price_cera = unitPriceCera`，界面即显示 1000。

**金额不要求按计价块对齐**：`[16..20)` 是玩家输入的任意十进制整数（客户端用
`strtol(str,NULL,10)` 解析），因此只校验上下限，不校验整除。

**零单价必须被接受**：`GoldConsignmentRepository.InsertListing` 只拒绝
`goldAmount <= 0`、`unitPriceCera < 0` 和溢出；早期版本用 `total <= 0` 判定会把每一次
上架都拒掉（已被 SelfTest 捕获并修复）。
