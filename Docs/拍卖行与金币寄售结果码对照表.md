# 拍卖行/金币寄售 ACK 结果码对照表

> 适用范围：`Server/DfoServer` 中拍卖家族（`0x00B6` / `0x00B7` / `0x00B8` / `0x00B9` / `0x00BC` / `0x00BD`）的**失败结果码 ↔ 客户端提示文案**映射。
> 关联文档：`金币寄售业务接入规范.md`、`拍卖行业务与持久化.md`。

## 1. 为什么需要这张表

客户端收到失败回包后，会按结果码查表显示提示。**大部分码不显示任何提示**，
玩家看到的现象就是"点了没反应"。要实现可用的交互反馈，服务端必须发送**有文案的码**。

## 2. 判定机制（静态确证）

`0x00B7` ACK `0x01126CD0` 成功分支读 `body[1]` 选窗口；
失败分支进入控制器 `0x1455D60`，按码查**跳转表**：

```
index  = byte[0x14560D0 + (code - 11)]        ; 仅处理 code ∈ [11..214]
target = dword[0x1456074 + index*4]
```

- **静默码**：`0xd2 / 0x69 / 0x7e / 0xce / 0x7b / 0x89`
  这 6 个值会被接受，但全部落到 `index 22 → 0x01456061`，**直接返回、不弹提示**。
- **有文案的码**：全表共 **22 个**，见第 3 节。

> ⚠️ 早期文档曾断言"客户端没有任何代码认识 `0x9E`"。该结论**错误**：
> `0x9E` 确实有专属文案（"处理量过多"）。判断一个码是否可用，必须查上表，
> 不能依赖"是否出现在白名单"。

## 3. 对照表（全部 22 个码）

码值顺序即 `0x8C..0x9E` 的连续区间，语义按功能场景排列。
标记 **实机** 的条目由单码隔离测试确认；**连点** 由一次性轮换测试确认。

| 码 | 十进制 | 客户端提示 | 证据 |
|---|---|---|---|
| `0x8C` | 140 | 当前拍卖行为关闭状态 | 实机 |
| `0x8D` | 141 | 使用未知程序的用户，将无法使用拍卖行 | 实机 |
| `0x8E` | 142 | 禁止交易的用户，将无法使用拍卖行 | 连点 |
| `0x8F` | 143 | 信用印章持有者若超过每天金币交易量上限，则无法继续使用拍卖行 | 连点 |
| `0x90` | 144 | 所持金币不足，将无法进行上架或竞拍 | 实机 |
| `0x91` | 145 | 无法上架到拍卖行的物品 | 连点 |
| `0x92` | 146 | 无法上架超出持有数量的物品数 | 连点 |
| `0x93` | 147 | 所持金币不足，将无法进行上架或竞拍（与 `0x90` 同文案，疑为变体） | 连点 |
| `0x94` | 148 | 缺少物品 | 连点 |
| `0x95` | 149 | 若要上架点券物品，则需要拍卖行优惠券 | 连点 |
| `0x96` | 150 | 拍卖行中不存在该物品 | 实机 |
| `0x97` | 151 | 已超过上架数量上限，需要拍卖行优惠券才能继续上架 | 连点 |
| `0x98` | 152 | 最低竞拍价或一口价中输入了错误数值 | 连点 |
| `0x99` | 153 | （无文案，落到静默出口） | 跳转表 |
| `0x9A` | 154 | 您没有权限 | 连点 |
| `0x9B` | 155 | 无法竞拍自己上架的物品 | 连点 |
| `0x9C` | 156 | 已完成竞拍 | 连点 |
| `0x9D` | 157 | 竞拍金额不符，可能存在更高价格的竞拍者 | 连点 |
| `0x9E` | 158 | 当前拍卖行服务器的处理量过多，请稍后再试 | 实机 |

区间外的三个码：

| 码 | 十进制 | 客户端提示 | 证据 |
|---|---|---|---|
| `0x0B` | 11 | 弹出「上架拍卖品」窗口（无文字提示） | 连点 |
| `0x74` | 116 | 弹出「上架拍卖品」窗口（无文字提示） | 连点 |
| `0x75` | 117 | 弹出「上架拍卖品」窗口（无文字提示） | 连点 |
| `0xD6` | 214 | 弹出「上架拍卖品」窗口（无文字提示） | 连点 |

> `0x0B / 0x74 / 0x75 / 0xD6` 实际效果是**把「上架拍卖品」窗口重新弹出来**，
> 属窗口切换而非错误提示，不要用于业务失败反馈。

## 4. 业务映射建议

金币寄售当前使用的码：

| 场景 | 码 | 常量 |
|---|---|---|
| 金币不足 | `0x90` | `AuctionMutationReplyBuilder.InsufficientGoldFailure` |
| 服务器繁忙 / 限流 | `0x9E` | `AuctionMutationReplyBuilder.ThroughputFailure` |
| 价格数值非法 | `0x98` | 建议使用 |
| 超出上架数量上限 | `0x97` | 建议使用 |
| 物品/条目不存在 | `0x96` | 建议使用 |
| 服务关闭 | `0x8C` | 建议使用 |
| 其它未归类失败 | `0x7B` / `0xCE` | 静默，不误导玩家 |

**原则：宁可静默，也不要发错误文案。** 例如金币不足不能发 `0x9E`（会被玩家理解为"服务器繁忙"），
这是本实现早期真实踩过的坑。

## 5. 复现方法（供后续新增码时使用）

服务端提供两个环境变量，避免为每个码重新编译：

| 变量 | 作用 |
|---|---|
| `GOLD_CONSIGN_FAIL_CODE` | 固定使用某个码（单码隔离测试） |
| `GOLD_CONSIGN_FAIL_SWEEP` | 逗号分隔的码列表，**每次拒绝自动换下一个**并记录序号 |

复现步骤：

1. 设置 `GOLD_CONSIGN_FAIL_SWEEP=142,143,145,...` 启动服务端。
2. 客户端登录，进入寄售窗口，**连续点击上架**（每次都会被拒）。
3. 服务端日志输出 `[GoldConsignProbe] sweep N/M code=0xNN`，与点击顺序一一对应。
4. 按顺序记录客户端提示文案，回填本表。

该机制把 17 个码的验证压缩到一次会话，显著快于逐个重启。

## 6. 未验证项

- `0x93` 与 `0x90` 文案完全相同，**是否为"上架/竞拍"两种变体尚未区分**。
  当前建议业务只使用 `0x90`。
- `0x8C..0x9E` 之外的码（除已列出的 4 个）未逐一验证。
- 不同客户端版本可能重排该表，**升级客户端后必须重新抽样验证**（至少验证实际使用的码）。
