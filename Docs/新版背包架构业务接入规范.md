# 新版背包架构业务接入规范

> 文档版本：1.1.5
> 数据库基线：`86jp-database-v1` / schema v1
> 更新日期：2026-09-02

本文按当前代码架构编写，用来替代早期 `InventoryModel/InvenItem/ItemExtraView/旧 DTO` 相关设想文档中的业务接入部分。

当前方向：

```text
在线物品真源 = InventoryService
物品核心语义 = ItemCore
容器位置语义 = InventoryListType + slotIndex
协议投影 = ItemListPacketBuilder / ItemListUpdateBuilder / ItemListProtocolWriter
持久化 = InventoryPersistenceService + Repository/Codec
```

后续新增或迁移物品业务时，默认必须走这条链路。当前代码中 `SqliteAssetService` / `IAssetService` / `IInventoryStore` / `CommonInventoryItem` 等旧物品门面和旧 DTO 已清理，后续不要为了兼容重新引入。

## 一、当前代码中的真实分层

### 1. Models

目录：`Server/DfoServer/Game/Inventory/Models/`

| 类型 | 当前职责 |
| --- | --- |
| `ItemCore` | 99B 服务端物品核心语义（较 A12 多 17B）。承载 itemKind、itemId、value、强化、耐久、附魔、增幅、异界气息、徽章、魔法封印、锻造、交易限制、排序锁、装备锁 ID 等。 |
| `ChronicleOption` | `ItemCore` 内异界气息单项模型。 |
| `RandomOption` | `ItemCore` 内魔法封印单项模型。 |
| `JewelSocket` | 时装 30B 孔位 detail，5 组 `ushort socketType + int emblemId`。 |
| `AvatarDetail` / `AvatarDetailManager` | 时装 detail 在线模型和管理器。负责 avatarUid、期限、染色、孔位、透明时装 ID 等。 |
| `CreatureDetail` / `CreatureDetailManager` | 宠物 detail 在线模型和管理器。负责 creature uid、名字、饱食度、经验、等级、期限、宠物类型等。 |
| `CargoModel` | 个人仓库在线模型。 |
| `AccountCargoModel` | 账号仓库在线模型。 |
| `VirtualCountItem` | 主背包虚拟数量槽模型。 |
| `EpicPieceBookModel` | 账号级史诗图鉴碎片数量模型。按 `etc/epicpieceinfo.etc [piece list]` 顺序保存 count[]，不保存 `ItemCore`。 |
| `InventoryItemStateBook` | 角色级 item_state 在线账本。承载道具冷却和持续效果的 `state_kind + itemId -> ExpireTime`，持久化到 `character_item_states`；登录 0x00AC/0x00AE 从它投影，并把 Unix 到期秒转换为剩余秒。 |
| `EquipmentItemLock` / `EquipmentItemLockManager` | 装备锁在线模型和管理器。 |
| `CollectBoxModel` | 收集箱在线进度模型，只保存 `boxIndex + slotIndex -> itemId`。 |
| `InventoryItem` | Repository/Codec 边界记录。表示数据库行中的 `list_type + slot_index + item_core + 行元数据`，不是在线业务模型。 |

注意：在线业务不要长期持有 `InventoryItem`。它只应该出现在 repository/codec、自测和诊断边界。

### 2. Services

目录：`Server/DfoServer/Game/Inventory/Services/`

| 类型 | 当前职责 |
| --- | --- |
| `InventoryService` | 在线背包总模型。持有主背包、穿戴栏、时装栏、宠物栏、个人仓库、账号仓库、史诗碎片图鉴、detail manager、装备锁、称号簿、成就、收集箱和 dirty 状态。 |
| `InventoryContext` / `InventoryLease` | 在线背包运行时挂载。用 `sessionId + characterId` 绑定在线 `InventoryService`，写操作需要通过 lease 校验归属并加锁。 |
| `InventoryCharacterLifecycleService` | 选角/进游戏时加载 `InventoryService`，注册 lease；离线/返回选角时配合 `InventoryContext.Unregister` 保存并释放在线背包。 |
| `InventoryPersistenceService` | 在线背包统一保存。定时、断线、切角、主动保存都应走它。负责在同一事务中保存物品槽、detail、称号簿、成就、收集箱、虚拟槽、史诗碎片图鉴、容器状态。 |
| `InvenItemCodec` | `character_inventory_items.item_core` 与 `InventoryItem/ItemCore` 的数据库边界 codec。名字保留为历史命名，但职责是新表 item_core codec。 |
| `AvatarDetailCodec` / `CreatureDetailCodec` | detail 表和 detail 模型之间的转换。 |
| `InventoryCreateService` | 根据 `itemKind + itemId + reason + count/options` 创建 `ItemCore`，并为时装/宠物准备 detail。业务一般不直接调用它，而是走 `InventoryRewardGrantService`。 |
| `InventoryRewardGrantService` | 新物品发放、批量发放、已有完整物品插入的标准入口；史诗碎片 itemId 会在这里按 `EpicPieceCatalogService.IsEpicPieceId` 分流到史诗图鉴数量。 |
| `InventoryInsertService` | 插入规划和插入应用。一般由 grant service 调用，业务不直接绕过 grant service。 |
| `InventoryDeleteService` | 指定槽删除、客户端删除 ACK 所需 mutation、使用消耗品等标准扣除入口。 |
| `InventoryMoveService` | 物品移动/穿戴/卸下/跨容器移动的标准入口。 |
| `ItemTradeSession` / `InventoryExchangeCommitService` | 前者只拥有双方报价和确认状态；后者持有双方当前 lease，以一个 SQLite 事务提交物品、金币及审计。 |
| `InventorySortService` | 排序逻辑入口。A21 `SORT_ITEM` body 为 listType + category + condition。condition 按标签页解释：装备 0按栏位/1按品级(史诗>传说>勇者，不用PVF原始编号)/2按Lv/3按部位；消耗品 0按栏位/3按类型/4按时间；材料与副职业 0按栏位/3按类型；任务栏只有锁定；装扮默认按品级，可选按部位；徽章、宠物本体、勋章无该功能；宠物装备/消耗品仅默认+锁定；仓库仅锁定。不支持的 condition 回退该页默认。 |
| `InventoryLockService` / `InventoryEquipmentLockTableService` | 排序锁、装备锁、0x00FB 锁列表投影相关逻辑。 |
| `InventoryShopRuntimeService` | NPC 商店/商店型购买在线实现。 |
| `InventoryCeraShopRuntimeService` / `InventoryCeraShopStackPolicy` | 商城购买、技能页扩展、名称装饰卡等商城路径在线实现和堆叠规则。 |
| `InventorySpecialConsumableService` | 罐子/礼包/抽奖类特殊消耗品在线实现。 |
| `InventoryPackageRewardResolver` / `InventoryOverflowRewardSink` | 礼包/随机奖励规划与溢出奖励入口。`MailboxInventoryOverflowRewardSink` 把无法直接入槽的普通物品构造成完整 `ItemCore` 永久系统邮件附件；需要与其他业务状态原子提交时必须使用 `TransactionBoundInventoryOverflowRewardSink`。 |
| `InventoryRepairService` | 修理在线实现。 |
| `InventoryItemUpgradeService` | 强化在线实现。 |
| `InventoryEquipmentMutationService` | 装备附魔、镶嵌等装备字段修改入口。 |
| `InventoryDisjointService` / `InventoryAvatarDisjointService` | 装备/时装分解在线实现。 |

| `InventoryCompoundItemRecipeService` | 普通配方/合成材料规划。 |

| `InventoryGoldCarryLimitLoader` | 金币携带上限读取，给虚拟金币槽发放/拾取使用。 |
| `InventoryStackRuleService` | 堆叠规则。 |
| `InventorySpaceCheckService` | 空间检查。 |
| `ItemSlotBoundService` | `itemKind -> list_type/slot range` 和槽位合法性规则，包含勋章栏 `list_type=38`、`0-97`。 |

### 3. Repositories

目录：`Server/DfoServer/Game/Inventory/Repositories/`

Repository 只负责数据库读写，不承载业务判断：

- `InventoryItemRepository`
- `AvatarDetailRepository`
- `CreatureDetailRepository`
- `InventoryContainerStateRepository`
- `InventoryMainVirtualCountRepository`
- `EquipmentItemLockRepository`
- `InventoryAuditRepository`
- `NameTagStateRepository`

另外，`CollectBoxProgressRepository` 目前仍在 `Game/Inventory` 根目录，职责是 `character_collectbox_slots` 的进度表读写。它不是物品主表 repository。

### 4. Protocol Builders

协议层当前关键入口：

| 类型 | 当前职责 |
| --- | --- |
| `InventoryRefreshSender` | handler 对外统一刷新门面。业务应优先调用它，不直接拼 0x0D/0x0E。 |
| `ItemListPacketBuilder` | 0x0D 全量 ITEM_LIST 构造。新入口是 `BuildBody(characterId, accountId, listType)`，从在线 `InventoryContext` 读。 |
| `ItemListUpdateBuilder` | 0x0E 槽位刷新构造。新入口是 `BuildUpdateBody(characterId, accountId, itemSpace, slots)`，从在线 `InventoryContext` 读。 |
| `ItemListProtocolWriter` | 当前 A21 common entry 为 101B、avatar entry 为 131B（方法名保留 84/126）。按协议字段投影 `ItemCore + Detail + slot`，不能直接写 `ItemCore.ToBytes()`。 |
| `Noti2InventoryProjectionBuilder` | NOTI2 装备/外观投影构建器。应从在线 `InventoryService` 取数据。 |

当前 0x0D/0x0E 已经没有旧 snapshot/旧 DTO overload。`ItemListUpdateBuilder.BuildEmptyUpdates` 只用于显式空槽刷新，不是旧 DTO 兼容入口。

## 二、在线业务的标准入口

### 1. 获取在线背包

所有会修改物品的 handler/service，都应该先拿 lease 并校验 session 所有权：

```csharp
var (characterId, accountId) = SessionOwnerResolver.Resolve(session);
if (!InventoryContext.TryGetLease(characterId, out var lease)
    || !lease.IsOwnedBy(session.SessionId))
{
    return;
}

lock (lease.SyncRoot)
{
    var inventory = lease.Inventory;
    // 修改在线模型
}
```

不要在普通在线业务里调用：

```csharp
InventoryService.LoadFromDb(...)
```

`LoadFromDb` 只允许在选角进入游戏、离线展示、迁移、自测、诊断工具中出现。

### 2. 新物品创建/发放

标准入口：

```csharp
InventoryRewardGrantService.TryCreateAndInsert(
    inventory,
    itemId,
    ItemCreateReason.QuestReward,
    count,
    out var result);
```

批量发放：

```csharp
InventoryRewardGrantService.TryGrantBatch(inventory, requests, out var batchResult);
```

它负责：

- 解析 `itemKind`
- 创建 `ItemCore`
- 根据 `ItemSlotBoundService` 找默认插入空间和槽位
- 合并堆叠或找空槽
- 为时装/宠物创建 detail 并回填 UID
- 插入在线 `InventoryService`
- 标记脏槽和脏 detail
- 返回刷新所需的 list/slot

新增业务不要自己：

- 直接 `ItemCore.Create(...)` 后塞槽
- 直接写 `character_inventory_items`
- 直接写 `character_avatar_detail`
- 直接写 `character_creatures`
- 自己生成时装/宠物 UID

只有业务规则明确允许“背包满时转邮件”时，才能在
`InventoryRewardGrantService` 返回 `InsertPlanFailed` 后调用
`IInventoryOverflowRewardSink`。无效物品、创建失败、detail 失败和应用失败
不能伪装成容量溢出。若同一操作还修改金币、消耗、次数、任务或 effect，
必须把 `MailboxInventoryOverflowRewardSink` 绑定到该操作现有的 SQLite
connection/transaction；邮件写入成功后才算奖励 committed，邮件失败必须让
整项业务回滚。金币、账号货币、Premium 和史诗碎片等非普通入槽物不转为
邮件附件。

### 3. 只创建 ItemCore，不插入容器

有些业务只需要生成一个“物品原子”，暂时不进入任何容器，例如副本场景掉落、奖励预览、掉落结算前的实例预生成。这种场景使用：

```csharp
InventoryRewardGrantService.TryCreateOnly(
    itemId,
    ItemCreateReason.DungeonDrop,
    count,
    out var result);
```

它负责：

- 规范化 itemId/count
- 识别契约、虚拟货币等特殊奖励
- 解析 `itemKind`
- 创建 `ItemCore`
- 写入 PVF 静态默认属性和创建原因相关属性
- 返回堆叠规则归一化后的数量

它不会：

- 插入 `InventoryService`
- 占用槽位
- 标记 dirty
- 写数据库
- 创建时装 `AvatarDetail`
- 创建宠物 `CreatureDetail`

调用方必须判断返回类型：

```csharp
if (result.Kind == InventoryRewardGrantKind.InventoryItem)
{
    var core = result.Core;
}
```

如果 `result.Kind` 是 `Premium`、`MainVirtualCount` 或 `EpicPiece`，说明该 itemId 被识别成特殊奖励，`Core` 不代表可插入背包的普通物品。

低层创建器为：

```csharp
InventoryCreateService.TryCreateCore(
    itemId,
    reason,
    count,
    out var core);

InventoryCreateService.CreateCore(
    itemKind,
    itemId,
    reason,
    count,
    options);
```

低层创建器只适合 `InventoryRewardGrantService` 内部、自测、诊断工具使用。普通业务优先走 `TryCreateOnly`，避免绕过特殊奖励和堆叠规则。

如果只创建出来的 `ItemCore` 后续要进入背包：

- 已经是完整实例属性的装备、称号、消耗品，走 `TryInsertExisting`
- 新发放的时装/宠物，优先走 `TryCreateAndInsert`
- 不要业务自己 `SetItem` 后手动补 detail

### 3.1 史诗碎片 epicpiece

史诗碎片不进入普通背包，也不作为普通 `InventoryItem` 入槽。识别依据是 `EpicPieceCatalogService.IsEpicPieceId(itemId)`，也就是当前 PVF `etc/epicpieceinfo.etc` 的 `[equipment piece drop info] / [piece list]` 中存在该碎片 itemId。

如果发放或插入的是史诗碎片：

- `InventoryRewardGrantService` 返回 `InventoryRewardGrantKind.EpicPiece`
- 直接更新在线 `InventoryService.EpicPieces` 数量
- `SaveDirty` 时保存到 `accounts.epic_piece_counts`
- 下发 `ENUM_NOTIPACKET_EPIC_BOOK_INFO mode=1`
- 不写 `character_inventory_items`
- 不写 `account_inventory_items`
- 不构造可长期保存的 99B `ItemCore`
- 不走普通物品入槽和空槽查找逻辑

`ItemCore.KindEpicPiece = 14` 只用于发放/创建链路的业务分流。业务代码看到这个 kind 时，应把它视为“账号级史诗图鉴数量变更”，不能把它当成 stackable 背包物品继续传给普通插入、移动、排序、仓库或邮件附件逻辑。

时装/宠物 detail 的 UID 分配和 dirty 标记必须通过发放/插入服务完成，这样主表和 detail 表才能在 `SaveDirty` 中同一事务落库。

### 4. 已有完整物品插入

如果物品已经有完整 `ItemCore`，且需要保留强化、附魔、锁、随机属性等全字节语义，使用：

```csharp
InventoryRewardGrantService.TryInsertExisting(
    inventory,
    existingCore,
    count,
    out var result);
```

适用场景：

- 称号簿取回称号
- 邮件取出已生成装备
- 临时容器取回完整装备
- 副本掉落阶段已经生成好实例属性的装备

如果只是按 itemId 生成默认静态物品，应使用 `TryCreateAndInsert`。

### 5. 扣物品/使用消耗品

客户端指定槽位删除：

```csharp
InventoryDeleteService.TryDeleteForClient(
    inventory,
    listType,
    slotIndex,
    count,
    out var mutation);
```

客户端指定槽位使用消耗品：

```csharp
InventoryDeleteService.TryUseStackableForClient(
    inventory,
    listType,
    slotIndex,
    expectedItemId,
    out var mutation);
```

业务只按 itemId 扣主背包材料：

```csharp
inventory.TryConsumeMainItem(itemId, count, out var consumeResult);
```

选择规则：

- 客户端传了 slot，优先 `InventoryDeleteService`
- 需要检查装备锁，优先 `InventoryDeleteService`
- 只扣主背包材料，且不关心具体槽，可用 `inventory.TryConsumeMainItem`
- 复杂业务先校验再扣，避免效果失败但材料已扣

### 6. 金币/复活币/胜点/晶体/灵魂

主背包虚拟槽由 `InventoryService` 管理，不创建普通 `ItemCore`：

| slot | itemId | 语义 |
| --- | --- | --- |
| 0 | 0 | 金币 |
| 1 | 1 | 复活币 |
| 2 | 2 | 胜点 |
| 354-359 | 固定晶体 itemId | 晶体碎片 |
| 360-364 | 固定灵魂 itemId | 灵魂碎片 |

史诗碎片不是主背包虚拟槽，不在 0-364 任意槽位中展示。它是账号级史诗图鉴数量，在线模型是 `InventoryService.EpicPieces`，持久化字段是 `accounts.epic_piece_counts`。

常用入口：

```csharp
inventory.GetMainVirtualCount(slot);
inventory.SetMainVirtualCount(slot, count);
inventory.CountMainItem(itemId);
inventory.TryGrantGold(amount, carryLimit, out grantedCount, out finalCount);
```

注意：

- 0/1/2 和 354-364 即使数量为 0，也不是空槽语义
- 352-353 是预留槽，不参与初始化和插入
- 判断主背包真实物品槽时，必须排除虚拟槽和预留槽
- 出售物品时，应先判断 `currentGold + sellGold <= carryLimit`

### 7. 守护者盾牌窗口

`list_type=33/34` 是盾牌窗口的虚拟 deck/图鉴空间，不进入 `InventoryService`，也不写入 `character_inventory_items`。

- 图鉴数据来自 PVF `etc/character/knight/shieldwindownewdata.etc`；quest 盾看任务完成记录，level 盾（`grow type=0`）看角色等级。转职完成以真实任务记录为准。
- `character_knight_shield_deck` 保存 5 个 itemId：槽 0 为主盾，槽 1-4 为备用盾；空槽不落行。
- 主盾的战斗、外观和完整 `ItemCore` 仍以穿戴栏槽 24（`EquipmentType.SupportWeapon`）为准，虚拟 deck 不得覆盖真实装备。
- 涉及 33/34 的 `MOVE_ITEMSPACE` 和 `CHANGE_DECK_INFO` 由 `KnightShieldHandler` 处理；穿戴栏槽 24 的普通移动成功后同步 deck。

## 三、协议刷新规范

### 1. 0x0E 槽位刷新

统一调用：

```csharp
await _refresh.SendUpdateItemList(session, listType, slotIndex);
await _refresh.SendUpdateItemList(session, listType, slotIndexes);
```

业务层不要直接调用或重新恢复旧 DTO 刷新入口：

```csharp
ItemListUpdateBuilder.BuildCommonUpdates(...)
ItemListUpdateBuilder.BuildAvatarUpdates(...)
ItemListUpdateBuilder.BuildPetUpdates(...)
```

这些旧入口当前已从代码中清理。需要刷新空槽时使用 `_refresh.SendEmptyUpdateItemList(...)`，普通槽位变化仍统一走 `_refresh.SendUpdateItemList(...)`。

### 2. 0x0D 全量刷新

统一调用：

```csharp
await _refresh.SendItemListRefresh(session, listTypes);
```

当前新路径：

```text
InventoryRefreshSender.SendItemListRefresh
  -> ItemListPacketBuilder.BuildBody(characterId, accountId, listType)
  -> InventoryContext 在线 InventoryService
  -> ItemListProtocolWriter
```

不要在业务 handler 中手写 0x0D。

### 3. ItemListProtocolWriter 的边界

`ItemCore` 不是协议 entry，不能直接 `ToBytes()` 发包。

协议 entry 需要：

```text
slot + ItemCore + AvatarDetail/CreatureDetail + itemspace
```

例如：

- 普通 84B：`WriteCommonEntry84`
- 时装 126B：`WriteAvatarEntry126`
- 宠物 84B：`WritePetCreatureEntry84`
- 虚拟数量槽 84B：`WriteVirtualCountEntry84`
- 空槽：`WriteEmptyEntry`

时装 `ItemCore.Value` 是 avatarUid，但 0x0D/0x0E 的 value 字段要写 detail 剩余有效期。宠物有效期等字段也需要从 `CreatureDetail` 投影。

### 4. 其他刷新

| 场景 | 推荐入口 |
| --- | --- |
| 外观变化 | `_refresh.SendNoti2AppearanceUpdate(session)` |
| subtype0 tail 重读 | `_refresh.ReloadSubtype0Tail(session)` |
| 金币刷新 | `_refresh.SendGoldUpdate(session)` |
| 装备锁列表 | `_refresh.SendAllEquipmentItemLockListRefresh(session)` 或 `_refresh.SendEquipmentItemLockListRefresh(session, listType)` |
| 排序锁 | `_refresh.SendSortItemLockSlotRefresh(session, listType, slotIndex)`（0x000E 单槽增量刷新，同步 entry 锁标志字节）；不得主动发 0x02CA |
| 收集箱 | `CollectionBoxBodyBuilder.TryBuildForBox(CollectBoxModel, boxIndex, out body)` 后发送 0x0381 |

如果某个 ACK 本身已经包含客户端需要的刷新字段，可以不额外发 0x0E，但必须以客户端消费结构为依据，不能靠猜。

## 四、保存规范

### 1. 常规保存

在线业务只修改 `InventoryService`，由 dirty 状态驱动保存：

```csharp
InventoryPersistenceService.SaveDirty(lease);
InventoryPersistenceService.SaveAllDirty();
```

当前保存内容包括：

- `character_inventory_items`
- `account_inventory_items`
- `character_avatar_detail`
- `character_creatures`
- `character_item_locks`
- `character_titlebook_items`
- 成就在线状态
- `character_collectbox_slots`
- 主背包虚拟货币槽
- 晶体
- `accounts.epic_piece_counts`
- 容器状态

保存触发点：

- `ClockService` 定时保存
- `InventoryContext.Unregister`
- 断线
- 返回选角/切角
- 服务停止 `SaveAllDirty`
- 少数需要强一致 UI 的业务成功后主动 `SaveDirty`

### 2. 事务原则

一次业务同时修改多个模型时，应在同一次 `SaveDirty` 中提交：

```text
背包槽 + detail
背包槽 + 称号簿
背包槽 + 收集箱
背包槽 + 成就
背包槽 + 锁列表
```

不要这样做：

```text
先直接写 detail 表
再改在线背包
等待以后 SaveDirty 写主表
```

这会产生孤儿 detail 或主表/detail 不一致。

### 3. Detail 即时保存

当前存在即时保存入口：

```csharp
InventoryPersistenceService.SaveAvatarDetailImmediately(detail);
InventoryPersistenceService.SaveCreatureDetailImmediately(characterId, detail);
InventoryPersistenceService.DeleteAvatarDetailImmediately(avatarUid);
InventoryPersistenceService.DeleteCreatureDetailImmediately(characterId, creatureKey);
```

它们只适合 detail 独立变更。即使用这些入口，也必须先改在线 manager，不允许绕过在线模型直接写表。

## 五、常见业务标准流程

### 1. NPC 商店购买

当前标准路径：

```text
handler 解析 itemId/count
  -> 取 InventoryLease 并加锁
  -> InventoryShopRuntimeService.TryBuyNpcItem
  -> 发送购买 ACK
  -> _refresh.SendUpdateItemList 刷目标槽/材料槽
  -> _refresh.SendGoldUpdate 如金币变化
```

购买得到的物品由 `InventoryRewardGrantService` 创建和插入。

### 2. 神秘商店/租赁武器/其他商店型业务

都应视为“校验商店条件 + 扣成本 + 发放物品”：

```text
校验 offer/价格/材料
  -> 扣虚拟槽或主背包材料
  -> InventoryRewardGrantService
  -> ACK
  -> 统一刷新槽位
```

不要恢复旧 `SqliteAssetService.TryAddItem` 或 `SqliteInventoryStore.TryPickupItem` 路径。

### 3. 副本掉落拾取

推荐方向：

```text
DropInfo / DropItem
  -> 如已经生成完整 ItemCore，则 TryInsertExisting
  -> 如只有 itemId/count，则 TryCreateAndInsert
  -> 刷新插入槽位
```

副本掉落装备如果已经在掉落阶段生成了品级、耐久、异次元气息等实例属性，拾取时必须保留该 `ItemCore`，不能按 itemId 重新生成默认装备。

### 4. 任务奖励/卡牌奖励/死亡塔奖励/礼包奖励

推荐先批量规划：

```csharp
InventoryRewardGrantService.TryGrantBatch(inventory, requests, out var result);
```

这样可以先确认空间足够，再一次性应用，避免部分奖励已入包、后续奖励失败。

普通副本免费/付费翻牌和安徒恩连续副本特殊翻牌允许普通物品在对应栏位
无空间时转永久系统邮件。普通翻牌的金币仍直接进入虚拟金币槽，付费牌成本、
直接入包部分、溢出邮件和 durable card effect 必须共用一个事务；安徒恩特殊
翻牌的每日领取计数、直接入包部分和溢出邮件也必须共用一个事务。邮件投递
失败时不得提交翻牌状态或每日次数，也不得通过伪造槽位刷新把奖励标成成功。

### 5. 使用消耗品

推荐流程：

```text
解析 list_type/slot/itemId
  -> 取 lease 并加锁
  -> 先校验业务效果能否执行
  -> InventoryDeleteService.TryUseStackableForClient
  -> 应用业务效果
  -> 发送 ACK
  -> _refresh.SendUpdateItemList 刷消耗品槽
```

如果 ACK 已包含消耗后数量，并且客户端消费已确认，可以省略 0x0E。

### 6. 移动/排序/穿戴/卸下

移动统一走：

```csharp
InventoryMoveService
```

不要在 handler 中手写：

```csharp
var a = inventory.GetItem(listA, slotA);
var b = inventory.GetItem(listB, slotB);
inventory.SetItem(listA, slotA, b);
inventory.SetItem(listB, slotB, a);
```

移动服务需要负责同步：

- 源槽和目标槽 dirty
- 装备锁位置
- 排序锁位置
- 穿戴栏外观
- 宠物/宠物装备状态
- subtype0 tail
- 0x0E 和 NOTI2 所需的结果信息

`list_type=33/34` 由 `KnightShieldHandler` 处理，不走 `InventoryMoveService`；槽 24 的真实盾仍走普通 MOVE，成功后同步 deck。

排序锁移动语义（客户端行为已实证）：位置锁是槽位语义，锁标志字节不得随物品进入穿戴栏——穿戴/脱下涉及 `Equipment` 列表时一律清 `SortLockFlag`（`ShouldPreserveSortLock`），服务端也不做背包格间的锁转移。客户端右键穿戴锁定格物品时会自行解锁该格并主动发 0x02CA toggle，服务端盲翻转应答把换入该格的物品翻成锁定，位置锁由此保持；换入物品若已带 flag=1 落地则会被该 toggle 翻灭。移动完成后不需要额外补发排序锁刷新，也不要主动发 0x02CA。

### 7. 装备强化/附魔/增幅/镶嵌/分解/修理

这些业务必须直接修改在线 `ItemCore`：

```text
InventoryService.GetItem
  -> 修改 ItemCore 语义字段
  -> InventoryService.SetItem 或 MarkDirty
  -> ACK
  -> _refresh.SendUpdateItemList
```

不要再把 `extra_json.extData0`、`TailData2F`、`raw_entry` 当作业务字段。

### 8. 时装/宠物获取

时装和宠物本体获取必须通过 grant/create 流程，让 manager 创建 detail：

```text
InventoryRewardGrantService.TryCreateAndInsert
  -> InventoryCreateService
  -> AvatarDetailManager / CreatureDetailManager
  -> ItemCore.Value 回填 UID
  -> 插入在线背包
  -> SaveDirty 同事务保存主表和 detail
```

业务不要自行生成 UID 或直接写 detail 表。

### 9. 收集箱

当前收集箱不建新物品表，沿用 `character_collectbox_slots` 作为进度表。

放入：

```text
CollectBoxRuntimeService.TryPutItem
  -> 校验 PVF boxIndex/slotIndex/itemId
  -> 在线主背包扣 1 个
  -> CollectBoxModel.SetItem
  -> SaveDirty
  -> 0x0012 删除 ACK
  -> 0x0381 刷收集箱
```

取出：

```text
CollectBoxRuntimeService.TryTakeItem
  -> CollectBoxModel 找 itemId
  -> InventoryRewardGrantService.TryCreateAndInsert(itemId, count=1)
  -> CollectBoxModel.ClearSlot
  -> SaveDirty
  -> 0x0E 刷回背包槽
  -> 0x0381 刷收集箱
```

收集箱内物品只保存 itemId。取出时按默认静态物品重新创建。

### 10. 称号簿/成就

称号簿已迁移到在线模型：

- `TitleBookModel`
- `AchievementModel`
- `CharacterTitleBookRepository`
- `CharacterAchievementRepository`

称号簿内称号需要完整 `ItemCore`。穿戴时从称号簿删除并全字节 copy 到穿戴栏；脱下时从穿戴栏删除并全字节 copy 回称号簿。不要简化成 itemId/count。

成就奖励称号如果是新生成，应按装备默认创建规则生成 `ItemCore`。

PVF 类型为 `[use item]` 的称号成就按以下边界推进：

- 材料规则来自称号任务 QST 的 `[int data]`，不能在 handler 中硬编码任务、材料或奖励映射。
- A21 扩展 `DELETE_ITEM` 只有 `operationType > 1` 表示技能材料消耗；普通丢弃的 `operationType=0/1` 不得推进。
- 进度只使用 `InventoryDeleteService` 返回的服务端实际物品 ID 和实际扣除数量，不能信任请求体中的 itemId/count 作为完成事实。
- 材料扣除、`AchievementModel` 进度和完成时生成的称号必须由 `OnlineInventoryMutationCommitCoordinator` 在同一事务保存；提交失败统一重载在线背包，不发送进度或完成通知。
- 已经为零的成就再次收到材料事件时保持幂等，不得重复生成完成称号。

### 11. 玩家交易

调用链为 `GameProtocolHandler -> ItemTradeHandler -> ItemTradeSession -> InventoryExchangeCommitService -> InventoryPersistenceService/Repository`。`REQUEST_PEER` / `RESPONSE_PEER` 的 trade 类型独立于 Party；`MOVE_ITEMSPACE` 的交易空间由交易 handler 接管，不能进入普通背包跨容器保存。

- 仅允许不同账号的当前在线角色在同频道交易（以服务端 `ListenerPort` 为准），不要求同城镇或同区域；双方仍须处于城镇就绪状态，不能位于副本、选图或互相拉黑。双方 session、角色、UID 和 owned lease 必须保持一致；发送锁取得后再次校验原绑定，旧 generation 不得投影到替代会话。
- 当前支持 Main 中的普通可交易实例（含尚未到期的限时实例）、晶体虚拟槽 354-359 和金币，每人最多九个物品报价。时装、宠物 detail、灵魂虚拟槽、史诗碎片、账号绑定、装备锁和实例交易限制不走本路径。PVF attach type/剩余交易次数复用 `MailboxSendPolicy.ValidateTransferability`；未知策略拒绝。邮件的 `ValidateAttachment` 仍拒绝限时附件，不得将这一渠道限制用于面对面交易。
- 晶体仓库是 `InventoryListType.CrystalWarehouse` 的 wire 别名，不新增物品容器。当前 A21 `MOVE_ITEMSPACE` 实包为 28B：来源空间 36、绝对虚拟槽 357/358、模板 3036/3037、数量、目标交易空间 4；来源槽与模板必须匹配。ACK 保留请求空间，撤回槽位取服务端报价真源，不能信任客户端目标槽。报价快照仅用于校验与协议投影，实际资产从 owned lease 的虚拟余额读取；提交复用虚拟扣除与 grant，并由原双边事务写入 `accounts.cube_*` 和审计，不写普通物品行。接收方数量溢出必须整笔拒绝，不得使用奖励饱和截断损失晶体；普通背包满不阻止晶体钱包转移。
- 限时普通物品在报价和最终提交时通过 `InventoryItemExpirationService.IsExpired` 校验当前绝对到期时间；等待确认期间过期则取消整笔交换。报价、协议 common entry、完整核心转移及落库必须保留原 `ExpireTime`，不重置或延长期限。不同到期时间不得因合堆丢失；不兼容堆叠仍拒绝整笔交换。
- 报价保存来源槽、数量和完整 `ItemCore` 快照，资产仍由原 `InventoryLease` 持有，不在客户端放入交易栏时提前扣除。撤回只修改报价；同一来源槽重复放入当前拒绝。成功落库前必须重新核对来源全字节、余额和双方 lease。
- 状态推进为双方登记完成（5）、双方准备（1）、双方最终确认（3）；首个最终确认不结算，重复或越级确认不产生资产变化。邀请一分钟后失效，在应答或下一次邀请时清理，不使用后台循环。
- 提交在角色 ID 顺序的双 lease 锁内执行。先保存双方已有 dirty 变更作为回滚基线，再加载双方基线快照。单个 SQLite 事务内先扣双方报价，再通过标准 grant 入口插入已有完整实例、调整双方金币，调用双方 `SaveDirtyInTransaction`，最后一次 commit；审计与资产同事务。满包、金币上限或任何一方保存失败均回滚交换，并在原 lease 内恢复基线。此前独立业务的 dirty 变更不得丢失。
- 对 PVF `trade limit` 物品扣减接收实例的剩余次数。合并堆叠前比较数量以外的完整核心，不能因通用合并策略只比较模板/附魔等级而丢失交易次数等实例状态；不兼容时拒绝整个交换。
- 跨区域交易表示双方可在不同城镇/区域发起、接受并完成交易，不表示场景切换保留交易窗口。取消、返回选人、进入选图、主动切区（`SET_USER_AREA`）、传送、进入 PvP 房间及断线仍清理交易绑定。成功时先按现有入口同步寻物任务投影，再发送结束通知和权威 Main `ITEM_LIST`；失败不发成功结束。通知失败不撤销已经提交的资产，重登从数据库恢复结果。

## 六、已清理旧组件的处理规则

### 1. `IAssetService` / `SqliteAssetService`

- `TryAddItem`
- `TryRemoveItem`
- `CountItem`
- `GrantGold`
- `TrySpendGold`
- `LoadSnapshot`

- 禁止重新新增 `IAssetService` / `SqliteAssetService` 类型或依赖
- 新 handler 构造函数不要注入旧资产门面
- 旧业务迁移时，应把 `TryAddItem` 改为 `InventoryRewardGrantService`

- `CountItem` 改为 `inventory.CountMainItem`

### 2. `IInventoryStore` / `SqliteInventoryStore`

- 禁止重新新增 `IInventoryStore` / `SqliteInventoryStore`

移动当前以 `InventoryMoveService` 为准。

- `InventoryMutationResult`
- `InventoryMutationSet`
- 具体业务 result
- `InventoryRewardGrantResult`

旧表已经退出新基线。历史结构只允许出现在 repository/codec 的解码单元测试、离线诊断资料或一次性人工排错脚本中，不得重新接入在线服务。

业务代码一旦进入在线路径，只能看到 `InventoryService + ItemCore + Detail`。

## 七、迁移一个业务时的检查清单

迁移前先问：

1. 这个业务是在线角色业务吗？
2. 它是否需要修改背包、仓库、穿戴栏、时装、宠物、称号簿、收集箱或货币？
3. 目前是否还在调用旧表 SQL、旧 DTO 或旧 item 结构？

迁移后必须满足：

1. 写操作从 `InventoryContext` 获取 lease
2. 写操作持有 `lease.SyncRoot`
3. 新物品发放走 `InventoryRewardGrantService.TryCreateAndInsert`
4. 只创建 `ItemCore` 走 `InventoryRewardGrantService.TryCreateOnly`
5. 已有完整物品插入走 `TryInsertExisting`
6. 指定槽扣物品走 `InventoryDeleteService`
7. 按 itemId 扣主背包材料走 `inventory.TryConsumeMainItem`
8. 金币/复活币/胜点/晶体/灵魂走虚拟槽，史诗碎片走 `InventoryService.EpicPieces`
9. 移动走 `InventoryMoveService`
10. 业务不直接写 `character_inventory_items`
11. 业务不直接写 detail 表
12. 0x0E 统一走 `_refresh.SendUpdateItemList`
13. 0x0D 统一走 `_refresh.SendItemListRefresh`
14. 外观变化按需走 `_refresh.SendNoti2AppearanceUpdate`
15. 装备锁变化按需走 0x00FB 刷新
16. 成功路径按需要 `InventoryPersistenceService.SaveDirty`
17. 没有恢复 `SqliteAssetService/IAssetService/IInventoryStore` 依赖
18. 没有新增旧 DTO 作为业务模型

## 八、推荐 handler 形态

推荐写法：

```csharp
public async Task HandleSomething(EnhancedClientSession session, GamePacketHeader header, byte[] body)
{
    if (!TryParse(body, out var request))
        return;

    var (characterId, _) = SessionOwnerResolver.Resolve(session);
    if (!InventoryContext.TryGetLease(characterId, out var lease)
        || !lease.IsOwnedBy(session.SessionId))
        return;

    SomethingResult result;
    lock (lease.SyncRoot)
    {
        if (!SomethingRuntimeService.TryApply(lease.Inventory, request, out result))
        {
            await SendFail(session, header.type, result);
            return;
        }
    }

    if (result.ShouldSaveImmediately)
        InventoryPersistenceService.SaveDirty(lease);

    await SendAck(session, header.type, result);

    foreach (var slot in result.ChangedSlots)
        await _refresh.SendUpdateItemList(session, slot.ListType, slot.SlotIndex);
}
```

核心原则：

- handler 负责解析包、拿 lease、发 ACK、发刷新
- runtime service 负责业务规则和在线模型修改
- repository 只负责 DB
- protocol builder 只负责写包

```csharp
new CommonInventoryItem { ... }
record.ExtraJson = ...

```

```csharp
inventory.SetMainVirtualCount(...)

```

## 十、兼容边界

- 新基线不创建 `character_items`、`account_cargo_items`、`character_equipped_entries` 等旧表。
- 运行时不提供旧背包搬运、旧名称装饰卡迁移或旧晶体槽迁移入口。
- 自测可以构造新 `InventoryService` / `ItemCore` fixture，但不得恢复旧 store、旧 DTO 或旧表 SQL。
- 钱包/货币 DB 门面可以用于非物品主表路径；在线物品数量和金币槽仍以 `InventoryService` 虚拟槽为准。
- 守护者盾牌 33/34 是虚拟空间，不写入普通物品表；主盾真源是穿戴栏槽 24，deck 表只保存 5 个 itemId。

## 附录：当前数据库表结构

以下结构以 `Server/DfoServer/Sqlite/item_schema.sql` 为准。新增表必须同时维护：

- `Sqlite/item_schema.sql`：新库的完整最终形态
- `Sqlite/SqliteMigrations.cs`：新基线发布后的增量迁移，从 schema v2 起按顺序追加

### 1. 角色/账号物品主表

`character_inventory_items` 是角色在线背包模型的主持久化表，`item_core` 固定 99 字节，只保存物品核心语义，不保存协议 entry。

```sql
CREATE TABLE IF NOT EXISTS character_inventory_items (
    item_uid INTEGER PRIMARY KEY AUTOINCREMENT,
    character_id INTEGER NOT NULL,
    list_type INTEGER NOT NULL,
    slot_index INTEGER NOT NULL,
    item_core BLOB NOT NULL CHECK(length(item_core) = 99),

);

CREATE INDEX IF NOT EXISTS idx_character_inventory_items_character_space
    ON character_inventory_items(character_id, list_type, slot_index);
```

`account_inventory_items` 是账号仓库物品表。账号仓库独立于角色背包，查询主键以 `account_id` 为准。

```sql
CREATE TABLE IF NOT EXISTS account_inventory_items (
```

`account_cargo_state` 只保存账号仓库状态，不保存具体物品。

### 2. 时装 detail

时装 `ItemCore.Value` 保存独立的 avatar UID，不和 `character_inventory_items.item_uid` 绑定。协议需要的期限、染色、徽章孔数据从 `character_avatar_detail` 读取。

透明克隆时装和转职光环都可能写入 `clear_avatar_id`，语义相反，不能混用：

- 透明克隆时装：`clear_avatar_id` 是被克隆外观模板 ID。USERINFO / 0x0D 的 `item_id` 仍是克隆装扮（属性用克隆自身，含其孔位）；外观 Display 用 `clear_avatar_id`，Link 用克隆自身。
- 转职光环：穿上时 `clear_avatar_id` 绑定被覆盖光环的**实例 avatar uid**，卸下清空绑定。USERINFO 装备槽 9 的 `item_id` 保留转职光环自身；协议关联字段从该 uid 解析为原光环**模板 ID**，紧接 `u32 长度 + 原实例镶嵌数据（18B）`，之后才写附魔、转职光环自身 jewel/color 和其余装备字段。该条件块由 A21 `1182850 -> 1637740 -> 274FBE0` 消费；`1A7D860` 使用模板 ID 恢复主体，`vtable+0x110` 应用关联实例的孔。不得把 uid 直接写到模板字段，也不得省略非零关联对应的条件块。
- 原光环和转职光环的 detail 保持独立，不把原实例镶嵌持久复制到转职光环。快照只读；未绑定或绑定失效时不得按背包剩余数量/模板猜测并写回关联。外观 Display 使用转职光环，Link=0。登录、副本和刷新保持原有 USERINFO 次数与时序；禁止通过预装原光环、重复 USERINFO 或清空第一包技能/奖励字段来重建继承。USERINFO subtype1/subtype3 与支援角色共用装备 writer，必须一致传入关联实例快照。


```sql
CREATE TABLE IF NOT EXISTS character_avatar_detail (
    item_uid INTEGER PRIMARY KEY,
    owner_id INTEGER NOT NULL DEFAULT 0,
    character_id INTEGER NOT NULL DEFAULT 0,
    item_id INTEGER NOT NULL DEFAULT 0,
    expire_date INTEGER NOT NULL DEFAULT 0,
    clear_avatar_id INTEGER NOT NULL DEFAULT 0,
    jewel_socket BLOB NOT NULL CHECK(length(jewel_socket) = 30),
    color1 INTEGER NOT NULL DEFAULT 0,
    color2 INTEGER NOT NULL DEFAULT 0,
    delete_date INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX IF NOT EXISTS idx_character_avatar_detail_character
    ON character_avatar_detail(character_id);

CREATE TABLE IF NOT EXISTS character_avatar_uid_sequence (
    avatar_uid INTEGER PRIMARY KEY AUTOINCREMENT
);
```

### 3. 宠物 detail

宠物 detail 复用 `character_creatures`。当前 `CreatureDetail.ExpireDate` 主要由模型/PVF 静态期限推导，不是 `character_creatures` 的独立列。

在线饱食度结算必须先在 owned `InventoryLease.SyncRoot` 内做只读预览，只有 `CreatureDetail.Stomach` 实际变化时才开启事务并标记 detail dirty。分钟巡检与全局背包保存必须保持 Clock 顺序，不得通过 `Task.Run` 并行写同一个 SQLite；宠物复活入口为真实回城入口与副本内喂食救活刚饿死的出战宠物（后者补发 REVIVAL_CREATURE(0x006B) 再发 0x0067），死亡检查失败重试必须有正延迟。副本内扣减的结算锚点在提交后按“已扣点数 × 60 / 消耗乘区”从旧锚点前进，小数时间余额保留在锚点内，不按结算时刻重置到当前时间；存库整数值视为锚点时刻的精确饱食度，死亡判定以真实 stomach 耗尽（≤ 0，允许极小 epsilon）为准，存活期间可见值钳制下限 1。分钟巡检算出饱食度为 0 时必须同步走死亡流程（取消死亡 timer、清锚点、alive 置 0、登记已通知 key，DIED 通知异步派发），不得静默写 0；饱食度已为 0 的宠物不得重复调度即时死亡检查。分钟巡检结算后可见值变化时，服务端经 ClockService 同名 one-shot 异步下发 0x0067 state 包（int32 creatureKey + int32 stomach；喂食、复活、巡检、进图锚定统一使用该格式，不可用富格式 entry）锚定客户端显示，进图时同样锚定一次，同名调度替换旧调度做节流。

```sql
CREATE TABLE IF NOT EXISTS character_creatures (
    character_id INTEGER NOT NULL,
    sort_order INTEGER NOT NULL,
    creature_key INTEGER NOT NULL,
    field04 INTEGER NOT NULL DEFAULT 0,
    mode_flag INTEGER NOT NULL DEFAULT 0,
    progress_value INTEGER NOT NULL DEFAULT 0,
    mode1_field0a INTEGER NOT NULL DEFAULT 0,
    mode1_field0b INTEGER NOT NULL DEFAULT 0,
    field_after_value INTEGER NOT NULL DEFAULT 0,
    creature_text BLOB,
    tail_flag INTEGER NOT NULL DEFAULT 0,
    extra_json TEXT NOT NULL DEFAULT '{}',
    PRIMARY KEY (character_id, sort_order),
    FOREIGN KEY (character_id) REFERENCES characters(character_id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_character_creatures_key
    ON character_creatures(character_id, creature_key);

CREATE TABLE IF NOT EXISTS character_creature_uid_sequence (
    creature_uid INTEGER PRIMARY KEY AUTOINCREMENT
);
```

## 新版背包审计

新版在线背包不复用旧 `item_audit_log`。该旧表已从新基线删除；新架构统一写入 `inventory_audit_log`。

审计表只记录摘要，不保存 `before_core` / `after_core` 的 99B 原文，避免数据库膨胀。默认字段包括：

- `session_id`：本次在线背包租约的 session。
- `owner_scope` / `owner_id`：角色物品为 `character + character_id`，账号仓库和晶体为 `account + account_id`。
- `character_id` / `account_id`：便于按角色或账号排查。
- `action_name`：当前由持久化层生成 `inventory_slot_create`、`inventory_slot_update`、`inventory_slot_delete`、`inventory_virtual_count_update`。
- `list_type` / `slot_index`：发生变化的物品空间和槽位。
- `item_id` / `item_kind`：变化主体。
- `value_before` / `value_after`：`ItemCore.Value` 的前后值。装备是品级/实例值，堆叠物是数量，时装/宠物是 UID 语义。
- `count_before` / `count_after` / `count_delta`：按业务数量解释后的前后数量。不可堆叠物品按 0/1 记录。
- `before_core_hash` / `after_core_hash`：99B `ItemCore` 的 SHA256，用于定位“内容确实变化”，但不把完整字节长期落审计表。
- `payload_json`：预留给后续高层业务补充原因、请求参数、奖励来源等摘要。

写入时机：

```text
InventoryService 发生变更
  -> 标记 dirty slot / dirty virtual count
  -> InventoryPersistenceService.SaveDirty(lease)
     -> 在同一事务中读取数据库旧值
     -> 与在线 InventoryService 新值对比
     -> 写 inventory_audit_log
     -> 保存新物品数据
     -> commit
     -> ClearDirtyState
```

这样审计记录的是最终会落库的差异，而不是业务中间尝试动作。业务内部即使先改内存再回滚，只要最终字节和数据库一致，就不会产生无意义审计。

接入要求：

- 新业务不要直接调用旧 `InventoryAuditLogger`。
- 新业务不要为了审计去直接写数据库；只要通过 `InventoryService` 修改在线模型，并保证 `SaveDirty` 被调用即可。
- 需要更细的业务原因时，再在对应 runtime service 增加高层 `payload_json/action_name` 扩展；不要把完整 `ItemCore` BLOB 放进审计表。
- `AvatarDetail` / `CreatureDetail` 当前仍由 detail repository 保存，默认不纳入物品槽审计。后续如果需要追踪染色、徽章、宠物名字等 detail 变化，应单独增加 detail 审计事件，而不是混入 `item_core` 槽位事件。

当前表结构：

```sql
CREATE TABLE IF NOT EXISTS inventory_audit_log (
    audit_id INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    session_id TEXT,
    owner_scope TEXT NOT NULL DEFAULT 'character' CHECK(owner_scope IN ('character', 'account')),

    account_id INTEGER NOT NULL DEFAULT 0,

    slot_index INTEGER,
    item_id INTEGER NOT NULL DEFAULT 0,
    item_kind INTEGER NOT NULL DEFAULT 0,
    value_before INTEGER NOT NULL DEFAULT 0,
    value_after INTEGER NOT NULL DEFAULT 0,
    count_before INTEGER NOT NULL DEFAULT 0,

```
