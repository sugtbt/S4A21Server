> 本系统**移植自 86JP**（`86JP_friend`）并适配 A21 客户端/架构；业务语义与协议字节布局沿用

## 1. 概述

### 1.1 功能范围

| 能力 | 入口 | 状态 |
|---|---|---|
| 单向好友关系存储 | `united_friend_relations` 表 | ✅ 生产 |
| 添加好友 | `0x0122 ADD_UNITED_SERVER_FRIEND` | ✅ 生产 |
| 删除好友 | `0x0123 DELETE_UNITED_SERVER_FRIEND` | ✅ 生产 |
| 好友列表下发/刷新 | `0x0111 UNITED_SERVER_FRIEND_INFO` | ✅ 生产 |
| 上线/下线推送 | `0x0112 INOUT_UNITED_SERVER_FRIEND` + `0x0002 USERINFO` + `0x0006 USER_LEAVE` | ✅ 生产 |
| 状态变更推送（在线/繁忙/PvP） | `0x0002 USERINFO` | ✅ 生产 |

### 1.2 核心语义

1. **好友关系是单向的**：A 添加 B 只记 `A→B`，B 未必添加 A。`united_friend_relations` 表每行 `(owner_name, friend_name)` 只表示 a→b，加载时**不补反向边**。
2. **推送方向是"谁的面板显示谁"**：谁把 B 加为好友（`IsFriend(观察者, B)`），谁收到 B 的通知。A 删 B 后，B 的一切推送自动对 A 停止（门控自然断开）。
3. **绿/灰图标是场景实体驱动的**，不是好友树节点状态位。登录/上线推 USERINFO 注入实体 → 绿；登出推 USER_LEAVE 移除实体 → 灰。
4. **场景实体只在同频道可见**；上下线聊天通知 `0x0112` 跨频道也推（无实体）。
5. **等级/职业刷新是事件驱动的**：升级/转职由【升级者主动推送】重推好友列表（§4.7），不做定期刷新——单进程内存实时，可即时推送，无延迟。

### 1.3 架构

- 无 DI 容器：`UnitedFriendSystem` 是静态单例（`DfoServer.Game.Friends`），`lock(Sync)` 保护内存图。
- 持久化走 SQLite 表 `united_friend_relations`（§2.2），数据访问经 `UnitedFriendRepository`；建表由
  schema/迁移负责（新库 `item_schema.sql`、旧库 `SqliteMigrations` v9），**无运行时隐式建表**（AGENTS.md 硬性约定）。
- 会话目录 `ISessionDirectory`（`DfoServer.Game.Session`）：`RegisterReplacingAsync` 在 init 包流之前把
  选角会话注册进目录，init builder 据此反查 self 会话；挂载点据此遍历在线会话。
- 所有发包走 `GamePacketEnvelopeBuilder.Build(cmd, type, body)` + `GamePacketWriter` 顺序写字段。
- 日志统一 `FileLogger.Log`（`[UnitedFriend]` 前缀）。

## 2. 数据模型

### 2.1 内存结构

```csharp
Dictionary<string, HashSet<string>> Friends;   // a → {b1, b2, ...}，键区分大小写（与角色名一致）
```

- `GetFriends(name)`：name 的好友名列表（Ordinal 排序）。
- `IsFriend(a, b)`：a→b 是否存在（方向敏感）。
- `RecordFriendship(a, b)`：加 a→b 边（幂等）+ 持久化。
- `RemoveFriendship(a, b)`：删 a→b 边，空集清理 + 持久化，返回是否存在。

**运行期权威是内存图**：上线/下线/状态/列表刷新的全部查询（`IsFriend`/`GetFriends`）都只走内存
`Friends`（O(1) 哈希命中），数据库表只在启动加载、加边、删边时访问。单进程、好友关系全量常驻内存。

### 2.2 持久化 `united_friend_relations` 表

表结构（BINARY 大小写敏感，对齐角色系统 `characters.name`）：

```sql
CREATE TABLE IF NOT EXISTS united_friend_relations (
    owner_name  TEXT NOT NULL,                  -- a（添加者）
    friend_name TEXT NOT NULL,                  -- b（被添加者，单向 a→b）
    created_at  TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (owner_name, friend_name)        -- 唯一约束 + 正向查询索引
);
CREATE INDEX IF NOT EXISTS idx_united_friend_relations_friend
    ON united_friend_relations(friend_name);     -- 覆盖反向查询"谁把 X 加为好友"
```

- 建表双路径（与其它表项一致，CONTRIBUTING/AGENTS 硬性要求两处同步维护）：
  - **新库**：`item_schema.sql` 直接建表（`SqliteDatabaseBootstrap.CreateCurrentDatabase`）。
  - **旧库**：`SqliteMigrations` **v9** `add_united_friend_relations`（`ApplyUnitedFriendRelations`，
    基线 `BaselineId="86jp-database-v1"`）。既有库经 `SqliteMigrations.Apply` 升级补建。
  - 删除角色 slot 压缩随 `fix/delete-character-slot` 追加 **v12** `compress_character_slot_holes`
    （`ApplyCompressCharacterSlotHoles`，幂等：已连续库与新库无变化；v10/v11 已被
    `add_game_events_and_joust`、`convert_client_text_blobs_to_gbk` 占用，合并 master 后顺延）。
- `UnitedFriendRepository` 构造调 `SqliteDatabaseBootstrap.Initialize(databasePath, schemaFilePath)`，
  只做表 CRUD，**不运行时隐式建表**。

**为什么用角色名做键（而非 `character_id` 外键）**：

1. **联合服好友可能跨服**。客户端协议 ADD 携带 `targetUserID` 与名字，但本服 `characters` 表不含
   其它服的对方角色，`character_id` 没有跨服对应物；名字是协议里唯一稳定、跨服可比的标识。
2. **好友关系应存活于角色删除之后**。若加 `FOREIGN KEY ... ON DELETE CASCADE`，角色删除会连带清掉
   其好友边；而删除角色后玩家重练同名角色，好友关系应当还在。名字键天然满足这一点。
3. 名字键与协议载荷（`0x0111` entry、`0x0112` 通知都只带名字）同构，加载/回写零转换。

**为什么对齐大小写敏感**：`characters.name` 唯一索引为 BINARY（大小写敏感），`Abc` 与 `abc` 是两个
不同角色；好友键必须与之一致。若用 NOCASE/忽略大小写，两个不同角色会被当成同一好友（内存字典同键
互相污染好友列表、表 PK 冲突导致 INSERT 失败）。

**为什么 PK + 反向索引**：`PRIMARY KEY (owner_name, friend_name)` 同时充当唯一约束与正向查询索引
（`WHERE owner_name=?` 免排序命中）；`friend_name` 索引覆盖反向查询（`WHERE friend_name=?`，即
"谁把 X 加为好友"）。两张查询方向各 O(log n)，行短、占用极小。

**写边/删边无显式事务**：单条 `INSERT OR IGNORE` / `DELETE` 由 SQLite 单语句原子执行；不属于
"多表组成的一次业务写入"（CONTRIBUTING 约定只在多表写同一事务时才需要显式事务）。

## 3. 协议总览

统一约定：

- **请求 ACK 复用请求 CMD type**：客户端发 `0x0122`/`0x0123`，服务端 ACK 也用同 type 回。
- **失败 ACK**：body = `[0x00, errorCode]`（2B）。客户端分派系统预读 flag：`0x00` → 错误弹窗（errorCode→文案）；非 0 → 成功。
- **成功 ACK（united-server 好友）**：body = `[0x01][3×int32]`（13B）。flag=0x01 → 余下 12B 走客户端统一响应分派。
- **命令 vs 通知**：请求/ACK 用 `cmd=0x01`；服务端主动通知（列表、实体、聊天）用 `cmd=0x00`。

| type | 名称 | 方向 | 用途 |
|---|---|---|---|
| `0x0002` | USERINFO | S→C | 实体注册/状态更新（subtype0 剩余区第 6 字节 = UserState） |
| `0x0006` | USER_LEAVE | S→C | 实体离开 |
| `0x0111` | UNITED_SERVER_FRIEND_INFO | S→C | 好友列表（subcmd=0 下发 / subcmd=2 删节点） |
| `0x0112` | INOUT_UNITED_SERVER_FRIEND | S→C | 好友上下线聊天通知 |
| `0x0122` | ADD_UNITED_SERVER_FRIEND | C→S / S→C | 添加好友请求 + ACK |
| `0x0123` | DELETE_UNITED_SERVER_FRIEND | C→S / S→C | 删除好友请求 + ACK |
| `0x0124` | PVP_BUDDY_CONN_LIST（复用值） | S→C | **未实现**（仅设计，未发实际代码） |

## 4. 协议流详解

### 4.1 添加好友（C→S `0x0122`）

**请求 body**（与 86JP 一致）：

```
[targetUserID:u16][operation:u8][nameLen:u32][name:GBK]
例：添加 "abc" → FF-FF-01-03-00-00-00-61-62-63 (10B)
```

- `targetUserID=0xFFFF`：客户端本地缓存未命中，用名字查找。
- `operation=0x01`：添加。

**处理器**：`UnitedFriendSystem.HandleAddUnitedServerFriend(s, h, body, dir)`，由
`GameProtocolHandler.RegisterFriendHandlers` 注册（`d[(ushort)CmdPacketTypeA21.ADD_UNITED_SERVER_FRIEND]`，
传入 `_worldDependencies.Sessions`）。

```
解析 body → 取 selfName
校验：
  目标名为空            → reject 0x15（该角色不存在）
  添加自己              → reject 0x01（静默，不弹）
  好友数≥100 且非好友   → reject 0x04（好友已满）
  目标角色不存在        → reject 0x15（该角色不存在）
通过 → RecordFriendship(self, target)
     → 成功 ACK 13B： [0x01][0x1BC6:i32][10:i32][2:i32]
     → NotifyFriendAddedAsync：被加好友在线且同频道 → 推其 USERINFO（图标绿）
     → SendFriendListAsync 全量刷新（subcmd=0 ×2）
```

**成功 ACK 13B 为何必须**：ADD/DELETE 共享统一响应分派——dispatcher 读 flag 非 0 后把余下 12B 交给
统一响应解析 `3×int32`，`B−C>6` → 设 friend_manager flag=1（激活好友面板）。发不足 13B 会静默 ret，
friend_manager 不激活。`fieldA=0x1BC6` 是有效范围下界。

**失败 ACK**：`[0x00, errorCode]`。errorCode 映射：

| errorCode | 客户端文案 |
|---|---|
| `0x04` | 好友已满，无法继续添加好友 |
| `0x07` | 普通频道限制（单区环境恒不触发，不实现） |
| `0x15` | 该角色不存在 |
| `0x01` / `0x0D` / `0x85` / 其他 | 静默（不弹） |

### 4.2 删除好友（C→S `0x0123`）

> ⚠️ **请求 body 与 ADD 不同构**（血泪坑，见 §6.3）。

**请求 body**：

```
[operation:u8][targetCharId:u32][name:GBK 到 body 尾]
例：删 characNo=4 "8888" → 01-04-00-00-00-38-38-38-38 (9B)
```

- **无** `[u16 targetUserID]` 前缀、**无** `[u32 nameLen]` 长度前缀；name 直达尾部。
- `targetCharId` 是被删好友的角色 ID（客户端本地节点查询命中）。

**处理器**：`UnitedFriendSystem.HandleDeleteUnitedServerFriend`（同 ADD 注册）。

```
解析 body：op=body[0], charId=u32(body,1), name=body[5..]
目标名兜底：body name 为空时按 charId 反查 _characterRepository.GetById().DisplayName
校验：
  目标无法解析 → reject 0x15
  自身无名     → reject 0x15
  非好友       → reject 0x05（防御性；"对方不在好友名单中"文案由客户端本地检查弹出，见 §6.4）
通过 → RemoveFriendship(self, target)
     → 成功 ACK 13B（与 ADD 同构）
     → SendFriendDeletedAsync（0x0111 subcmd=2 删节点）
     → SendFriendListAsync 全量刷新（subcmd=0 ×2）
```

### 4.3 好友列表（S→C `0x0111`）

**初始化下发（S4A21 差异：走 init 包流，非登录 hook 手动发包）**：

- `NewCharacterInitSequence` 在 init 包流里注册 `UnitedServerFriendInfoBodyBuilder`（IInitPacketBuilder，
  NotiType=`0x0111`），**连发 occ=0/1 两遍**：
  ```csharp
  Raw(0x00, (ushort)NotiPacketTypeA21.UNITED_SERVER_FRIEND_INFO, 0);
  Raw(0x00, (ushort)NotiPacketTypeA21.UNITED_SERVER_FRIEND_INFO, 1);
  ```
- builder `TryBuild`：`ISessionDirectory.TryGet(CharacterId)` 反查 self 会话（`RegisterReplacingAsync`
  在 init 包流之前已注册）→ `UnitedFriendSystem.BuildFriendListInitBody(self, dir)`。self 未水合/无名 →
  8 字节空态（`[subcmd=0][count=0]`）兜底，保持基线总是发包。

**subcmd=0 下发**（init 两遍；Add/Delete 后经 `SendFriendListAsync` 全量刷新，同样两遍）：

```
[subcmd:i32=0][count:u32=N]
+ N × [sR:u8=1][channel:u16][nameLen:u32][name:GBK]
      [Lv:u8][Job:i32][GrowType:u8][Y:u8=0][Z:i32=0]
```

- entry 里 `channel` **三态**：同频道在线=0（不显示频道文字）、异频道在线=真实频道、离线=0；Lv/Job/GrowType：在线取会话实时值，**离线按名字查 DB character 记录取真实值**（`SqliteCharacterRepository.GetByName`，`delete_flag=0`），查不到（异常/已删）才回退默认值 Lv=1/Job=0/GrowType=0。
- **大区 sR 恒为 1**：本项目**不存在跨区系统**，所有玩家大区固定为默认值 1，不读取/不维护真实大区字段。全链路（列表 entry、0x0112 聊天通知、subcmd=2 删节点）sR 均写死 1。
- **连发两遍原因**：第 1 遍建节点（`+0x5D=0` 被 UI 过滤隐藏），第 2 遍置 `+0x5D=1` 显示。只发一遍会不显示。

**subcmd=2 删节点**（`SendFriendDeletedAsync`，删除好友必须走）：

```
[subcmd:i32=2][count:u32=1][sR:u8=1][nameLen:u32][name:GBK]
```

- 客户端从 RB 树**真正删除**该节点。
- **必须用 subcmd=2**：subcmd=0 只插入/更新节点、**不清陈旧节点**——删除后若只刷 subcmd=0，被删好友节点残留。

### 4.4 上线推送（登录 hook）

`CharacterSessionLifecycleCoordinator` → `NotifyPlayerEnteredGame(self, dir)`：

> **S4A21 差异**：初始好友列表已由 init 包流下发（§4.3），本 hook **不再重复下发列表**，只做单向推送：
> 0x0112 进入频道 + 同频道补发 0x0111 归零频道文字 + USERINFO 场景实体。86JP 的登录 hook 同时下发列表，
> S4A21 已把列表职责移到 init builder。

1. 遍历在线会话 s，分两个方向：
   - **方向1（s 的面板显示 self）**：`IsFriend(otherName, selfName)` →
     - 推 `0x0112` 上线聊天（channel=真实频道 → "X 进入频道"，**跨频道也推**）；
     - 若同频道：**补发 0x0111 列表刷新**（`SendFriendListAsync`）把 0x0112 刚写入的 node+0x54 归零（同频道在线好友不显示频道文字），再推 `0x0002 USERINFO(self)` 注入实体 → 图标绿。
   - **方向2（self 的面板显示 s）**：`IsFriend(selfName, otherName)` 且同频道 →
     - 推 `0x0002 USERINFO(s)` → self 看好友绿。

**0x0112 body**（`BuildChatNoticeBody`，与 86JP 一致）：

```
[channel:u16][sR:u8=1][nameLen:u32][name:GBK][oF:u8=0x00]
channel≠0 → "X 进入频道"；channel==0 → "X 退出频道"
oF=0x00 → 不进黑名单（全程不用 oF≠0）
```

**USERINFO subtype0 body**（`UserInfoSubtype0Builder.BuildNotificationBody`，**A21 布局，与 86JP 不同**）：

```
[subtype:u8=0][count:u16=1][38B 零填充固定头][CharacterId:u16][Name:dstr]
[Job:u8][GrowType:u8][Level:u8][PvpGrade:u8][PvpRatingGrade:u8][UserState:u8]   ← UserState 在剩余区第 6 字节
[外观 count][N × 外观 entry][无工会 64B 尾]
```

> ⚠️ 86JP 的"body 第 6 字节 = UserState"在 A21 **不成立**——A21 在 count 后插了 38B 固定头 + dstr Name，
> UserState 落在剩余区第 6 字节（相对 Job 起算），且 uid = CharacterId（86JP 是独立的 onlineUserId）。

**同频道补发刷新的频率 / 压力副作用**：

- **触发**：每有一个「同频道好友上线」事件，方向 1 向每个同频道观察者补发 1 次 `0x0111`（subcmd=0 ×2，两遍）。补发的列表是**观察者的全量好友列表**，不是单人 entry。
- **量级**：观察者好友数 N → 每次事件 2 包、约 `2×N×(18B+nameLen)`。
- **结论**：好友上线是稀疏事件，低并发环境可接受。**明确不采用去抖/合并**（去抖窗口内其他上线事件会把
  node+0x54 置回真实频道，频道文字残留；0x0112/USERINFO 无法去抖）→ 维持每次补发。

### 4.5 下线推送（登出 hook）

`CharacterSessionLifecycleCoordinator`（`UnregisterAsync` 前）→ `NotifyPlayerDisconnected(self, dir)`：
遍历在线会话 s，`IsFriend(otherName, selfName)`（s 的面板显示 self）：

1. 推 `0x0112` 下线聊天（channel=0 → "X 退出频道"，跨频道也推）。
2. 若同频道：推 `0x0006 USER_LEAVE(uid)` 移除实体 → 图标灰。顺序：先 0x0112 后 0x0006。

**必须在 `UnregisterAsync` 前执行**：目录仍含本会话，才能正确判定在线集合（本会话的登录/下线状态对
其他会话的在线/离线判定有意义）。

**实体不会自动消失** → 无需 MOVE 心跳，登录推一次即可；登出必须主动 USER_LEAVE 才会灰。

> **城镇残留白影处理**（参照 86JP 已知协议验证，见 [MR 142](https://gitgud.io/rewio/86JP/-/merge_requests/142)）：
> 好友离开当前区域（返回选人/切区域/进副本）后，旧区域已生成其场景实体的玩家收不到实体移除，
> 残留城镇白影（实体不会自动消失）。
>
> **目的**：让旧区域玩家屏幕上的离开者实体**立即消失、不残留**。
>
> **达成方式（要发的包）**：向旧区域广播【不含离开者】的 `AREA_USERS(0x0018)` 权威名册，
> 客户端按名册重建实体列表、移除残留。**不用 `USER_LEAVE(0x0006)`**：会销毁队伍成员对象，
> 组队进本时队友客户端闪退。
>
> 抽成共享 `TownAreaRosterDepartureNotifier`，两处复用：
>   1. `TownHandler.SetUserAreaCoreAsync`：切区域/切城镇（记录离开前区域，区域真正变化时触发）
>   2. `DungeonEntryHandler`：进本提交后（`RegisterActiveParticipant` 后，普通/塔/队伍队员三处）
>
> env `DFO_AREA_LEAVE_NOTIFY` 三档：0=不通知、1(默认)=名册对账、2=位置迁移备选（USER_AREA 0x0017）。

### 4.6 状态变更推送（UserState）

`NotifyUserStateChanged(self, dir)`：self 的 UserState 变化后，向 `IsFriend(otherName, selfName)`
**且同频道**的会话推 `0x0002 USERINFO`（subtype0，剩余区第 6 字节带新 UserState）→ 好友面板图标刷新。

**UserState 枚举**（客户端单点判断 `UserState==1 ? 繁忙 : 在线`）：

| 值 | 含义 | 触发场景 |
|---|---|---|
| `0x00` | 在线 | 城镇/回城/副本结算回城等 |
| `0x01` | 繁忙 | 进副本选择/进副本 |
| `0x02` | PvP | PvP 建房/进房 |

**S4A21 已挂载点（7 处）**：

| 场景 | 位置 | UserState |
|---|---|---|
| 进副本选择/进副本 | `DungeonEntryHandler.cs`（`UserState=0x01` 后） | 0x01 |
| 副本结算回城 | `DungeonTownReturnCoordinator.cs`（`UserState=0x00` 后） | 0x00 |
| GIVEUP_GAME / BACK_2_VILLAGE 回城 | `TownHandler.ReturnSelfToTownAsync.cs`（`UserState=0x00` 后） | 0x00 |
| 副本选择界面返回 | `TownHandler.ReturnSelectionToTownAsync.cs`（`UserState=0x00` 后） | 0x00 |
| 死亡复活回城 | `DungeonCombatHandler.cs`（`UserState=0x00` 后） | 0x00 |
| 教程结束回城 | `DungeonTutorialHandler.cs`（`UserState=0x00` 后） | 0x00 |
| 队伍跟随回城 | `PartyHandler.cs`（`UserState=0x00` 后） | 0x00 |

> **为何回城路径必须全接线**：好友图标在同城镇由场景实体驱动（分身重新出现→绿），但**回城到不同城镇时
> 旧区域好友看不到实体重建**，只能靠 `NotifyUserStateChanged` 推 USERINFO 才能让面板恢复「在线」。
> 若回城路径漏接，好友面板会**卡在副本「繁忙」状态**。因此所有回城 0x00 路径必须与
> `DungeonTownReturnCoordinator` 一致接线。

> **剩余待接入（1 处）**：`DungeonRunLifecycle.TryAttachResumedDungeonRun`（断线重连恢复进副本，0x01）
> 是**静态方法，无目录**，需由调用方在返回 `true` 后补调 `NotifyUserStateChanged`。

### 4.7 等级/职业变更推送（事件驱动刷新）

升级/转职后由【升级者主动推送】：向把 self 加为好友的在线会话重推 `0x0111 subcmd=0` 全量好友列表，
刷新列表中 self 的 Lv/Job/GrowType。

**设计决策：事件驱动，不做定期刷新。**

- **依据：服务端业务决策（非反编译结论）**。S4A21 是**单进程**，好友关系图、在线会话、角色数据全在
  内存，升级判定点与好友系统同进程 → 事件驱动**即时**推送，零延迟。
- 官方客户端"好友等级/职业常有延迟"的根源是**跨服架构 + 定期批量同步**，不是客户端问题。本项目无
  跨服层，**不需要也不应该引入定期刷新**。

**推送对象与门控**：所有 `IsFriend(观察者, self)` 的在线会话。**不分频道**——等级/职业是好友【列表
节点数据】，跨频道好友也在列表里显示；这与 USERINFO 场景实体（仅同频道）和 §4.6 状态推送（同频道门控）不同。

**机制**：

1. `NotifyFriendListInfoChanged(self, dir)`（会话版）/ `NotifyFriendListInfoChanged(player, dir)`（名字版）：
   遍历在线会话（排除 self、`Player == null`），`IsFriend(otherName, selfName)` 命中 →
   `SendFriendListAsync(other, dir, GetFriends(otherName))`。
2. `SendFriendListAsync` 组包：在线好友从会话实时取 Lv/Job/GrowType/频道；**离线好友按名字查 DB
   character 记录取真实值** → self 的 entry 自动带最新值。
3. 重推**不误刷绿/灰图标**：图标由场景实体驱动，与列表节点状态位无关。

**S4A21 挂载点（4 处）**：

| # | 位置 | 触发条件 | 目录来源 |
|---|---|---|---|
| 1 | `DungeonProgressNotificationProjector.SendInDungeonLevelUpFollowups`（副本结算升级） | 副本内升级 | `DungeonSharedServices.Sessions` 穿入 Projector |
| 2 | `QuestNotificationProjector`（城镇任务升级/转职） | `leveledUp || ChainType==1/2` | `GameSession → QuestManager → Projector` 三级穿 `ISessionDirectory` |
| 3 | `GameProtocolHandler` `INCREASE_STATUS`（经验道具升级） | 前后比较 `Level` 变化 | `_worldDependencies.Sessions` |
| 4 | `CharacterSelectHandler` 删除角色（`SoftDeleteAndCompactSlots` 后） | 角色删除 | `_sessions` |

- **Quest 路径为何能免穿会话**：`QuestNotificationProjector` 只有 `PlayerContext`（无会话引用），
  `NotifyFriendListInfoChanged` 提供 **PlayerContext 名字版重载**（循环 `dir.GetAllGameSessions()`，
  按名字匹配排除 self），只需把 `ISessionDirectory` 穿进 `QuestManager` 构造链。
- **Quest/经验道具用"前后比较"**：底层服务（`QuestManager`/`InventoryHandler`）不持有会话目录引用。
  为不向纯逻辑服务注入目录，在分派层用前后比较触发。Quest 升级与转职经 QuestNotificationProjector 统一判定。
- ⚠️ **副本内任务升级可能双触发**（副本结算投影 + 任务投影各推一次）：幂等无害（重推全量列表，
  无状态破坏），可接受。
- **无延迟说明**：升级判定同步完成后立即组包推送，同进程内即时到达。

### 4.8 角色删除 / 更名响应（生命周期 hook）

**触发场景**：关系键是**角色名**，角色被删除（名字不再存在）或更名（名字改变）都会让旧键悬空，必须同步清理/迁移表项并刷新相关好友的面板。

**删除角色**（挂载在 `CharacterSelectHandler` DELETE_CHARACTER `SoftDeleteAndCompactSlots` 成功后，best-effort，失败只记日志不影响删除 ACK）：
- `HandleCharacterDeletedAsync(name, dir)`：
  1. **owner 方向**：内存图移除 `name` 键（X 加的所有好友一并消失）。
  2. **friend 方向**：所有把 X 加为好友的 owner 的列表移除 X。
  3. **表**：`DELETE WHERE owner_name=X OR friend_name=X`（单条原子）。
  4. **通知**：只通知 `friend_name=X` 的在线会话（单向语义——X 加的人其面板不显示 X，无需通知）。

**更名角色**（`HandleCharacterRenamedAsync(oldName, newName, dir)`，**预留能力**）：
- **owner 方向**：X 的整条好友边迁移键到 Y（Y 已有出边时**并集合并**）。
- **friend 方向**：所有把 X 加为好友的 owner 的列表把 X 换成 Y。
- **表**：两方向 `UPDATE`（owner_name、friend_name）放在**一个事务**里提交，避免半更新。
- **通知**：与删除相同（向受影响 owner 推送）。

**通知机制（删除/更名共用 `NotifyFriendNameRemovedAsync`）**：对受影响 owner 的在线会话先发 `0x0111
subcmd=2` 删旧节点，再 `SendFriendListAsync` 全量刷新。subcmd=0 全量刷新不清陈旧节点——只全量会导致
被删/被改名角色残留在面板。

**设计要点**：
- **受影响 owner 列表在变更前快照**：变更后 `IsFriend(owner, oldName)` 恒为 false，无法现算；锁内先收集再变更。
- **更名无入口**：S4A21 服务端未实现改名卡，`HandleCharacterRenamedAsync` 为**预留能力**，未来改名功能接入时调用。

## 6. 开发细则（易错点）

### 6.1 单向门控方向（最高频错误）

推送条件一律是 **`IsFriend(观察者, self)`**（谁把 self 加为好友），**不是** `IsFriend(self, 观察者)`。

```csharp
// ✅ 正确：s 的面板显示 self
if (IsFriend(otherName, selfName)) { ... 推 self 的 USERINFO/0x0112 给 s ... }
// ❌ 错误：会变成"self 的面板显示 s"才推，方向反了
```

方向2（self 看好友绿）才是 `IsFriend(selfName, otherName)`。

### 6.2 同频道 vs 跨频道

- 实体（`0x0002`/`0x0006`）：**仅同频道**推。频道由监听端口映射（`GameNetworkConfig.ResolveGameChannel(s.ListenerPort).ChannelId`）。
- 聊天通知（`0x0112`）：**跨频道也推**（无实体，仅按好友关系门控）。

### 6.3 ADD 与 DELETE body 不同构（血泪坑）

- ADD：`[u16 targetUserID][u8 operation][u32 nameLen][name]`
- DELETE：`[u8 operation][u32 targetCharId][name 到尾]`（无长度前缀）

曾按 ADD 格式解析 DELETE → nameLen 读到垃圾、name 空 → 误回 0x15 → 客户端弹"列表不存在该角色"。
**改格式必须实测抓包确认，别靠猜。**

### 6.4 "对方不在好友名单中"是客户端本地检查

客户端查**本地**好友树，未命中直接弹字符串且**根本不会发包**。所以正常 UI 下删非好友时文案由客户端
自己弹，服务端 not-exists 分支（回 `[0x00, 0x05]`，0x05 未注册 → 客户端静默）只是状态不同步的防御回包。

### 6.5 成功 ACK 必须 13B

统一响应分派把 flag 后 12B 交给 `3×int32` 解析。发不足 13B → 静默 ret → friend_manager 不激活。
ADD/DELETE 成功 ACK 都发 `[0x01][0x1BC6][10][2]`（B−C=8>6 → flag=1）。

### 6.6 列表刷新三通道协同

- **subcmd=0 ×2**：建节点 + 置显示。不清陈旧节点。
- **subcmd=2**：真删节点。删除好友**必须先 subcmd=2** 再 subcmd=0 全量刷新。
- 空好友列表：subcmd=2 删完节点后 count=0，`SendFriendListAsync` 直接 return（面板已空，无需再刷）。

### 6.7 并发与幂等

- 所有图操作在 `lock(Sync)` 内，`RemoveFriendship` 幂等；校验后并发移除 → race 分支回 `[0x00, 0x05]`。
- Add 幂等：`RecordFriendship` 已存在时不重复写盘。
- `GetOnlineSessions(dir, self)` 对 `dir == null` 返回空列表（自测/单例模式下目录可空）。

### 6.8 空值/异常防护

所有推送方法：self 无名 / 目标名空 → 直接 return；try/catch 包裹，失败仅日志不中断主流程。
回城路径 `_sessions`/`_svc.Sessions` 均做 null 检查（部分 handler 在自测/单例模式下 Sessions 可为 null）。
init builder `TryBuild` 失败 → 8 字节空态兜底，保持 init 包流总是发包。

## 7. 协议字节布局（S4A21 代码事实）

> 字节布局沿用 86JP 已实锤结论（两项目实现一致），本节以 S4A21 代码为准汇总。
> **A21 客户端的反汇编地址（86JP 的 VA 表）不适用**，A21 侧如需客户端级证据需另行逆向；本项目的
> 布局依据 = S4A21 代码实现 + 86JP 客户端逆向 + 86JP 实机验证。
> §7 小节编号沿用 86JP 约定（0x0111=§7.3 / 0x0122·0x0123=§7.4 / errorCode=§7.5），
> 代码注释里的交叉引用按此编号；A21 特有的 USERINFO subtype0 布局并入 §7.2。

### 7.1 0x0112 上下线聊天

```
[channel:u16][sR:u8=1][nameLen:u32][name][oF:u8=0]
```

- `channel≠0` → "X 进入频道"；`channel==0` → "X 退出频道"。
- 只写 `node+0x54=ch`、`node+0x5E=(oF!=0)`；**`oF≠0` 会进黑名单**，全程 `oF=0x00`。
- ⚠️ **0x0112 不能让在线图标变绿**（黑名单位），绿/灰只由场景实体（USERINFO/USER_LEAVE）驱动。

### 7.2 USERINFO subtype0（A21 布局）

```
[0][count:u16=1][38B 零头][CharacterId:u16][Name:dstr]
[Job][GrowType][Level][PvpGrade][PvpRatingGrade][UserState]   ← 剩余区第 6 字节
[外观 count][N × 外观 entry][无工会 64B 尾]
```

- **UserState 落点**：剩余区第 6 字节（相对 Job 起算），非整个 body 第 6 字节。
- **外观**：`record.Appearance` 非空 → 过滤 `IsA21RosterAppearanceSlot`（slot 0=帽子 ~ 13=名称装饰卡）；
  空且 CharacterId>0 → 查生产库（`LoadCharacterAppearanceFromDb`）——**自测必须预置非空外观避开**。
- 无工会固定 64B 尾（A21 无工会路径，避免客户端把旧字段当 dstr 长度）。

### 7.3 0x0111 好友列表（subcmd 分派）

| subcmd | 作用 | body 格式 |
|--------|------|-----------|
| 0 | 好友列表刷新（面板显示） | `[0:i32][count:u32][N × entry]` |
| 1 | 列表装载（同 0） | `[1][count][N × entry]` |
| 2 | 删节点（真删 RB 树节点） | `[2:i32][count:u32][N × (sR:u8, nameLen:u32, name)]` |
| 3 | 跨服在线刷新 | 未实现 |
| 4 | 删+重建刷新 | 未实现 |

> **entry 格式（18B+nameLen，全字节消费）**：
> `[sR:u8][ch:u16][nameLen:u32][name][Lv:u8][Job:u32][GrowType:u8][Y:u8=0][Z:i32=0]`
> 字段 Y/Z **无任何消费方**，生产固定 0/0，仅作占位维持 18B 对齐。
> ⚠️ **entry ≠ 23B+nameLen**：count>1 时每多 5B → 后续 entry 起点前移全错位。

**subcmd=0 装载双路径**（解释"连发两遍"）：
- 路径1（命中已有节点）：置 `+0x5D=1` → 设在线 → **绿**
- 路径2（新节点）：RB 树插入，新节点 `+0x5D` 默认 0 → **灰**
- 推论：首见走路径2（灰），重发走路径1（绿）→ **必须连发两遍 subcmd=0**。

### 7.4 0x0122/0x0123 请求与 ACK

| 包 | body |
|---|---|
| ADD 请求 | `[targetUserID:u16][operation:u8][nameLen:u32][name]` |
| DELETE 请求 | `[operation:u8][targetCharId:u32][name 到尾]` |
| 失败 ACK | `[0x00, errorCode]` |
| 成功 ACK | `[0x01][fieldA:i32][B:i32][C:i32]`（13B，生产 `0x1BC6/10/2`） |

成功路径分派：上层 dispatcher 读 `body[0]=success_flag`；`0x00` → 按 `body[1]` 弹 errorCode；非 0 →
余下 12B 传统一响应解析（`3×int32`）：
- 字段A 有效范围 `[0x1BC6..0x1BF5] ∪ [0x1C15..0x1C19]`，超界静默 ret
- `diff = B − C`：`≤0`→静默 ret；`[1..6]`→show_chat_message（不设 flag）；`>6`→设 friend_manager flag=1
- 生产默认 A=0x1BC6, B=10, C=2（diff=8>6 → 设 flag 路径）

### 7.5 errorCode 表

| errorCode | 弹窗文案 | 触发场景 |
|---|---|---|
| `0x04` | 好友已满 | `GetFriends(selfName).Count >= 100` 且非好友 |
| `0x07` | 只能添加相同大区 | 单区环境恒不触发，**不实现** |
| `0x15` | 该角色不存在 | 目标名空 / `GetByName()==null` |
| `0x01` / `0x0D` / `0x85` / 其他 | 无文案 → **静默不弹** | 不能加自己等；删除非好友的 0x05 也走此档 |
