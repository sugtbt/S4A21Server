# 副职业架构业务接入规范

本文说明当前副职业系统的代码结构、状态所有权和业务接入方式，适用于分解师、炼金术师、附魔师、控偶师及后续副职业。

当前已接入分解师完整基础能力，以及附魔师、炼金师和控偶师的基础能力。配方型职业共用配方状态、学习、生产和提取协议边界，职业等级、产物公式及 PVF 定义仍由各职业配置提供。

## 一、核心模型

### 1. ExpertJobState

`ExpertJobState` 是角色副职业领域状态的统一入口，当前包含：

- `GiveUpCount`：所有副职业共享的状态。
- `DisjointMachine`：分解师设备状态。
- `EnchanterMachine`：附魔师设备耐久状态。
- `LearnedRecipeIds`：配方型副职业通过转职、升级或设计图获得的已学习配方。

副职业类型和经验不属于 `ExpertJobState`，继续由角色 subtype0 状态管理。

### 2. Definition、State 和 Projection

- Definition：从 PVF 读取的只读职业规则，例如经验阈值、制作规则、设备耐久和升级费用。
- State：角色或已部署商店的可变状态，例如已学习配方、设备等级和耐久。
- Projection：登录初始化、USERINFO、商店 ACK 和 NOTI 所需的协议模型。

三者分别由 ConfigProvider、领域模型和 Builder 管理，不在同一个类型中混用。

### 3. 商店型和配方型职业

当前副职业按运行形态分为两类：

| 类型 | 主要状态 | 典型入口 |
| --- | --- | --- |
| 商店型 | 已部署商店、访客绑定、设备状态 | 创建、进入、操作、关闭 |
| 配方型 | 已学习配方、制作材料和产物 | 学习配方、制作物品 |

一个职业可以同时拥有配方和商店能力。公共架构按能力组合，不按职业名称复制整套流程。

## 二、总体架构

```text
角色加载
  -> IExpertJobStateRepository
  -> ExpertJobState
  -> ExpertJobStateCodec
  -> ExpertJobInfoSnapshot
  -> ExpertJobInfoBodyBuilder
  -> NOTI 0x00CD

商店型职业命令
  -> ExpertJob Parser
  -> ExpertJobStoreHandler
  -> ExpertJobStoreRuntimeService
  -> 具体职业 Service
  -> InventoryService + ExpertJobState
  -> ExpertJobPersistenceService
  -> ExpertJob PacketBuilder / InventoryRefreshSender / USERINFO

配方型职业命令
  -> 具体职业 Parser 和 Handler
  -> Recipe Definition + 具体职业 Service
  -> InventoryService + ExpertJobState
  -> ExpertJobPersistenceService
  -> 具体职业 ACK / 状态刷新

非商店职业操作
  -> EnchanterHandler 等职业 Handler
  -> 具体职业 Service
  -> InventoryService + ExpertJobState
  -> ExpertJobPersistenceService
  -> 职业 ACK / 背包刷新 / USERINFO
```

公共层负责状态装载、商店生命周期、操作串行化和原子保存。职业层负责资格、成本、产物、经验及职业专属状态变化。

### 2. `Network/Parsers/ExpertJob`

该目录保存副职业命令的请求模型和解析器。目前包含创建商店、进入商店、关闭商店、分解、商店附魔、提取、修理和升级请求。

新增命令时，在此目录增加类型化请求；业务参数由 Parser 输出，Handler 不重复读取原始字节。

### 3. `Network/Handlers/ExpertJobStoreHandler`

`ExpertJobStoreHandler` 是商店型职业的网络适配入口，负责：

- 校验当前角色、场景和商店绑定。
- 取得请求者和所有者的在线背包 lease。
- 取得所有者的操作 gate。
- 调用对应职业服务。
- 保存副职业和背包变化。
- 发送请求者 ACK、所有者 NOTI 和在线状态刷新。

职业公式和 PVF 规则不放入 Handler。

附魔师设备修理由 `EnchanterHandler` 适配；已学习配方生产和附魔师生成宝珠统一由 `ExpertJobCompoundHandler` 分发，装备提取统一由 `ExpertJobExtractionHandler` 分发。设计图作为堆叠物品使用时由背包命令入口识别，再进入 `ExpertJobRecipeLearningService`。这些路径与附魔商店共用同一个 `ExpertJobOperationCoordinator`，避免同一角色的状态并发写入。

### 4. `Network/Builders/ExpertJob`

该目录保存商店创建、进入、关闭和职业操作的包体构造器。Builder 只接受运行态或领域结果，不负责加载状态或计算业务。

### 5. 选择角色初始化

副职业初始化由以下组件共同完成：

| 组件 | 职责 |
| --- | --- |
| `SqliteSelectCharacterDataSource` | 加载职业类型及 `ExpertJobState` |
| `ExpertJobStateCodec` | 生成统一 `ExpertJobInfoSnapshot` |
| `ExpertJobInfoBodyBuilder` | 按职业模式写入 `0x00CD` 包体 |

分解师模式写入分解机等级和耐久；普通配方型模式写入已学习配方列表；附魔师模式还写入卡片资格档位、职业等级和设备耐久。

## 四、状态所有权

### 1. 职业类型和经验

`character_subtype0_fields` 保存：

| 字段 | 语义 |
| --- | --- |
| `expert_job_type` | 当前副职业类型 |
| `expert_job_exp` | 当前副职业经验 |

这两个字段同时用于在线 `PlayerContext.Subtype0Tail` 和 USERINFO subtype0 投影。职业操作增加经验后，需要同步刷新角色在线投影。

### 2. 职业领域状态

`character_expert_job` 保存角色级副职业状态：

| 字段 | 语义 |
| --- | --- |
| `character_id` | 角色主键 |
| `giveup_count` | 通用副职业状态 |
| `disjoint_machine_grade` | 分解机等级 |
| `disjoint_machine_endurance` | 分解机耐久 |
| `enchanter_endurance` | 附魔商店设备耐久 |
| `updated_at` | 更新时间 |

`character_expert_job_recipes` 保存已学习配方：

```text
(character_id, recipe_id)
```

附魔师转职和升级自动学习的配方、通过设计图学习的配方统一保存为 PVF 配方物品 ID。运行时需要内部产品索引时，通过当前 PVF Definition 解析，不在角色状态中重复持久化。

现有结构的选择原则：

- 角色只有一个值的稳定状态使用明确列。
- 可重复的配方、订单或记录使用独立子表。
- 运行时商店和访客关系不落入角色状态表。
- 协议包体不作为数据库状态保存。

### 3. 商店运行态

`ExpertJobStoreRuntimeService` 持有进程内商店状态：

```text
ExpertJobStoreSession
  OwnerSessionId
  OwnerCharacterId
  OwnerUserId
  ExpertJobType
  Kind
  NameBytes / Cost
  TownId / AreaId / Position / Direction
  DisjointMachine / Enchanter 等职业专属设备状态
```

访客进入商店后建立 `ExpertJobStoreVisitorSession`。后续操作通过 visitor session 找到商店所有者，不直接信任客户端重复提交的角色信息。

商店运行态只用于在线发现和路由。设备等级、耐久、配方和经验仍以角色领域状态为持久化来源。

## 五、商店生命周期

```text
未部署
  -> TryCreate
  -> 已部署
  -> TryEnter / Leave
  -> 具体职业操作
  -> TryClose / TryCloseSession
  -> 已关闭
```

### 1. 创建商店

`ExpertJobStoreRuntimeService.TryCreate` 负责公共创建条件和注册：

- 角色拥有与 `ExpertJobStoreKind` 匹配的副职业。
- 角色当前不在副本或队伍中。
- 同一角色没有重复部署商店。
- 商店名称、费用和职业专属状态有效。

分解机的手续费上限、设备等级范围等专属条件由分解师配置提供。附魔商店的手续费上限、耐久和可用技能由附魔师配置及角色状态提供；创建商店本身不消耗耐久。

### 2. 进入和操作

访客按同区域 `OwnerUserId` 进入商店。操作前重新确认：

- visitor session 仍绑定该商店。
- 所有者 session 和商店注册信息一致。
- 请求者与所有者均拥有有效在线背包 lease。
- 当前城镇和区域仍与商店一致。

请求者与所有者相同时复用同一个 lease；其他玩家使用分解机时同时操作两个角色的在线状态。

### 3. 关闭和清理

主动关闭、切换区域、返回选角、切换角色和断线都会移除所有者商店。关闭所有者商店时，同时移除指向该商店的访客绑定。

访客离开或断线只清理自身绑定，不关闭所有者商店。

进入新区域后，服务端会将该区域已有商店重新投影给玩家。

## 六、职业操作入口

商店型职业操作统一采用以下结构：

```text
解析请求
  -> 查找 visitor 与 owner store
  -> 取得 owner operation gate
  -> 取得一个或两个 InventoryLease
  -> 在 InventoryLease.SyncRoot 内调用职业 Service
  -> ExpertJobPersistenceService.Save
  -> 发送请求者结果
  -> 发送所有者状态变化
  -> 刷新经验或物品投影
```

### 1. OperationCoordinator

`ExpertJobOperationCoordinator` 以所有者角色 ID 为键提供 `SemaphoreSlim`。同一角色的分解、提取、修理、升级、设计图学习及后续职业操作共享这条串行化边界。

### 2. InventoryLease

职业服务直接消费 `InventoryService`，但调用方必须先取得属于当前 session 的 lease。

涉及两个角色时，按 `CharacterId` 升序取得两个 `SyncRoot`；自助操作只取得一次锁。锁内只执行在线状态校验和修改，不发送协议包。

### 3. 领域结果

具体职业服务返回类型化结果，例如：

```text
DisjointMachineOperationResult
  ErrorCode
  DisjointResult
  RequesterGold
  OwnerGold
  Endurance
  ExperienceGain
```

Handler 根据结果构造协议投影，不重新计算成本或产物。

## 七、统一持久化

`ExpertJobPersistenceService` 用于一次职业操作同时保存在线背包和副职业状态。

```text
BEGIN TRANSACTION
  InventoryPersistenceService.SaveDirtyInTransaction(requester)
  InventoryPersistenceService.SaveDirtyInTransaction(owner，可选)
  IExpertJobStateRepository 的职业状态写入
COMMIT
```

适用变化包括：

- 请求者材料或目标装备。
- 请求者金币。
- 商店所有者金币。
- 设备等级、耐久或其他职业状态。
- 副职业经验。

具体 Repository 提供 `SaveInTransaction` 一类接口，Handler 不直接写副职业表。保存成功后再发送成功投影。

分解师由 `IDisjointMachineStateRepository.SaveInTransaction` 同时保存分解机状态和经验增长。配方型职业由 `IExpertJobStateRepository` 保存经验及本次自动或手动学习的配方 ID；附魔商店耐久等职业专属设备状态继续由 `IEnchanterMachineStateRepository` 保存。

事务失败时，必须先释放或回滚 SQLite 事务，再通过 `InventoryRollbackRecoveryService` 从已提交状态恢复在线背包；不得在活动事务仍持有锁时打开第二连接恢复。

## 八、PVF 定义

每个职业建立独立 ConfigProvider，将 PVF 投影为只读 Definition。公共商店运行时不解析职业 PVF。

### 1. 分解师

`DisjointMachineConfigProvider` 读取：

- `character/expertjob/disjointer.exj`
- `character/expertjob.etc`

当前 Definition 包含：

- 初始耐久和手续费上限。
- 每次耐久消耗和经验增长范围。
- 基础、追加和大成功分解结果。
- 自助分解规则。
- 各级耐久及修理成本。
- 副职业经验阈值、升级费用和角色等级限制。

`DisjointMachineResultCalculator` 根据分解机等级、装备稀有度、装备状态和装备等级选择这些规则。

### 2. 配方型职业

配方型职业的 Definition 至少应表达：

```text
RecipeDefinition
  RecipeId
  RequiredExpertJobType
  RequiredExpertJobLevel
  Materials[]
  GoldCost
  Products[]
  职业专属参数
```

配方 ID 保留 PVF 身份，学习状态只保存 ID，不把完整配方内容复制到角色表。

### 3. 附魔师

`EnchanterConfigProvider` 读取 `character/expertjob/enchanter.exj`，并结合其中引用的堆叠物品定义建立：

- 职业经验等级、自动学习配方、商店技能和卡片资格档位。
- 怪物卡定义、资格配方及各职业等级的附魔成功率和经验范围。
- 附魔商店初始耐久、耐久消耗及各等级修理规则。
- 提取器等级资格、装备状态结果、追加结果和大成功结果。
- 设计图物品、产品索引、产品物品和学习等级资格；设计图学习按当前附魔师等级加 2 的官方资格窗口校验。

当前版本的装备等级、稀有度和职业等级均以当前 PVF 为准；旧服务端只用于确认业务类别和校验顺序。

### 4. 炼金师

`AlchemistConfigProvider` 读取 `character/expertjob/alchemist.exj`，并结合制作图和提取器的堆叠物品定义建立：

- 职业经验等级、自动学习配方和设计图等级资格。
- 提取器职业等级及 `[alchemist extraction]` 索引。
- 按提取器、装备稀有度和装备状态区分的基础、追加及大成功产物。

附魔师、炼金师和控偶师共用 `EXPERT_EXTRACTION (0x01A0)` 请求及成功结果布局，但基础材料数量公式由各职业配置实现，不在 Handler 中按职业分支计算。

### 5. 控偶师

`DollControllerConfigProvider` 读取 `character/expertjob/doll_controller.exj`，并结合制作图和提取器的堆叠物品定义建立：

- 职业经验等级、自动学习配方、设计图等级资格和制作成功率。
- 提取器职业等级及 `[doll_controller extraction]` 索引。
- 按提取器、装备稀有度和装备状态区分的基础、追加及大成功产物。

控偶师与炼金师复用相同的配方生产、设计图学习、装备提取、事务保存和在线刷新实现。职业差异由各自 ConfigProvider 提供，不在公共 Handler 中维护物品 ID 或产物分支。

## 九、初始化和在线投影

### 1. 登录初始化

`ExpertJobStateCodec.ProjectToSnapshot` 按 `expert_job_type` 生成快照：

- `Mode == 3`：写入分解机等级和耐久。
- `Mode == 1/2/4`：写入已学习配方 ID。
- `Mode == 1`：在配方列表后继续写入卡片资格档位、附魔师等级和设备耐久。
- 无副职业：输出空模式。

`ExpertJobInfoBodyBuilder` 负责将快照写入 `NOTI 0x00CD`。选角初始化顺序为 USERINFO subtype0 → `0x00CD`，结束时再发一次 USERINFO subtype0。

A21 USERINFO0 必须走 `UserInfoSubtype0Builder.BuildNotificationBody`：subtype/版本后保留 38 字节固定头；无工会 64 字节尾偏移 23/24 写入当前 `expert_job_type` / `expert_job_exp`。无副职业时经验为 0，不得把库内历史 `-1` / `uint.MaxValue` 发到线上。尾字段必须带当前职业，否则后一次 USERINFO0 会覆盖已应用的 `0x00CD`。

### 2. 职业任务完成

副职业获得或变更时，在任务完成事务中更新 `expert_job_type`，调用 `SqliteExpertJobStateRepository.InitializeInTransaction` 初始化领域状态，并把 PVF `[skill]` 并入角色技能表。

在线顺序：USERINFO subtype0 → 登录布局 `NOTI EXPERT_JOB_INFO (0x00CD)` → `FINISH_QUEST` ACK → `EXP` / `SET_QUEST_TRIGGER` / `ACCEPTABLE_QUEST_LIST`。当帧不发独立 `SKILLINFO`，不发 USERINFO subtype1。

`0x00CD` 必须与登录相同，走 `ExpertJobInfoBodyBuilder`，用于同步已学习配方；附魔师还包含卡片资格、等级和设备耐久。不得发送放弃阶段的名称串，也不得发送与当前 Mode 不符的错位快照。

`FINISH_QUEST` ACK（`chainType=20`）使用 7 字节 consume（无 reservedTail），随后是 `chainType`、`growNumber` 和两页 4 字节技能（`slot + skillId + level`）。8 字节 consume 会错位闪退。`QuestAckBuilder` 按该布局组包。

### 3. 放弃副职业

`GIVEUP_EXPERT_JOB (0x00EF)` 使用空请求体，由 `GiveupExpertJobRequest`、`ExpertJobGiveupHandler` 和 `ExpertJobGiveupPacketBuilder` 负责协议边界。`ExpertJobGiveupApplicationService` 根据 `ExpertJobGiveupConfigProvider` 提供的当前 PVF 规则，在同一事务中扣除金币、删除职业专属物品和技能、清理全部副职业任务、清空已学习配方及设备状态，并将 `expert_job_type`、`expert_job_exp` 重置为 0。

放弃费用按 `giveup_count` 选择档位；到达最后一档后计数封顶，后续放弃继续使用最后一档费用。重新完成副职业转职任务时，职业经验重置为 0，`giveup_count` 保持不变。

提交成功后由 `ExpertJobGiveupNotificationProjector` 依次刷新背包、技能、`0x00CD`、进行中与可接任务列表、USERINFO subtype0，再发送成功 ACK。各在线投影独立容错，不改变已提交的放弃结果。

放弃阶段同 opcode 的 `0x00CD` 是名称串，不是登录用的 Mode/Grade 机台快照。当前放弃投影尚未对齐官方顺序，见第十二节。

### 4. 经验和设备变化

副职业经验属于 USERINFO subtype0。经验变化后刷新所有者 subtype0 状态。

设备等级、耐久及金币变化由对应操作 ACK 或所有者 NOTI 投影；如协议结果不包含完整物品变化，再使用 `InventoryRefreshSender` 刷新槽位。

配方型副职业经验增长后，自动学习配方与经验在同一事务中保存；跨越职业等级或设计图学习成功时重新发送 `0x00CD`，同步已学习配方，不依赖重新登录。附魔师投影还会同步卡片资格、等级和设备耐久。附魔商店的卡片、目标装备、双方金币、设备耐久和经验属于同一次业务提交，失败路径必须返回命令错误 ACK，避免客户端停留在职业操作状态。

配方型职业的提取器由客户端副职业主界面从在线背包选择。普通产品制作使用 `0x000E` 批量刷新变化槽位；提取器制作成功后通过 `InventoryRefreshSender` 发送主背包全量 `0x000D`，再发送 `0x00CD` 触发主界面基于完整背包重扫。提取器背包变化与副职业等级变化是两个独立刷新条件。

## 十、分解师适配

分解师是当前公共副职业架构的首个职业适配，实现关系如下：

```text
ExpertJobStoreRuntimeService
  -> DisjointMachineState
  -> DisjointMachineService
  -> InventoryDisjointService（通用装备分解事务）
  -> DisjointMachineResultCalculator（玩家分解机产物）
  -> IDisjointMachineStateRepository
```

### 1. 系统分解和玩家分解

`InventoryDisjointService` 保留系统分解默认入口，同时允许玩家分解机传入独立的产物解析器。两种入口共享目标装备校验、空间规划和背包 mutation。系统分解和玩家分解机的基础、稀有度附加及暴击公式相互独立，仅共同使用 `etc/disjoint.etc` 的 `[additional result expand]` 通用装备灵魂定义。

### 2. 分解结果

玩家分解机按 PVF 的 `(machineGrade, rarity, equipmentState)` 选择职业结果，叠加对应的 additional、big-win 和 self-service 定义，再追加 `[additional result expand]` 的通用装备灵魂。不得复用系统分解的无色晶体、稀有度附加或暴击计算。

装备状态由 `DisjointMachineResultCalculator` 集中解析，Handler 和 PacketBuilder 不重复判断普通、未净化或异界装备。

### 3. 修理和升级

修理与升级是独立领域服务，共享 `DisjointMachineState` 和 ConfigProvider：

- 修理改变金币和耐久。
- 升级校验当前耐久、副职业经验、角色等级和金币，再改变设备等级及耐久。

两者通过同一 operation gate 和持久化入口与分解操作串行执行。

## 十一、扩展新的副职业

### 1. 新增商店型职业

新增商店能力时需要扩展：

1. `ExpertJobStoreKind` 中的能力类型。
2. `ExpertJobStoreSession` 中的类型化职业状态。
3. `ExpertJobStoreRuntimeService.TryValidateKind` 的创建资格。
4. 对应的请求 Parser 和 PacketBuilder。
5. 具体职业 Service、Result 和 ConfigProvider。
6. 对应职业 Repository 或现有状态 Repository。

商店部署、区域查询、visitor 绑定、operation gate 和双背包事务继续复用公共组件。

### 2. 新增配方型职业

配方型职业复用：

- `ExpertJobState.LearnedRecipeIds`。
- `character_expert_job_recipes`。
- `ExpertJobStateCodec` 的配方初始化投影。
- `ExpertJobPersistenceService` 的背包与职业状态事务。

每个职业独立提供配方 Definition、学习服务、制作服务和协议入口。材料扣除和产物插入继续使用新版背包服务。

如果不同职业的 recipe ID 不是全局唯一，需要将职业类型纳入领域身份和数据库主键，不能只在运行时按当前职业区分。

### 3. 新增职业专属状态

按数据基数选择保存方式：

| 状态形态 | 推荐结构 |
| --- | --- |
| 每角色一个稳定标量 | `character_expert_job` 明确列 |
| 每角色一个复杂设备 | 类型化状态和专属列或一对一表 |
| 多条配方、订单或记录 | 独立子表 |
| 仅在线部署期间有效 | `ExpertJobStoreSession` 运行态 |

新增状态后，同时扩展 Repository、初始化逻辑、`ExpertJobState` 和协议快照。正常在线状态不再写入 `character_init_flags` 的 BLOB。

### 4. 非商店型能力

不需要玩家部署和访客进入的能力，直接建立具体职业 Handler 和 Service，不接入 `ExpertJobStoreRuntimeService`。仍可复用副职业状态 Repository、operation coordinator 和持久化服务。

## 十二、当前边界

- `ExpertJobStoreKind` 已注册分解机和附魔商店；商店运行态不承担跨重启恢复。
- `character_expert_job_recipes` 当前按 `(character_id, recipe_id)` 唯一，自动学习和设计图学习共用同一份集合，默认 recipe ID 在职业间不冲突。
- `ExpertJobStateCodec` 已支持分解师设备投影、通用配方列表投影和附魔师卡片资格、等级、耐久投影；新的初始化布局仍必须显式扩展。
- 已接入的附魔师操作是设计图学习、已学习配方生产、装备提取、设备修理、附魔商店部署、`USE_ENCHANT_STORE (0x025A)` 商店附魔和卡片生成宝珠。
- 已接入的炼金师操作是设计图学习、已学习配方生产和炼金提取器装备提取。
- 已接入的控偶师操作是设计图学习、已学习配方生产和灵魂提取器装备提取。
- 旧 `expert_job_blob` 只保留迁移解码能力，不是在线状态入口。
- 放弃路径尚未对齐官方：官方为名称串 `0x00CD` → `SKILLINFO` → `CLEAR_QUEST_LIST (0x0164)` → USERINFO0（尾 type=0）→ 成功 ACK；当前仍发空模式 2 字节 `0x00CD`，以及进行中/可接任务列表。
