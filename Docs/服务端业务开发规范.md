## 1. 目的和优先级

本规范用于多人开发、代码审查和 AI 协作，目标是保持业务真源唯一、协议行为稳定、数据库可恢复、修改可追溯，避免未经验证的重写、重复实现和跨层乱改。

规则优先级如下：

1. 客户端实际协议、已验证的 SelfTest 和当前生产代码行为。
2. 目标业务域的专项规范：副本、背包/GM、副职业和 ClockService 规范优先解释该领域的具体所有权与 wire/恢复边界。
3. `Docs/` 下的本总规范和专项规范，用于跨领域规则、变更流程和版本登记。
4. PVF 中已经确认的业务数据和字段语义。

出现冲突时，必须停止扩大修改范围，记录冲突、证据和待确认项，由维护者决定后再继续。

## 2. 不可改变的基线

### 2.1 数据库

- 发布包不携带 SQLite 种子库。
- 数据库不存在时，由 `SqliteDatabaseBootstrap` 根据 `Server/DfoServer/Sqlite/item_schema.sql` 创建完整新库。
- 基线身份固定为 `86jp-database-v1`、baseline schema v1；`PRAGMA user_version` 与 `schema_metadata.schema_version` 表示连续增量版本，当前为 schema v14。
- 新功能只有在确实需要结构变化时，才能从新体系 schema v2 开始增加连续、短小、纯数据库依赖的增量迁移；新库由完整 `item_schema.sql` 创建后直接标记为当前版本，既有 v1-v10 库逐级升级到 v11。v11 是数据迁移：v11 以下旧库一次性把旧 UTF-8 线上名字节改成 GBK，不改表结构；新库无旧字节，不跑转换。
- 既有数据库缺失或不匹配 `schema_metadata.baseline_id` 时，默认拒绝启动；不得在普通业务路径中偷偷建表、改表、补列或搬运旧数据。
- 新库不预置玩家账号、角色或测试账号。SelfTest 必须显式创建所需前置数据。

### 2.2 运行时约束

- 单进程、单 SQLite 数据库和当前会话/角色 generation 是本项目的运行边界。
- 在线 Inventory 的唯一运行时真源是当前会话持有的 `InventoryLease` 和 `InventoryService`。
- Dungeon、PvP、Party、Session 等有生命周期的状态必须绑定当前 session、character、run、room 或 generation，旧 generation 不得修改新状态。
- `ClockService` 是进程内到期提醒和短时控制，不是持久化系统；回调不得凭空创建奖励、货币、次数或进度。需要跨重启正确的状态必须保存绝对截止时间或 durable effect，并在启动、登录、使用或恢复时重算。
- 参与者 timer 使用 `RunTimerRegistry`；Instance/Room 共享世界 timer 必须由共享 owner 持有，不能复制到每个玩家 run。所有回调必须复验 identity、phase、version/ticket 和当前 attachment。
- SelfTest 必须串行执行，共用日志文件：`Server/DfoServer/bin/Debug/server.log`。

## 3. 业务所有权和目录边界

| 层/目录 | 唯一职责 | 不得承担 |
| --- | --- | --- |
| `Network/Parsers` | 校验 body 长度、字段宽度、枚举和值域，生成命令对象 | 写数据库、修改在线状态、发送业务奖励 |
| `Network/Handlers` | 协议顺序、权限前置检查、调用用例、发送 ACK/通知 | 另建持久化真源、绕过 Service 直接改表 |
| `Game/*`、`GameWorld/*` | 业务规则、领域状态、PVF 解析和投影 | 依赖具体 socket 或自行拼协议 |
| `Infrastructure/*` | 数据库、时钟、随机数、路径、运行时组合根 | 持有某个玩法的业务状态 |
| `Sqlite/*`、`*Repository.cs` | schema、迁移、查询、事务内持久化 | 解析客户端请求或发送封包 |
| `SelfTests/*` | 可重复验证协议、业务、失败恢复和组合关系 | 依赖旧种子库、修改生产数据或并行抢日志 |
| `Docs/*` | 方案、规范、版本、纠错和证据 | 记录未经验证的结论为事实 |

同一业务数据只能有一个权威所有者。可以有缓存、投影和通知，但必须明确它们的失效、重放和恢复方式，不能把缓存当成新的业务真源。

## 4. 变更分类和必备产物

任何修改开始前，先选择一种主分类，并建立修改批次编号（例如 `R-INV-001`、`R-DOM-071`、`R-GOV-001`）：

### 4.1 Bug 修复

- 记录复现条件、原行为、期望行为、影响范围和证据。
- 在提交或 MR 描述中记录问题、修正和验证结果。
- 增加或修正一个能稳定复现问题的 SelfTest。
- 说明失败后的内存状态、数据库状态、客户端响应和重试行为。

### 4.2 新业务功能

- 先写业务入口、数据所有者、事务边界、失败语义和协议影响。
- 复用现有 Repository、Service、Coordinator、Parser 和发送器，禁止先复制一套近似实现。
- 若需要新表或新字段，先完成数据库设计和迁移说明，再写业务代码。
- 必须同时覆盖成功、重复请求、并发/旧 generation、持久化失败和重连/离线恢复（如适用）。

### 4.3 数据库变更

- 仅从新体系 schema v2 开始追加迁移；迁移版本只能递增，已经发布的迁移不得改写。
- 同时修改 `item_schema.sql`、迁移注册、数据库自测和本规范涉及的表所有权说明。
- 迁移必须只依赖数据库连接和事务，不调用业务 Service、在线 Manager、Handler 或 PVF。
- 不得为了让旧库通过而恢复历史兼容表、旧 DTO、种子账号或运行时 EnsureTable。
- 必须验证新库创建、重复初始化、版本拒绝、失败回滚和升级后重启。

### 4.4 协议变更

- 先提供证据：抓包、客户端逆向、已有 parser、PVF 字段或已验证参考实现。
- 明确 command ID、body 精确长度/可选字段、字段端序、错误码、ACK/NOTI 顺序和重复请求行为。
- 新增 parser 自测和真实 Handler/组合根注册断言。
- 不得因“字段看起来应该如此”而收紧或放宽长度；历史扩展体必须有明确 wire 依据。

### 4.5 结构重构

- 先写行为不变清单和受影响调用链。
- 重构期间不得混入无关格式化、批量改名、协议改动或业务规则调整。
- 大文件只有在职责边界、状态所有权或测试隔离真正改善时才拆分；不为减少行数机械搬文件。
- 重构完成必须跑原路径回归，不得只验证新入口。

## 5. 强制实现规则

### 5.1 Inventory 和持久化

- 在线变化必须在当前 `InventoryLease.SyncRoot` 内读取、校验和修改。
- 不得拿不到 owned lease 后直接写数据库，也不得先写数据库再伪造在线 Inventory 状态。
- 需要成功回包前落库时，使用统一提交协调器或对应业务 CommitService。
- 多张表、账号状态、Inventory dirty、邮件溢出或 durable effect 属于同一个业务结果时，必须使用同一个 SQLite 事务。
- 只有事务提交成功后才能发送成功 ACK、奖励通知、物品刷新或清除可重试 reservation。
- 提交失败必须恢复在线投影、保留可重试状态或执行持久化恢复；不能吞异常后继续发奖励。

### 5.2 Session、Party、PvP、Dungeon

- 任何异步等待后都要重新确认当前 session/character/run/room generation。
- 旧连接、旧 room、旧 match 或旧 run 的延迟任务不得消费、结束或覆盖新 generation。
- 断线、换角色、返回选角、重连和被顶号必须复用已有生命周期协调器，不得在 Handler 内另写一套释放顺序。
- 返城、结算、重连和奖励恢复必须使用入场时捕获的 run anchor 或 durable identity。
- 有状态计时器注册到 `RunTimerRegistry` 或 `ClockService`；不得自行开线程和无限 `while` 循环。
- `Task.Run` 只能用于不持有 session/run 的只读 PVF 预热或明确的后台工作，并必须捕获异常、可观察、可停止。

### 5.3 Dungeon 领域接入

- `DungeonInstance` 拥有共享物理世界、共享选择快照、房间、唯一 clear fact 和实例机制；`DungeonInstanceRoom` 拥有房间 identity、actor/Encounter 和清房事实；`DungeonRun` 只拥有单个参与者的 Selection、Combat、Settlement、QuestBridge、个人 effect 和 participant timer。
- `Definition` 是从 PVF/ETC 解析并冻结的只读规则，`Runtime` 是单局可变状态，`Projection` 只是协议/UI/日志投影；三者不得合并成一个可变大类。
- 事件至少携带 `PartyDungeonInstanceId`、`RunId`、`RunGeneration`、`RoomInstanceId`、`SourceEventId` 和 affected scope。Party relay 与本地事件必须复用同一 `SourceEventId`，不能为不同玩家重新制造业务事件。
- 新增或修改副本命令必须经过 typed parser/dispatcher；业务服务只返回 typed result/reject，不直接拼 ACK、选择错误码或把 dungeon/MAP/item/quest ID 作为通用分类器。
- 共享副本只冻结一份 SelectionSnapshot、maze、MAP、起点和 Boss 结果；队员不得独立随机共享物理地图。清理旧 run 必须使用 expected identity，不能无条件写 `CurrentRun = null`。
- 副本、任务、结算或共享 Inventory 路径变更，必须运行聚焦自测和 `--selftest-all`；自测必须显式设置 `PVF_ARCHIVE_PATH`。自动回归通过但未完成真机协议/UI/断线时序验证时，只能写“自动测试通过”。

### 5.4 Quest-Dungeon 交界

- 任务进本事实必须携带冻结的 `QuestRunSnapshot` 和 `QuestActivationId`；旧 activation、旧副本事件和旧任务掉落不得推进重新接取的新任务。
- 任务前置/冲突只能由 immutable definition 和统一 evaluator 决定；列表展示或缓存不能替代接取事务中的重新加载与重验。
- Quest application service、Repository/CAS 和 Inventory lease 共同拥有任务事务；Dungeon Handler 不得直接写任务 SQL、按 slot 盲写 trigger 或复制第二份 FINISH parser。

### 5.5 Inventory、GM 和 ItemCore

- 在线模型只认 `InventoryService`、`InventoryContext` 和 `InventoryLease`；`InventoryItem` 仅存在于 Repository/Codec、自测和诊断边界。
- `ItemCore` 是固定 99 字节的小端序核心；时装/宠物 detail 由对应 detail model/repository 管理，`ItemCore.Value` 必须分别与 `AvatarUid`/`CreatureUid` 对齐，`JewelSocket` 固定 30 字节。
- GM 直接写 SQLite 只适用于离线角色；在线角色必须下线重进，或通过服务端 GM 入口同步在线模型。不得重新引入 `SqliteAssetService`、`IInventoryStore`、旧 DTO、`extra_json` 或旧背包表作为新写入目标。
- 金币、复活币、胜点、晶体的虚拟槽和账号字段必须按背包专项规范处理；晶体不得伪造为普通物品写入角色物品表。

### 5.6 ExpertJob 副职业

- `ExpertJobState` 是副职业领域状态入口；副职业类型和经验继续由角色 subtype0 所有，不得把两者混成一份状态。
- 商店部署、访客和职业操作按所有者通过 `ExpertJobOperationCoordinator` 串行化；职业服务必须先取得相关在线 Inventory lease。
- 背包与副职业状态通过 `ExpertJobPersistenceService` 在同一事务内提交；失败通过 `InventoryRollbackRecoveryService` 恢复在线模型，不得在活动事务持锁时打开第二连接。
- 职业公式、等级、配方、设备耐久和费用来自当前 PVF ConfigProvider；Handler 只负责协议分发、调用和投影。

### 5.7 Mailbox A21 协议

- Owner 仍是 `MailboxHandler` + `MailboxService`。`0x0061` / `0x0060` / `0x005F` 只从 `PacketTypesA21.cs` 取值。
- 空收件箱发 6B 全 0；有邮件时进城 init 发完整 `MAILBOX_MAIL_LIST`，打开邮箱再发同一份。
- A21 summary 尾部固定写两个长度前缀 blob + extra1。非时装 blob 为 `0/0`；时装 jewel/color 为 `A21AvatarJewelBytes=18` + 4B。时装 type 0-11 在 extra1 之后、remain 之前再写两段空长度前缀，然后 remainSeconds / summaryKey + extra2。
- A21 detail 在 `letterStat` 后多 1 字节。邮件 dstr 为 GBK(936)。
- 与客户端互发的协议字符串默认走 `ClientTextEncoding`（GBK 936）。聊天/组队等已按原始字节透传的路径保持透传；`EVENT_INFO` 也按 GBK 写入，数据库保存中文 TEXT，组包时在 wire 边界统一编码。库内线上名字节只认 GBK。邮件正文和好友键是 Unicode TEXT。日志、配置、哈希仍用 UTF-8。
- 宠物 type=25：expire 前写 `i32 + u8`，flag 固定 0。`Marker16=-1` 不得原样下发。
- 宠物装备 type=26-28：耐久位写剩余秒数，0 表示永久。
- 领取时装/宠物附件时在同一 IMMEDIATE 事务里分配 UID，并进入 `InventoryUidAllocationContext`。禁止在该事务持锁时再 `OpenConnection` 写序列表。

### 5.8 随机、时间和 PVF

- 客户端可复算的掉落使用房间 `DnfLcg`。
- 其他服务端随机使用 `Infrastructure.ServerRandom`，不得自行 `new Random()`。
- 周期任务使用 `Infrastructure.ClockService`；停机期间可能错过的结算必须能在下次加载或写入时补算。
- `ClockService` 回调不得作为奖励、次数、货币或进度的唯一提交点；timer 到期只是提醒或推进已有状态，最终业务必须通过持久化状态、领取校验或当前 session 重算确认。
- 需要跨重启存活的阶段保存绝对 UTC deadline；启动、登录或查看时先读库判断是否过期，再按规则结算或重新注册剩余 timer。
- PVF 只读缓存必须使用 `Lazy`、锁或并发集合安全发布；缓存是派生数据，不是在线业务真源。

## 6. AI 和多人协作专用规则

### 6.1 开始修改前

1. 先读取根目录 `AGENTS.md`、本规范、贡献指南和目标业务域专项文档；副本、背包、GM、副职业和 ClockService 的专项文档必须按目标范围联查。
2. 使用文件清单和符号搜索确认真实路径、命名空间、调用者和现有测试。
3. 检查工作区是否已有他人修改；不回滚、不覆盖、不重置无关改动。
4. 先写简短变更说明：目标、非目标、受影响文件、验证命令和预期退出条件。

### 6.2 修改过程中

- 手工代码和文档编辑使用 `apply_patch` 或等价的可审阅小补丁；禁止未经审阅的全局替换、正则批量重写和整目录格式化。
- 禁止使用 `git reset --hard`、强制 checkout 或递归删除等破坏性操作处理不明来源的工作区变化。
- 不确定的协议、数据库字段、PVF 语义或旧代码行为必须标记为“待确认”，不能凭名称推断。
- 不得为了通过编译删除校验、吞异常、放宽长度检查、添加默认账号或绕过事务。
- 不得新增第二个类似的 Service、Repository、缓存、随机源或生命周期管理器，除非文档说明现有所有者无法复用。
- 每次出现编译错误、测试失败、命令路径错误或文档与实现不一致，都要在同一批次的提交或 MR 描述中登记。

### 6.3 提交前

- 代码、SelfTest、规范和提交说明必须彼此一致。
- 所有相关 SelfTest 串行执行；共享日志冲突时停止并改为串行，不得用并行结果冒充验收。
- 检查数据库、PVF、协议 ID、迁移版本和生成文件是否发生非预期变化。
- 提交说明必须列出：修改批次、变更文件、行为变化、数据库影响、PVF 影响、测试结果和未完成项。

## 7. 标准工作流

```text
读取规范和现状
  -> 建立修改批次与变更说明
  -> 定位唯一业务所有者
  -> 小范围实现
  -> 编译
   -> 相关专项 SelfTest（串行）
   -> 共享 Dungeon/Quest/Settlement/Inventory 路径时运行 --selftest-all
  -> 核心数据库/组合根 SelfTest
  -> PVF/数据库/协议完整性检查
  -> 更新规范版本和修改说明
  -> 代码审查
  -> 合并
```

不允许跳过“定位所有者”“失败路径验证”“文档登记”三步。只改代码不改记录，视为未完成。

## 8. 最低验收清单

### 代码

- [ ] 修改没有跨越未声明的业务边界。
- [ ] 没有新增重复真源、重复缓存、重复事务或重复生命周期。
- [ ] 异步路径检查了当前 generation，异常可观察且有明确恢复语义。
- [ ] 没有直接绕过现有 Repository、CommitService、Coordinator 或发送器。

### 数据库

- [ ] schema/迁移版本连续且未修改已发布迁移。
- [ ] 数据库新建、重复初始化、拒绝和回滚测试通过。

### 协议和测试

- [ ] command 注册唯一，parser 长度和字段语义有证据。
- [ ] 成功、失败、重复、旧 generation、断线/重连场景已覆盖（适用时）。
- [ ] 相关 SelfTest 已串行执行，结果已记录。
- [ ] 共享 Dungeon/Quest/Settlement/Inventory 路径已显式设置 `PVF_ARCHIVE_PATH` 并运行 `--selftest-all`。
- [ ] Timer 已明确属于 Participant、Instance 或 Room，且不是跨重启业务真源。
- [ ] 领域专项规范中的当前限制没有被扩大解释为跨重启恢复或 exactly-once。
- [ ] Rebuild 为 0 warning / 0 error。

### 文档和审查

- [ ] 规范版本、修改批次、剩余工作量已更新。
- [ ] 新问题已登记 `C-序号`，纠正结果和影响文件完整。
- [ ] 提交说明没有混入无关重构、格式化或生成文件。
- [ ] 至少一名熟悉该业务域的维护者复核了所有权和失败语义。

## 10. 违反规范时的处理

发现直接写表、绕过 owned lease、恢复旧迁移、吞异常、并行抢日志、覆盖他人改动或无证据变更协议时，应立即停止合并，保留现场，建立纠错记录并退回到最近一个可验证状态。

本规范不是为了禁止合理演进，而是要求每次演进都能说明“谁拥有数据、何时提交、失败如何恢复、如何证明没有破坏旧业务”。
