# 服务端业务开发规范

> 规范版本：1.1.27
> 生效日期：2026-09-08
> 适用范围：`ServerS4A21` 内全部服务端、工具、SelfTest、数据库、PVF 相关修改
> 配套基线：`86jp-database-v1` / baseline schema v1；当前连续迁移版本 schema v43
> 关联文档：`副本架构业务接入规范.md`、`新版背包架构业务接入规范.md`、`GM工具_新背包表结构与ItemCore语义.md`、`副职业架构业务接入规范.md`、`ClockService.md`

## 1. 目的和优先级

本规范用于多人开发、代码审查和 AI 协作，目标是保持业务真源唯一、协议行为稳定、数据库可恢复、修改可追溯，避免未经验证的重写、重复实现和跨层乱改。

普通金币拍卖由单一 `AuctionRuntime` 跨频道持有订单、资产提交和恢复流程。拍卖业务库与成交历史投影均为显式初始化的独立数据库，不占用公用迁移编号；跨库操作通过不可变意图和永久 receipt 恢复，不能视为原子事务。在线资产复用现有 owned lease 和提交协调器。配置、协议证据与恢复边界统一见[拍卖行业务与持久化](拍卖行业务与持久化.md)。

金币寄售是**独立功能**，不是拍卖行的子功能：它复用 `0x00B6`/`0x00B7` 但使用更短包体，靠 body 长度分流；拥有独立开关 `GOLD_CONSIGN_ENABLED`、独立数据表（schema v42）与独立费率期限；售出后按 `accounts.token_cera` 记入卖家账号。协议证据、字段布局、事务边界与已知未闭环项见[金币寄售业务接入规范](金币寄售业务接入规范.md)。

规则优先级如下：

1. 客户端实际协议、已验证的 SelfTest 和当前生产代码行为。
2. 目标业务域的专项规范：副本、背包/GM、副职业和 ClockService 规范优先解释该领域的具体所有权与 wire/恢复边界。
3. `Docs/` 下的本总规范和专项规范，用于跨领域规则和变更流程。开发规范只记录规范，不得写入更新记录。
4. PVF 中已经确认的业务数据和字段语义。

出现冲突时，必须停止扩大修改范围，记录冲突、证据和待确认项，由维护者决定后再继续。

## 2. 不可改变的基线

### 2.1 数据库

- 发布包不携带 SQLite 种子库。
- 数据库不存在时，由 `SqliteDatabaseBootstrap` 根据 `Server/DfoServer/Sqlite/item_schema.sql` 创建完整新库。
- 基线身份固定为 `86jp-database-v1`、baseline schema v1；`PRAGMA user_version` 与 `schema_metadata.schema_version` 表示连续增量版本，当前为 schema v43。
- 新功能只有在确实需要结构变化时，才能从新体系 schema v2 开始增加连续、短小、纯数据库依赖的增量迁移；新库由完整 `item_schema.sql` 创建后直接标记为当前版本，既有数据库按注册步骤逐级升级到当前版本。建表与版本推进必须在同一迁移事务内完成。
- 既有数据库缺失或不匹配 `schema_metadata.baseline_id` 时，默认拒绝启动；不得在普通业务路径中偷偷建表、改表、补列或搬运旧数据。
- 新库不预置玩家账号、角色或测试账号。SelfTest 必须显式创建所需前置数据。

### 2.2 运行时约束

- 单进程、单 SQLite 数据库和当前会话/角色 generation 是本项目的运行边界。
- 在线 Inventory 的唯一运行时真源是当前会话持有的 `InventoryLease` 和 `InventoryService`。
- Dungeon、PvP、Party、Session 等有生命周期的状态必须绑定当前 session、character、run、room 或 generation，旧 generation 不得修改新状态。
- `ClockService` 是进程内到期提醒和短时控制，不是持久化系统；回调不得凭空创建奖励、货币、次数或进度。需要跨重启正确的状态必须保存绝对截止时间或 durable effect，并在启动、登录、使用或恢复时重算。
- 参与者 timer 使用 `RunTimerRegistry`；Instance/Room 共享世界 timer 必须由共享 owner 持有，不能复制到每个玩家 run。所有回调必须复验 identity、phase、version/ticket 和当前 attachment。
- SelfTest 必须串行执行，共用日志文件：`Server/DfoServer/bin/Debug/server.log`。

## 3. 业务所有权和目录边界

| 层/目录 | 唯一职责 | 不得承担 |
| --- | --- | --- |
| `Network/Parsers` | 校验 body 长度、字段宽度、枚举和值域，生成命令对象 | 写数据库、修改在线状态、发送业务奖励 |
| `Network/Handlers` | 协议顺序、权限前置检查、调用用例、发送 ACK/通知 | 另建持久化真源、绕过 Service 直接改表 |
| `Game/*`、`GameWorld/*` | 业务规则、领域状态、PVF 解析和投影 | 依赖具体 socket 或自行拼协议 |
| `Infrastructure/*` | 数据库、时钟、随机数、路径、运行时组合根 | 持有某个玩法的业务状态 |
| `Sqlite/*`、`*Repository.cs` | schema、迁移、查询、事务内持久化 | 解析客户端请求或发送封包 |
| `SelfTests/*` | 可重复验证协议、业务、失败恢复和组合关系 | 依赖旧种子库、修改生产数据或并行抢日志 |
| `Docs/*` | 当前生效的方案与规范 | 记录未经验证的结论为事实；写入更新记录 |

同一业务数据只能有一个权威所有者。可以有缓存、投影和通知，但必须明确它们的失效、重放和恢复方式，不能把缓存当成新的业务真源。

直播强化时序由原生动画计时推进：START通知后，客户端动画计时结束才发送普通强化完成请求。服务端不另设猜测秒数的延时；只允许待完成动画匹配的请求进入强化事务，其他直播期间的普通强化请求不能旁路结算。开始与完成分别记忆近期请求身份，取消或失败后恢复可操作状态。

## 4. 变更分类和必备产物

任何修改开始前，先选择一种主分类，并建立修改批次编号（例如 `R-INV-001`、`R-DOM-071`、`R-GOV-001`）：

### 4.1 Bug 修复

- 记录复现条件、原行为、期望行为、影响范围和证据。
- 在提交或 MR 描述中记录问题、修正和验证结果。
- 增加或修正一个能稳定复现问题的 SelfTest。
- 说明失败后的内存状态、数据库状态、客户端响应和重试行为。

### 4.2 新业务功能

- 先写业务入口、数据所有者、事务边界、失败语义和协议影响。
- 复用现有 Repository、Service、Coordinator、Parser 和发送器，禁止先复制一套近似实现。
- 若需要新表或新字段，先完成数据库设计和迁移说明，再写业务代码。
- 必须同时覆盖成功、重复请求、并发/旧 generation、持久化失败和重连/离线恢复（如适用）。

### 4.3 数据库变更

- 仅从新体系 schema v2 开始追加迁移；迁移版本只能递增，已经发布的迁移不得改写。
- 同时修改 `item_schema.sql`、迁移注册、数据库自测和本规范涉及的表所有权说明。
- 迁移必须只依赖数据库连接和事务，不调用业务 Service、在线 Manager、Handler 或 PVF。
- 不得为了让旧库通过而恢复历史兼容表、旧 DTO、种子账号或运行时 EnsureTable。
- 必须验证新库创建、重复初始化、版本拒绝、失败回滚和升级后重启。

### 4.4 协议变更

- 先提供证据：抓包、客户端逆向、已有 parser、PVF 字段或已验证参考实现。
- 明确 command ID、body 精确长度/可选字段、字段端序、错误码、ACK/NOTI 顺序和重复请求行为。
- 新增 parser 自测和真实 Handler/组合根注册断言。
- 不得因“字段看起来应该如此”而收紧或放宽长度；历史扩展体必须有明确 wire 依据。
- TCP framing 必须先验证声明长度不小于当前 header、且不大于 `1 MiB`；单会话未解析缓存不得超过 `2 MiB`。非法帧必须终止当前连接，禁止以零长度继续循环或无限等待超大帧。

角色信息字段、所有权和消费条件见[USERINFO1 客户端消费结构](USERINFO1客户端消费结构.md)；决斗初始化、房间包序、结算和战绩见[决斗场业务实现](决斗场业务实现.md)。协议投影必须使用对应业务快照，未确认字段保持已验证的占位值。

### 4.5 结构重构

- 先写行为不变清单和受影响调用链。
- 重构期间不得混入无关格式化、批量改名、协议改动或业务规则调整。
- 大文件只有在职责边界、状态所有权或测试隔离真正改善时才拆分；不为减少行数机械搬文件。
- 重构完成必须跑原路径回归，不得只验证新入口。

## 5. 强制实现规则

### 5.1 Inventory 和持久化

- 在线变化必须在当前 `InventoryLease.SyncRoot` 内读取、校验和修改。
- 不得拿不到 owned lease 后直接写数据库，也不得先写数据库再伪造在线 Inventory 状态。
- 需要成功回包前落库时，使用统一提交协调器或对应业务 CommitService。
- 多张表、账号状态、Inventory dirty、邮件溢出或 durable effect 属于同一个业务结果时，必须使用同一个 SQLite 事务。
- 只有事务提交成功后才能发送成功 ACK、奖励通知、物品刷新或清除可重试 reservation。
- 提交失败必须恢复在线投影、保留可重试状态或执行持久化恢复；不能吞异常后继续发奖励。

### 5.2 Session、Party、PvP、Dungeon

- 任何异步等待后都要重新确认当前 session/character/run/room generation。
- 旧连接、旧 room、旧 match 或旧 run 的延迟任务不得消费、结束或覆盖新 generation。
- 断线、换角色、返回选角、重连和被顶号必须复用已有生命周期协调器，不得在 Handler 内另写一套释放顺序。
- PvP 复用角色生命周期和房间发布队列；整局结算必须原子提交并按 room/match generation 防重。频道、协议、经验、队伍和技能细则统一见[决斗场业务实现](决斗场业务实现.md)。
- 同 listener 的好友跨 town/area 发起组队邀请时，只能在双方均为 town-ready、无 dungeon run 且 UID 有效的情况下，先向被邀请者投影邀请者的 `USERINFO subtype0`，再发送原有 `REQUEST_PEER`。不得发送 `USER_AREA`、`AREA_USERS` 或 `USER_LEAVE`，不得改写好友关系或放宽跨频道门禁。
- Party 邀请/申请的 pending 必须绑定双方 UID、SessionId 和登记时 PartyId；接受、取消和 mutation 必须在 `PartyManager` 同一锁内 exact consume 并复验 generation。双方无队、inviter 已有队、requester 申请加入 target 原队三种状态不得靠翻转 requester/target 或猜 requestType 合并。
- `RESPONSE_PEER type0` 只有当前精确客户端已证实的 exact accept body 才能进入 Party mutation；拒绝或非规范 body 必须 fail closed，并在同一锁内 exact consume 对应 pending。不得因拒绝发送 formation、迁移成员或清除无变化的队伍列表投影，也不得把某个拒绝尾值泛化到其他 requestType。
- 当前地图队伍列表只是 PartyManager/SessionDirectory 的可丢弃投影，不是业务真源。只向当前 town-ready、无队、无 run 的同 listener/town/area 会话发送；旧行用客户端已证 type3 显式移除，发送成功后才更新 per-session 缓存，send lock 内必须重验目录 generation 和区域/队伍状态。
- 返城、结算、重连和奖励恢复必须使用入场时捕获的 run anchor 或 durable identity。
- 有状态计时器注册到 `RunTimerRegistry` 或 `ClockService`；不得自行开线程和无限 `while` 循环。
- `Task.Run` 只能用于不持有 session/run 的只读 PVF 预热或明确的后台工作，并必须捕获异常、可观察、可停止。

### 5.3 Dungeon 领域接入

- `DungeonInstance` 拥有共享物理世界、共享选择快照、房间、唯一 clear fact 和实例机制；`DungeonInstanceRoom` 拥有房间 identity、actor/Encounter 和清房事实；`DungeonRun` 只拥有单个参与者的 Selection、Combat、Settlement、QuestBridge、个人 effect 和 participant timer。
- `Definition` 是从 PVF/ETC 解析并冻结的只读规则，`Runtime` 是单局可变状态，`Projection` 只是协议/UI/日志投影；三者不得合并成一个可变大类。
- 事件至少携带 `PartyDungeonInstanceId`、`RunId`、`RunGeneration`、`RoomInstanceId`、`SourceEventId` 和 affected scope。Party relay 与本地事件必须复用同一 `SourceEventId`，不能为不同玩家重新制造业务事件。
- 新增或修改副本命令必须经过 typed parser/dispatcher；业务服务只返回 typed result/reject，不直接拼 ACK、选择错误码或把 dungeon/MAP/item/quest ID 作为通用分类器。
- 共享副本只冻结一份 SelectionSnapshot、maze、MAP、起点和 Boss 结果；队员不得独立随机共享物理地图。清理旧 run 必须使用 expected identity，不能无条件写 `CurrentRun = null`。
- 副本、任务、结算或共享 Inventory 路径变更，必须运行聚焦自测和 `--selftest-all`；自测必须显式设置 `PVF_ARCHIVE_PATH`。自动回归通过但未完成真机协议/UI/断线时序验证时，只能写“自动测试通过”。

### 5.4 Quest-Dungeon 交界

- 任务进本事实必须携带冻结的 `QuestRunSnapshot` 和 `QuestActivationId`；旧 activation、旧副本事件和旧任务掉落不得推进重新接取的新任务。
- 进本后接取的任务必须并入当前 run 的快照（只补这一条，不重建白名单），否则掉落、击杀和清图都会在整局内被白名单过滤。合并使用接取事务写库后重新读出的 `ActiveQuest`，与进本赋值共用 `run.SyncRoot`。
- 任务前置/冲突只能由 immutable definition 和统一 evaluator 决定；列表展示或缓存不能替代接取事务中的重新加载与重验。
- 问答前置的答案下标从 0 开始，活动 trigger 保存完整答案下标，完成 flag 持久化为 `answerIndex + 1`。当前 A21 的 `CmdPacketTypeA21.SET_QUEST_TRIGGER` 问答请求在任务 ID 和 type 0 后发送一个答案下标字节，不得转换为普通任务的增减布尔值；统一进度入口校验答案范围并按绝对值保存，重复选择不得累加。客户端编码和发送顺序证据见《副本架构业务接入规范》的问答完成规则；完成事务内复验必须与事务前校验使用同一规则。
- Quest application service、Repository/CAS 和 Inventory lease 共同拥有任务事务；Dungeon Handler 不得直接写任务 SQL、按 slot 盲写 trigger 或复制第二份 FINISH parser。
- PVF `[daily]`、`[daily random]`、`[special daily]` 是按角色、北京时间 06:00 切日的每日任务；`[normaly repeat]` 才能立即重复和批量完成。每日 FINISH 只接受一次完成，在现有 Inventory/Quest immediate 事务内领取 `quest_daily_completed_<questId>` 日计数，并写入客户端完成投影；同日重复接取或领奖必须失败且不得再次发奖。
- `character_daily_counters` 的当前日记录是每日领奖权威，`character_quest_completions` 仅为客户端与前置任务的当日投影。读取可接、已完成和选角 init 状态时，只有当前 `day_id` 与每日计数都有效才展示该每日完成标记；次日 06:00 后首次接取通过 `DailyResetService` 日切，并在同一事务移除过期投影。进程内 timer 不能代替请求期日界校验。

### 5.5 Inventory、GM 和 ItemCore

- 在线模型只认 `InventoryService`、`InventoryContext` 和 `InventoryLease`；`InventoryItem` 仅存在于 Repository/Codec、自测和诊断边界。
- `ItemCore` 是固定 99 字节的小端序核心；时装/宠物 detail 由对应 detail model/repository 管理，`ItemCore.Value` 必须分别与 `AvatarUid`/`CreatureUid` 对齐，`JewelSocket` 固定 30 字节。
- GM 直接写 SQLite 只适用于离线角色；在线角色必须下线重进，或通过服务端 GM 入口同步在线模型。不得重新引入 `SqliteAssetService`、`IInventoryStore`、旧 DTO、`extra_json` 或旧背包表作为新写入目标。
- 金币、复活币、胜点、晶体的虚拟槽和账号字段必须按背包专项规范处理；晶体不得伪造为普通物品写入角色物品表。
- 龙跃武器（PVF `[equipment grow]`）的成长值由 `EquipmentGrowthService` 拥有：击杀普通/稀有/精英/领主怪时按怪物等级与副本难度加权累积，成长值是装备实例状态，持久化在 `character_equipment_growth`。跨列表移动（背包↔穿戴）会改变 `item_uid`，成长值必须随实例迁移，迁移与物品落库同属一个事务。协议投影与解放升星尚未闭环，见背包专项规范。

### 5.6 ExpertJob 副职业

- `ExpertJobState` 是副职业领域状态入口；副职业类型和经验继续由角色 subtype0 所有，不得把两者混成一份状态。
- 商店部署、访客和职业操作按所有者通过 `ExpertJobOperationCoordinator` 串行化；职业服务必须先取得相关在线 Inventory lease。
- 背包与副职业状态通过 `ExpertJobPersistenceService` 在同一事务内提交；失败通过 `InventoryRollbackRecoveryService` 恢复在线模型，不得在活动事务持锁时打开第二连接。
- 职业公式、等级、配方、设备耐久和费用来自当前 PVF ConfigProvider；Handler 只负责协议分发、调用和投影。

### 5.7 Mailbox A21 协议

- Owner 仍是 `MailboxHandler` + `MailboxService`。`0x0061` / `0x0060` / `0x005F` 只从 `PacketTypesA21.cs` 取值。
- 空收件箱发 6B 全 0；有邮件时进城 init 发完整 `MAILBOX_MAIL_LIST`，打开邮箱再发同一份。
- A21 summary 尾部固定写两个长度前缀 blob + extra1。非时装 blob 为 `0/0`；时装 jewel/color 为 `A21AvatarJewelBytes=18` + 4B。时装 type 0-11 在 extra1 之后、remain 之前再写两段空长度前缀，然后 remainSeconds / summaryKey + extra2。
- A21 detail 在 `letterStat` 后多 1 字节。邮件 dstr 为 GBK(936)。
- `0x0144` 收件人查询成功回包固定为 `result(1) + DSTR name + 保留字节 0 + level UInt16LE + job UInt8 + growType UInt8 + 两个尾零`。名字后的保留字节不可省略；缺少时客户端会把 level 读成 `job << 8`，并把 growType 当作职业索引。
- 与客户端互发的协议字符串默认走 `ClientTextEncoding`（GBK 936）。聊天/组队等已按原始字节透传的路径保持透传；`EVENT_INFO` 也按 GBK 写入，数据库保存中文 TEXT，组包时在 wire 边界统一编码。库内线上名字节只认 GBK。邮件正文和好友键是 Unicode TEXT。日志、配置、哈希仍用 UTF-8。
- 宠物 type=25：expire 前写 `i32 + u8`，flag 固定 0。`Marker16=-1` 不得原样下发。
- 宠物装备 type=26-28：耐久位写剩余秒数，0 表示永久。
- 领取时装/宠物附件时在同一 IMMEDIATE 事务里分配 UID，并进入 `InventoryUidAllocationContext`。禁止在该事务持锁时再 `OpenConnection` 写序列表。
- 邮件领取的携带量和主背包重量校验使用 `ItemSlotBoundService` 的目标空间规则；公会勋章和守护珠属于 `InventoryListType.GuildMedal`。领取结果必须保留实际变更的 list/slot，并经 `InventoryRefreshSender` 刷新对应空间，不能将勋章栏槽位归入 Main。附件领取标记和物品保存仍在同一事务提交，失败时回滚并保留可重试附件。

### 5.8 随机、时间和 PVF

- 客户端可复算的掉落使用房间 `DnfLcg`。
- 其他服务端随机使用 `Infrastructure.ServerRandom`，不得自行 `new Random()`。
- 周期任务使用 `Infrastructure.ClockService`；停机期间可能错过的结算必须能在下次加载或写入时补算。
- `character_daily_reset.day_id/week_id` 只允许单调前进。显式传入旧 UTC 时间锚的读取或写入必须 fail closed，不得把 stale 当作零值、回拨门控或清空较新周期账本。
- `ClockService` 回调不得作为奖励、次数、货币或进度的唯一提交点；timer 到期只是提醒或推进已有状态，最终业务必须通过持久化状态、领取校验或当前 session 重算确认。
- 需要跨重启存活的阶段保存绝对 UTC deadline；启动、登录或查看时先读库判断是否过期，再按规则结算或重新注册剩余 timer。
- PVF 只读缓存必须使用 `Lazy`、锁或并发集合安全发布；缓存是派生数据，不是在线业务真源。

### 5.9 NPC 好感度

- NPC、等级门槛、每日赠礼次数、特殊赠礼数量、点数范围和物品分组均以当前 PVF 的 `etc/npcfavorsystem.etc`、`npc/npc.lst` 与对应 NPC/物品文件为准，不在协议层复制名单。
- A21 `REQUEST_NPC_FAVOR_OPERATION`（0x032A）已验证的赠礼请求固定为 8 字节：操作字节、NPC `Int32LE`、原始物品空间字节、槽位 `UInt16LE`。当前只接受实机捕获的 `operation=0` 与 `space=0x24`；其他操作和空间必须继续 fail closed，不能按相邻命令猜测。
- 请求不携带数量。特殊晶体赠礼使用 PVF `[favor gift item count]`；普通赠礼使用当前好感阶段匹配规则的最低数量，未命中偏好规则时一次消费 1 个。
- NPC 文件必须同时兼容旧 `[favorable relationship]` 与新版 `[favorable relationship 2]`。新版使用其 `[favor level point]` 的倒数第二项作为信赖门槛、最后一项作为点数上限，初始点数为 0；每日特殊晶体次数继续取全局 `[favor gift limit]`。
- 在线赠礼必须取得当前 session 拥有的 `InventoryLease`，背包扣除与 v33 `character_npc_favor` 更新通过同一个 `OnlineInventoryMutationCommitCoordinator` 事务提交。提交失败必须恢复在线背包，成功后只刷新实际变化槽位。
- 成功赠礼必须回复同类型 CMD 0x032A ACK。当前客户端 `DNF.exe`（SHA-256 `1F8244D3F7309BBE2FDE4299E1863A894F6B28D5707BF01732980585B20B00DD`）先由 CMD dispatcher 消费 `result UInt8(1)`，再进入 VA `0x01133D90` 的成功赠礼分支消费 12 字节：`operation UInt8(0)`、`npcId Int32LE`、`appliedFavorPointDelta UInt16LE`、`favorPoint Int32LE`、`giftDisposition UInt8`，因此完整 ACK body 固定为 13 字节。ACK 使用事务实际提交后的点数与实际增量，并先于背包槽位刷新发送；空 ACK 或缺失成功结果字节不会触发客户端 NPC 反馈对话。达到同一 NPC 的每日赠礼次数后不得扣物品或改变好感度，并回复 `result UInt8(0) + error UInt8(0x66)`；客户端失败分支 VA `0x01133FDD` 将 `0x66` 映射到 `dstr.dat` 资源 65020（0xFDFC）的“已超过每天可赠送的次数上限。”。其他尚未闭环的失败原因继续 fail closed，不得复用相邻错误码。
- 好感点跨日保留；每日计数按北京时间 06:00 惰性换日。进入信赖阶段的 NPC 数量上限为 3。尚未进入赠礼 ACK 的初始化/全量同步仍不得猜测：`NPC_FAVOR`（0x00C2）已逆向为 `UInt16 count + count * (UInt16 npcId + UInt16 favorValue)`，`NPC_MOOD`（0x00C3）为 `UInt16 count + count * (UInt16 npcId + UInt8 mood)`；`NPC_FAVOR_POINT_INFO`（0x02E7）虽已确认读取宽度，但字段业务语义未闭环，暂不发送。

### 5.10 角色经验与升级奖励

- 角色经验与等级的业务入口统一使用 `CharacterExperienceService`：会话经验用 `Grant`，已有事务用 `GrantInTransaction`，教程直升用 `GrantToLevel`；升级券及同等级属性刷新用 `CommitProgressInTransaction`。`CharacterProgressService` 仅为其内部持久化原语。业务代码不得裸写 `characters.level/exp`，或另建升级计算和奖励触发入口。
- 角色等级、经验、战斗属性与 `character_level_up_events` 在同一事务提交；需要保存角色或采用 `OnAnyChange` 的账号荣誉、成长胶囊增量也并入经验事务。`OnLevelUpOnly` 杀怪在未升级且不需满级纠偏时，账号增量沿用唯一的 `AccountExperienceBuffer` 内存累计，由上游的分钟、离图和停机入口合并保存，不能恢复为每只怪写库。成功升级后沿用账号 pending 的 flush，保证后续直接读库的角色广播可见；失败保留 pending 等待原有缓存重试。已有调用方事务内的直写不得消费 pending，避免回滚丢失此前杀怪经验。事件的前等级来自事务内数据库，只在实际升高时记录，重复保存、同等级属性刷新、满级纠偏及降级不产生升级事件。应当保存的经验无法落库时，事务内入口必须抛出失败，不能允许任务或其他调用方继续提交奖励；提交失败不得发布新的会话等级。
- 杀怪与队伍经验、普通通关及持久经验效果、任务、死亡之塔、大会、经验道具、升级券和教程直升均由共同持久化原语自动记录事件。各 handler 保留原来的 EXP、SP/TP、属性和任务通知，不能用奖励通知替代。GM 工具或外部直接改库不属于该接口；需要发升级奖励的管理操作必须调用统一入口。
- 基础奖励只读当前 PVF `etc/serverparameter_chn.etc` 的 `[level up reward]`：每段为等级、两个客户端文本参数、物品编号、数量。文本参数不推断为职业条件；损坏、重复等级的定义整体拒绝。跨级按 `(previousLevel, newLevel]` 逐级匹配。配置在投递时解析并按进程缓存，修改 PVF 需重启；没有配置的等级不发邮件。
- `CharacterLevelUpRewardService` 只消费已提交的事件。一次事件的所有系统邮件、附件、审计、`character_level_up_rewards` 永久发放账本和基础邮件消费标记同事务提交；任何失败整单回滚，事件保留并延迟重试。账本按角色、奖励键和等级唯一，邮件过期、领取、删除或清理不会恢复发奖资格。
- 基础邮件为 30 天有效的系统邮件，使用 `level-up-reward:{characterId}:{level}` 幂等键；到期从成功投递时间算起。schema v34 迁移只建立升级事件和发放账本，不从已有邮件或角色当前等级推断发放记录，也不补发历史等级奖励。
- `ServerRuntimeBuilder` 装配邮箱和奖励服务。公共命令完成后统一处理待投递事件，包括请求触发的其他队员；启动及 `ClockService` 的有界恢复提醒处理尚未投递的事实。timer 不创建升级事实，SQLite 工作在 Clock 顺序回调内，异步发包单独调度。关闭运行时必须取消恢复和通知 timer。
- 通知只在邮件事务提交后，经当前角色 transition gate 和 owned `InventoryLease` 发送。重登从持久收件箱恢复，网络发送失败不得撤销或重发邮件。`MAILBOX_ALARM` 复用邮箱 builder；个人提示使用 `SERVER_BROADCAST_TIME_MESSAGE`，枚举取自 `PacketTypesA21`，正文为毫秒 Int32 与 GBK DSTR。无客户端 ACK 的提示不承诺恰好展示一次，UI 与时序仍须实机验证。
- 后续等级活动可通过 `CharacterLevelUpEventRepository.LoadCommittedAfter` 读取已提交事件；每个活动自己保存消费游标、资格和幂等账本，并将奖励与游标提交放入同一事务。不得复用基础邮件的消费标记，也不得把登录当前等级当作新升级。面向已有等级角色的活动须另定义资格扫描规则。
- 修改该入口必须串行运行 `--selftest-character-level-up-reward`、相关经验/道具/任务/副本测试及 `--selftest-all`，显式设置 `PVF_ARCHIVE_PATH`。测试应覆盖跨级、回滚、失败重试、并发消费者、过期清理、新库与既有库迁移、队伍投递、重启、旧会话与原有 EXP/属性/任务通知。

## 6. AI 和多人协作专用规则

### 6.1 开始修改前

1. 先读取根目录 `AGENTS.md`、本规范、贡献指南和目标业务域专项文档；副本、背包、GM、副职业和 ClockService 的专项文档必须按目标范围联查。
2. 使用文件清单和符号搜索确认真实路径、命名空间、调用者和现有测试。
3. 检查工作区是否已有他人修改；不回滚、不覆盖、不重置无关改动。
4. 先写简短变更说明：目标、非目标、受影响文件、验证命令和预期退出条件。

### 6.2 修改过程中

- 手工代码和文档编辑使用 `apply_patch` 或等价的可审阅小补丁；禁止未经审阅的全局替换、正则批量重写和整目录格式化。
- 禁止使用 `git reset --hard`、强制 checkout 或递归删除等破坏性操作处理不明来源的工作区变化。
- 不确定的协议、数据库字段、PVF 语义或旧代码行为必须标记为“待确认”，不能凭名称推断。
- 不得为了通过编译删除校验、吞异常、放宽长度检查、添加默认账号或绕过事务。
- 不得新增第二个类似的 Service、Repository、缓存、随机源或生命周期管理器，除非文档说明现有所有者无法复用。
- 开发规范只改正文，不得追加更新记录。
- 每次出现编译错误、测试失败、命令路径错误或文档与实现不一致，都要在同一批次的提交或 MR 描述中登记。

### 6.3 提交前

- 代码、SelfTest、规范正文和提交说明必须彼此一致。
- 所有相关 SelfTest 串行执行；共享日志冲突时停止并改为串行，不得用并行结果冒充验收。
- 检查数据库、PVF、协议 ID、迁移版本和生成文件是否发生非预期变化。
- 提交说明必须列出：修改批次、变更文件、行为变化、数据库影响、PVF 影响、测试结果和未完成项。

## 公会业务接入边界

### 公会地下城

- 定义只读当前 PVF 的 `etc/guild/guilddungeon/guilddungeonstyle.lst` 与其引用文件，由 `GuildDungeonFile` 解析、`GuildDungeonCatalog` 验证并发布不可变目录。前置、征服阈值、每次通关增量和奖励均从目录读取，禁止硬编码全图开放或修改客户端资源。
- `GuildDungeonService` 负责入场与结算编排，`GuildDungeonRepository` 是进度持久化 owner。连续迁移 v39 增加 `guild_dungeon_progress` 和 `guild_dungeon_clears`；完整基线 `item_schema.sql` 同步包含两表，业务运行时不得建表。
- 本地服务端周期政策为北京时间每月 1 日 06:00 重置。按绝对时间计算当前周期，以公会、周期、样式和地下城为进度键，重启不能重置或延长周期。此时间是本服政策，不是由客户端协议推导的官方运营周期。
- `GUILD_DUNGEON_INFO` 使用 `NotiPacketTypeA21` 枚举。包体依次为启用字节、样式 Int32、截止 Unix 秒 UInt32、待确认 UInt32（保持 0）、条目数 UInt32；每项是地下城 UInt32、通关次数 UInt32。当前客户端 SHA256 `1F8244D3F7309BBE2FDE4299E1863A894F6B28D5707BF01732980585B20B00DD` 的处理函数 `005BC2A0`、倒计时消费 `0271E969 -> 028A2F20` 与征服计算 `02A4A670` 是字段依据；进度字段是通关次数，不能写入百分比或原始征服值。
- 已入会角色登录在 `GUILD_INFO`、`GUILD_AGIT_INFO` 后追加地下城状态，仍位于 `USER_STATE` 前；未入会角色发送禁用状态，清除切换角色后的客户端残留。公会身份刷新与进入选图时重新查询当前周期。协议里的未确认字段、重复通关加成及周特殊奖励不得凭相邻字段或包名补造语义。
- 入场必须验证当前成员关系和全部前置征服阈值，并冻结公会、周期和样式到 participant selection 与 instance mechanism。结算重验成员和周期；跨月旧 run、已离会成员不能给新周期或其它公会写入进度。
- 每位有效参与者以权威结算事件和角色编号去重；一次事务写入通关次数、公会与个人贡献、系统奖励邮件及结算台账。SQLite 下 `IGameDatabase.Write` 的 immediate 写事务即同公会结算的串行化边界，不另加行锁；失败全部回滚，重放不得重复发奖。奖励附件走现有邮件领取及背包提交链路，不能由副本 Handler 直接改背包。
- 聚焦回归为 `--selftest-guild-dungeon` 与 `--selftest-a21-guild-creation`，须显式设置当前 `PVF_ARCHIVE_PATH`，串行执行后再跑 `--selftest-all`。客户端倒计时、实际入场、通关、邮件领取和重登持久化仍须独立实机验收。

### 公会基础功能

- `guilds`、`guild_members`、`guild_applications` 由基线 schema 和连续迁移 v29 创建；运行时禁止隐式建表。公会名称大小写不敏感唯一，一名角色只能属于一个公会。创建时必须在同一事务中建立公会、会长成员记录并扣除创建费。
- `GuildCreationHandler` 的创建草稿绑定 owned `InventoryLease`，由现有角色 transition gate 串行执行；取消、重新检查名称时清除认证，换角色或重新登录不得继承认证。名称检查后由客户端上传宣传语并申请认证，服务端自动批准单人创建，不需要另一名玩家。
- 公会名按 GBK 计长，服务端政策为 2～24 字节，并复用 PVF 名称规则；宣传信息限制 40 字符、80 字节。名称检查不是预占，实际创建必须在事务中再次检查唯一性。
- 当前客户端名称检查成功 ACK 为单字节成功标记，失败为成功标记与错误字节；单人认证使用 `REPLY_GUILD_CREATE_PERMIT` 的单字节通过结果，不创建虚拟玩家。依据当前 DNF.exe（SHA256 `1F8244D3F7309BBE2FDE4299E1863A894F6B28D5707BF01732980585B20B00DD`）名称回调 `0111A2C0`、认证回调 `0118AE20`，名称请求已有 GBK DSTR 抓包。
- `CALL_GUILD_CREATE_RIGHT` 最终请求严格接受实机捕获的单字节 `01`，并要求当前草稿已认证。`GuildCreationService` 从当前 PVF 的 `[guild create cost]` 读取费用，通过现有 `OnlineInventoryMutationCommitCoordinator` 原子扣金、建立公会和会长成员；失败沿用在线背包回滚恢复，重复创建不得再次收费。
- 成功提交后先刷新金币与角色身份，再下发 `GUILD_CREATE` 和创建成功 ACK。成功通知布局依据客户端 `0118E350`（公会编号与名称 DSTR）；ACK 回调 `0111A3A0` 打开 `GuildMakeComplete.xui`。单人创建、成员列表与申请审批已有当前客户端实机证据；重登恢复仍须独立验收。
- 角色公会身份只从 `guilds`/`guild_members` 投影。当前客户端 `013E758E -> 013E2BF0` 将宠物信息之前的 UInt32 写入角色公会编号，不能使用旧 `FatiguePenalty` 字段。宠物存活状态之后的尾部由两字节、UInt32、名称 DSTR、公会等级 UInt32 及剩余字段组成（`013E75CB` 至 `013E7601`、`013E2E60`）；名称变长时必须整体移动后续副职业、名誉、心情与技能页字段。新公会等级为 1，尚未开放升级。
- `GUILD_MEMER_LIST` 接受空请求；`GUILD_ALL_MEMBER_LIST` 接受 UInt32 零的初始全量请求，两者均按请求者的持久化成员关系查询在线和离线成员，不能由客户端指定其它公会编号。全量回包沿用成员行格式，末尾额外写 UInt32 零（`01134670 -> 01130B60`、`01130FD6`）；一次返回完整名单，不注册未验证的后续分页。处理器绑定当前角色 transition 和 owned lease，非成员或畸形请求返回失败，同时补发请求者的 `GUILD_MEMBER_INFO` 职级。
- 成员列表布局依据同批客户端 `01130B60`：成功字节、公会编号、会长名称 DSTR、UInt32 进度、UInt16 总人数、UInt16 行数；每行依次为角色编号、名称 DSTR、备注 DSTR、UInt16 等级、职业/转职/服务器/频道/职业显示标记/隐藏标记/职级七字节、UInt32 离线秒数、账号编号、代表角色标记与账号别名 DSTR。本命令没有全量分页命令的末尾游标。频道 FF 的离线含义由 `01130F6E` 与 `00777770` 验证，职级位于客户端成员对象 +148（`019EB1C2`），离线秒数的显示换算见 `00774D4D`。
- 会长职级 1 只从 `guilds.leader_character_id` 投影，其他成员职级由 `guild_members.rank` 持久化，默认 4，范围 2～5。频道由 session directory 中仍拥有当前租约的会话解析。离线时间暂取账号最后退出时间，缺失时取角色保存时间，并限制在 0～Int32.MaxValue；它不参与收益或权限判断。成员列表里的公会进度字段写入 `guilds.contribution`；代表角色和账号别名保持空状态。
- 申请留言由连续迁移 v30 的 `guild_applications.message` 持久化；服务端留言政策沿用 40 字符、80 GBK 字节限制。重复申请保留首次留言与时间。搜索按完整公会名查询，申请列表只向该公会会长返回；审批必须在同一数据库事务校验会长、申请和成员唯一性、插入成员并删除其所有申请。
- `guild_applications.applied_at` 持久化 UTC 绝对时间；申请列表末尾 UInt32 必须在查询时投影为已经过的秒数，不能直接发送 Unix 时间戳。当前客户端 `024DB878 -> 024DB440` 直接以 86400、31536000 比较并按小时/天换算，不会自行减去当前时间。投影下限为 0，上限为 Int32.MaxValue，以适应客户端有符号比较；重启不得重置申请时间。不足一小时显示“1小时前”属于客户端换算行为。
