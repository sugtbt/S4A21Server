# 副本架构业务接入规范

本文是副本、任务副本、特殊地下城、塔类副本、竞技/大会类副本和后续副本机制的对外接入规范。

## 一、提交前必须完成的流程

1. 阅读本规范、`CONTRIBUTING.md`、相关背包规范，以及关联 issue/MR、协议证据和已有同类实现。
2. 从最新 `main` 创建分支，先确认基线可以构建和运行相关回归。
3. 先定位 PVF、ETC、任务、协议和已有同类机制的证据，再设计代码入口。
4. 明确共享副本实例、玩家参与状态、房间状态和持久状态的所有权。
5. 先实现 typed definition、runtime、fact/intent 和应用服务，再接入网络投影。
6. 为重复事件、并发结算、断线、旧 timer 和失败重试定义行为。
7. 添加或更新自动化测试，运行公共路径回归和实机验证。
8. 检查迁移、协议字段来源、日志和 diff，确认没有临时测试代码、生成文件或无关重构。
9. 在 MR 描述中写清楚变更范围、证据、数据库变化、测试结果和未完成项。

## 二、核心术语

### 1. DungeonInstance

共享物理副本实例。它表示同一队伍实际进入的那一份地图世界，负责：

- 唯一的 <code>PartyDungeonInstanceId</code>。
- 共享选图快照和奖励策略。
- 已冻结的房间模板。
- 房间状态、世界效果账本和诊断 journal。
- 同一物理世界中的召唤、开门、地图改变和通关事实。

### 2. DungeonRun

玩家参与状态。历史类名继续保留，正式语义等同于 <code>DungeonParticipantRun</code>。

<code>PlayerContext.CurrentRun</code> 是玩家当前参与入口，负责：

- <code>RunId</code> 和 <code>RunGeneration</code>。
- 玩家任务快照、Buff、掉落资格、统计和结算投影。
- 当前房间引用。
- 玩家级机制运行态和 timer registry。

不得为了改名推倒 <code>PlayerContext.CurrentRun</code>，也不得把它重新解释成共享物理实例。

### 3. DungeonInstanceRoom

共享房间实例，负责：

- <code>RoomInstanceId</code>。
- 最终 MAP 模板和随机 seed。
- <code>FirstActorSequenceId</code>。
- 房间状态和具名 Encounter runtime。
- 组队成员共享的房间清理事实。

### 4. Definition、Runtime、Projection

- Definition：从 PVF/ETC 解析并冻结的只读规则。
- Runtime：某个 Instance、Room 或 Player 在单局中的可变状态。
- Projection：把权威状态投影为协议包、客户端 UI 或日志。

三者不得混在同一个可变大类中。

## 三、总体架构

~~~text
客户端 CMD
  -> GameProtocolHandler
  -> typed Parser
  -> Handler / Coordinator / Application Service
  -> DungeonInstance + DungeonRun + DungeonInstanceRoom
  -> typed Fact / Directive / Effect Intent / ClearIntent
  -> Repository / InventoryService / ClockService / PartyManager
  -> Notification Projector / Sender / Builder
  -> 客户端 NOTI 或 CMD ACK

PVF / ETC
  -> Tool/PvfLib
  -> GameWorld Catalog / Index / Projector / SelectionPlanner
  -> immutable Definition / SelectionSnapshot / ResolvedRoomTemplate
~~~

依赖方向必须从网络适配层指向应用层和领域层，再指向配置投影或 Repository。领域层不能反向依赖 Session、包 Builder 或原始 header/body。

## 四、当前代码中的真实分层

本章描述当前生产接线，不按目录名猜测所有权，也不把“类型已经存在”解释为“跨进程恢复已经完成”。现阶段的标准调用方向是：

~~~text
raw packet
  -> typed parser / network adapter
  -> application coordinator
  -> Instance / Room / ParticipantRun 的权威 transition
  -> typed intent / result
  -> Repository、InventoryService 或 Sender
~~~

物理目录仍保留少量迁移期兼容位置，例如 <code>DungeonKillApplicationService</code> 位于 <code>Network/Handlers/Dungeon</code>；这不赋予它发明第二套领域状态的权限。

### 1. Definition 输入层：Tool/PvfLib 与 GameWorld

<code>Tool/PvfLib</code> 忠实解析 DGN、MAP、ETC、QST 和脚本字段，保留重复字段、顺序、作用域和原始来源；格式错误必须返回可诊断结果。它禁止发包、读取在线玩家、修改单局状态或按副本 ID 决定业务。

安图恩攻坚团本的 phase limit、地下城 active/recovery/passive、孵化场首次/重复周期和 reserve-open 延迟来自 <code>etc/raid/anton.etc</code> 的 immutable definition。<code>Tool/PvfLib</code> 必须保留 phase、trigger/behavior 上下文、重复指令、顺序和来源；<code>Game/Raid</code> 只负责带有效值、冲突及 recovery/reserve 一致性校验的语义投影，运行时不得重新解析 raw token 或维护第二套时长真源。

<code>GameWorld</code> 将解析结果投影为进程内只读目录、关系索引和不可变 Definition，当前生产组件包括 <code>DungeonCatalog</code>、<code>DungeonMapCatalog</code>、<code>QuestCatalog</code>、<code>QuestRelationIndex</code>、<code>QuestTargetIndex</code>、<code>QuestRewardProjector</code>、<code>DungeonSelectionPlanner</code>、<code>ResolvedRoomTemplateProvider</code>、<code>DungeonActorTemplateProjector</code>、<code>SpecialDungeonDefinitionCatalog</code>、<code>TournamentDungeonDefinitionCatalog</code>、<code>BloodAltarDungeonDefinitionCatalog</code> 和 <code>DungeonRewardPolicyData</code>。

GameWorld 可以缓存当前进程内不会变化的 PVF 投影，但不得持有某一局的可变运行态。运行时 PVF 热替换和 index 重建不属于当前服务器合同。

### 2. 领域所有权层：Game/Dungeon

| 权威 owner | 当前职责 | 当前 checkpoint |
| --- | --- | --- |
| <code>DungeonInstance</code> | 共享选择快照、共享房间、唯一 <code>DungeonClearedFact</code>、实例 effect、参与者 effect journal 和诊断 journal | 全部为进程内 |
| <code>DungeonInstanceRoom</code> | 房间 identity、共享 actor 死亡事实、Encounter 和清房状态 | 全部为进程内 |
| <code>DungeonRun</code> | 单个参与者的 Selection、Combat、Settlement、QuestBridge、Mechanisms、Timers 和个人 effect ledger | 全部为进程内 |
| <code>DungeonInstance.Mechanisms.BloodAltar</code> | 祭坛共享 MAP、轮次、波次、动态 actor、实例 timer 和唯一完成事实 | 全部为进程内 |
| <code>DungeonRun.Settlement.BloodAltar</code> | 祭坛参与者结算阶段、奖励提交、经验/金币/UI/返城 checkpoint | 全部为进程内 |
| <code>DungeonInstanceRegistry</code> | participant attachment 的 Active/Detached/恢复/取消/过期状态 | 全部为进程内 |
| <code>DungeonPersistentEffectOutbox</code> | 已登记的非库存持久 effect lease、提交结果和失败重试 | SQLite 持久化，但只覆盖已登记 kind |

<code>DungeonEventEnvelope</code>、<code>DungeonEffectId</code>、<code>DungeonEncounterDirective</code> 和 <code>DungeonClearIntent</code> 是跨入口传递事实与意图的 typed 合同。<code>SpecialDungeonMechanismApplicationService</code> 与 <code>SpecialDungeonEffectPlanJournal</code> 也属于本层；前者不在 Network 层。

Tournament 的共享 bracket、轮次、路径 actor 与死亡事件账本属于 <code>DungeonInstance.Mechanisms.Tournament</code>；参与者 EXP、两组奖励选择及投递 checkpoint 属于 <code>DungeonRun.Settlement.Tournament</code>。<code>TournamentDungeonApplicationService</code> 只转换这些领域状态，不读取 raw packet 或直接发包。

祭坛的共享波次、难度分支、动态 actor 和实例 timer 属于 <code>DungeonInstance.Mechanisms.BloodAltar</code>；参与者经验、金币提交、结算 UI 和返城竞争属于 <code>DungeonRun.Settlement.BloodAltar</code>。两者不能互相代替：参与者 settlement runtime 尚未建立时，祭坛实例仍拥有祭坛专用命令，命令必须被消费并 no-op，不得落入普通 Card 入口。

<code>DungeonRun</code> 根部仍保留兼容投影属性。新增代码应写入组合状态对象或正确的 Instance/Room owner，不得继续向根部平铺世界状态。

### 3. 任务应用层：Game/Quests

任务命令由 parser/network adapter 转为 typed 请求，再进入 <code>QuestAcceptanceApplicationService</code>、<code>QuestGiveupApplicationService</code>、<code>QuestCompletionApplicationService</code> 或 <code>QuestProgressApplicationService</code>。目标判断由 <code>QuestObjectiveEvaluator</code> 完成，变化由 <code>QuestProgressReducer</code> 生成，Repository 负责事务与 CAS，<code>QuestNotificationProjector</code> 只投影结果。

副本事实不直接写任务表，而是通过 <code>DungeonQuestBridge</code> 或任务专用同步入口携带 <code>QuestRunSnapshot</code>、<code>QuestActivationId</code> 和 <code>DungeonEventEnvelope</code> 进入同一任务应用服务。<code>QuestManager</code> 仍是普通任务网络命令的兼容门面，不是第二个任务真源。

### 4. 应用编排层：Network/Handlers/Dungeon

当前生产唯一入口如下：

| 业务 | 生产入口 | 不得旁路的权威状态 |
| --- | --- | --- |
| 选本/建局/START_MAP | <code>DungeonEntryHandler</code>、<code>DungeonMapHandler</code>、<code>DungeonRunLifecycle</code> | Instance selection、Run identity、Room identity |
| 普通击杀与 party relay | <code>DungeonKillApplicationService.ProcessAsync(KillContext)</code> | shared death fact、frozen participant roster |
| 通关 | <code>DungeonSettlementHandler.SubmitClearIntentAsync</code> | <code>DungeonClearedFact</code>、participant clear checkpoint |
| 结算展示 | <code>DungeonSettlementHandler</code> | authoritative settlement effect、pending presentation |
| 副本专用命令 | <code>DungeonCommandReceivedDispatcher</code> | typed command 与完整 run/room identity |
| 断线重连 | <code>DungeonRejoinCoordinator</code> | Registry attachment 与原 <code>DungeonRun</code> |
| 特殊机制外部效果 | <code>SpecialDungeonEffectRouter</code>、<code>SpecialDungeonNotificationSender</code> | Game/Dungeon 已冻结的 effect plan |
| 大会机制 | <code>TournamentDungeonCoordinator</code> | Instance Tournament runtime、participant reward state、Champion 唯一 <code>ClearIntent</code> / Eliminated 失败终止 |
| 祭坛机制 | <code>BloodAltarDungeonCoordinator</code> | Instance Blood Altar runtime、participant settlement、唯一祭坛 <code>ClearIntent</code> 与专用 settlement |

<code>DungeonMechanismCoordinator</code> 和 <code>SpecialDungeonNotifier</code> 是薄编排/兼容门面。Handler 不得自行建立第二套 run、clear、任务、timer 或奖励状态机。

### 5. Builder、Sender、Repository 与 composition root

- Builder 只序列化已确认字段。
- Sender 只执行协议投影，不决定领域成功。
- Repository 只负责数据库读写、CAS 和事务，不读取 Session 或发包。
- <code>DungeonSharedServices</code> 只作为 composition root，不承载新的业务判断。
- 无 ACK Sender 成功只能表示写入 transport，没有客户端消费确认；不得据此宣称 exactly-once。

### 6. 当前保留的专用链路

Card 已接入普通 Settlement 的个人状态；AntonNormal 已接入普通 clear 的持久机制 effect；Tournament 使用独立 definition/runtime 与奖励协议，复用 canonical kill，且只有 Champion 结果进入普通 <code>ClearIntent</code>。Eliminated 结果在 Tournament 专用终止态完成，不得伪装成普通通关。DeathTower 仍使用独立的 stage runtime、塔内物品和 settlement 入口，只在建局、击杀适配与 EndRun 生命周期上复用普通框架。Blood Altar 使用独立的 instance wave/runtime、参与者 settlement 和专用协议，不能回落到普通卡牌结算。专用链路的实际原子性与恢复限制以第十八章为准，不能因为已经拆出 Service/Coordinator 就推断为统一 pipeline。

| 状态 | 所有者 | EffectScope | 示例 |

| 共享选图、最终 MAP | DungeonInstance | Instance | maze、Boss MAP、起点 |
| 房间 actor、开门、清房 | DungeonInstanceRoom | Room | 条件 Boss、门、波次 |
| 队伍共同世界效果 | DungeonInstance | Party/Instance | 一次召唤、一次地图改变 |

| 任务、Buff、个人统计 | DungeonRun | Player | QuestRunSnapshot、能量 Buff |
| 翻牌和个人结算 | DungeonRun | Player | 免费卡、付费卡、经验 |
| 神秘商店每人商品、购买库存 | DungeonRun | Player | 商品候选独立抽取，SecretShopOffer 每人独立扣减，互不影响 |

现有 <code>DungeonMechanismRuntimeSet</code> 中仍有兼容字段。新增世界事实不得因为这些旧字段存在而继续平铺到每个玩家 run；应优先放入 Instance 或 Room。

## 六、身份与代际

### 1. 必需身份

~~~text
DungeonInstanceIdentity
  = PartyDungeonInstanceId

DungeonParticipantRunIdentity（兼容名 DungeonRunIdentity）
  = DungeonInstanceIdentity
  + RunId
  + RunGeneration

DungeonRoomIdentity
  = DungeonInstanceIdentity
  + RoomInstanceId

DungeonParticipantRoomIdentity
  = DungeonParticipantRunIdentity
  + DungeonRoomIdentity
~~~

### 2. 校验规则

- 组队转发必须确认同一 <code>PartyDungeonInstanceId</code>。
- 房间事件还必须确认同一 <code>RoomInstanceId</code>。
- 异步 continuation 必须确认 <code>RunId + RunGeneration</code> 仍匹配。
- session、characterId、party 引用和 <code>RoomKey</code> 只能作为辅助条件。
- <code>DungeonId + RoomKey</code> 不能证明属于同一物理实例。
- 新局建立必须先推进 generation，使旧 timer、旧 await、旧 relay 和旧结束流程失效。

### 3. EventId 传播

本地击杀与 party relay 必须传播同一个 <code>SourceEventId</code>。针对不同参与者投影时使用 <code>ForAffectedPlayer</code> 改写受影响 run/room，不得生成新的业务事件 ID。

## 七、生命周期状态机

### 1. Run

~~~text
Created -> Selecting -> Active -> ClearCommitting -> Cleared
   |           |          |              |             |
   +-----------+----------+--------------+-----------> Ending -> Ended
~~~

合法入口：

- <code>TryBeginSelecting</code>
- <code>TryActivate</code>
- <code>TryBeginClearCommit</code>
- <code>TryCompleteClearCommit</code>
- <code>TryBeginEnding</code>
- <code>TryMarkEnded</code>

重复转换返回 no-op 或 false。<code>Ended</code> 不得回退。

### 2. Settlement

~~~text
NotStarted -> Preparing -> ResultShown -> CardsRevealed -> Completed
                                  \---------------------> Completed
~~~

只有 Run 已进入 <code>Cleared</code> 才能开始 settlement。

### 3. Room

~~~text
Created -> Active -> Cleared -> Closed
~~~

房间重访复用已经冻结的 <code>DungeonInstanceRoom</code>，不重新随机模板。

### 4. Encounter

~~~text
NotStarted -> Active -> Succeeded
                    \-> Failed
~~~

- 同一 <code>SourceEventId + DirectiveKind</code> 重放返回 <code>Replayed</code>。
- 重复 Start/Succeed 返回 <code>NoOp</code>。
- <code>Succeeded</code> 与 <code>Failed</code> 都是终止态，不可互相回退。
- 当前生产接入在 START_MAP 提交 Start，在清房和 ClearIntent 提交 Succeed。
- Encounter 记录事实，不直接发奖励、开门或结算。

旧 <code>DungeonRunPhase</code> 只保留兼容投影，新业务不得将其作为状态真源。

## 八、事件与效果

### 1. DungeonEventEnvelope

事件至少携带：

~~~text
SourceEventId
PartyDungeonInstanceId
RunId
RunGeneration
RoomInstanceId
SourcePlayerId
AffectedPlayerId
SourceActorId
SourceActorCode
Cause
OccurredTick
~~~

### 2. DungeonEffectId

~~~text
EffectId
  = SourceEventId
  + EffectKind
  + EffectScope
  + ScopeTarget
~~~

Effect scope 只能是 Instance、Party、Room、Player 或 Persistent。

### 3. 内存 effect ledger

~~~text
Absent -> Reserved -> Committed
                   \-> Failed -> 可用同一 EffectId 重试
~~~

规则：

- reserve 在所属聚合锁内完成。
- 网络、数据库、PVF 读取和其他 I/O 在锁外执行。
- commit 必须使用 reserve 返回的 lease。
- <code>Reserved</code> 或 <code>Committed</code> 的同一 EffectId 不重复执行。
- 失败重试必须复用原 EventId 和输入，不得生成新 ID 绕过去重。

## 九、选本与任务地图

### 1. 选择快照

队长根据入口、难度和进本时任务生成唯一 <code>DungeonSelectionSnapshot</code>。组队成员复用 maze、layered map、起点、Boss 坐标、随机 Boss MAP、linked dungeon 和特殊候选。

不得让每名队员独立随机共享物理地图。

### 2. Dungeon Admission 与拒绝投影

选本准入必须按以下单向链路执行：

~~~text
任务/权限/入场物品/疲劳/次数检查
  -> DungeonAdmissionReject（网络无关事实）
  -> DungeonAdmissionRejectBuilder（A14 协议投影）
  -> DungeonAdmissionRejectSender（唯一 SELECT_DUNGEON 失败 ACK）
~~~

- 业务服务不得直接选择错误码、拼接 ACK 或调用专用“缺票 builder”。Tournament、普通 DGN required-item、疲劳和 ETC 次数规则只能返回 typed 拒绝原因。
- 专用副本分流完成后，普通入口必须先通过 <code>DungeonSelectionPlanner.TrySelectMaze</code> 解析真实路线，再创建 run、清理旧 run 效果或触发任何入场消费。没有普通 maze 且未接入专用 runtime 的副本返回 <code>DungeonUnavailable</code>；不得让缺失迷宫异常关闭连接，也不得伪造普通地图。
- A14 <code>SELECT_DUNGEON(0x0010)</code> 的所有失败体固定为 <code>success=0 + errorCode + context</code> 三字节；不得省略 context。
- <code>MissingRequiredItem(memberSlot)</code> 投影为 <code>00-11-slot</code>；<code>InsufficientFatigue(memberSlot)</code> 为 <code>00-16-slot</code>；<code>MemberEntryLimitReached/MissingPermission(memberSlot)</code> 为 <code>00-AD-slot</code>；<code>DailyEntryLimitReached</code> 为 <code>00-F6-00</code>。<code>MissingPrerequisite</code> 必须保留稳定失败槽、目标副本和有序缺失前置：catalog 将目标唯一解析为 rewardable capability 时使用原生整队条件提示 <code>00-07-00</code>；目标唯一属于连续副本且 rewardable capability 明确 absent 时，先用静默 <code>00-09-00</code> 收束失败，再以 <code>NotiPacketTypeA21.SERVER_NOTICE_MESSAGE</code> 投影准确文案。玩家通知中的目标与缺失前置必须使用当前 PVF DGN <code>[name]</code>，不得显示内部副本 ID 或维护 ID/名称硬编码表；目标名称或任一前置名称不可用时，显示不含 ID 的通用前置条件提示。内部副本 ID 只保留在结构化事实与诊断日志中。目录 absent/ambiguous 或结构化事实不完整时保守使用原生拒绝，不得解析诊断字符串或按副本 ID 选择协议。
- <code>NotPartyLeader</code> 投影为 <code>00-08-00</code>；<code>InvalidSelectionState</code> 为 <code>00-13-00</code>；<code>DungeonNotFound</code> 为 <code>00-15-00</code>。没有更精确且已验证的客户端语义时，<code>Unknown/DungeonUnavailable</code> 保守投影为 <code>00-01-00</code>。
- context 的成员槽来自 Party 冻结的稳定槽位，合法范围为 <code>0..7</code>；不得按大会、门票 ID 或副本 ID 特判。非成员级拒绝的 context 必须为 0。
- 任务地图目录只裁决开放资格，不负责协议；linked dungeon 授权、大会 definition 和扣票失败也复用同一 sender。已创建 Selecting run 后拒绝时，必须按 expected run identity 原子结束旧 run，并在同一生命周期临界区恢复新的 <code>DungeonSelectionContext</code>，保证 <code>GIVEUP_GAME</code> 仍可回城。
- 当前生产已接入任务门禁、linked destination 和 Tournament definition/required-item 的 typed 拒绝。统一疲劳消费和 ETC 入场次数服务尚未完成；接入前不得伪造扣除或从暂停试验目录复制第二套拒绝协议。

### 3. QuestRunSnapshot

每名参与者在进本时冻结自己的活动任务。当前产品语义是：

- 队长决定共享物理地图。
- 每名玩家按自己的 QuestRunSnapshot 推进个人任务。
- 进本后新接任务不追溯本局已发生事件。

<code>QuestRunSnapshot.WithQuest</code> 只把「接取事务实际写入的那一条」并入当前 run，不重建整份白名单：已发生事件不被追溯，其他任务和上一局条目也不会被带入。合并必须使用接取后重新读出的 <code>ActiveQuest</code>（含新 <code>QuestActivationId</code>），写入与进本赋值共用 <code>run.SyncRoot</code>；同一 questId 的旧 activation 被覆盖，旧局事件因此无法推进重新接取的新任务。未合并时掉落、击杀与清图都会因该任务不在白名单而被过滤，并在日志留下任务号与原因。

结构性任务条件必须在选图时冻结。临时任务副本在授权任务完成后是否关闭，由 PVF 入口、任务连接和权限投影共同判断，不按 dungeon ID 补丁处理。

### 4. MAP 解析

解析优先级必须由 <code>DungeonSelectionPlanner</code> 和 <code>ResolvedRoomTemplateProvider</code> 统一管理。显式 MAP、任务 maze、目录亲和度、入口区域和 fallback 不得散落在 Handler 中。

随机结果第一次解析后冻结到 Instance/Room；同局重访、组队成员和延迟回调必须看到同一结果。

## 十、START_MAP、房间与 actor

- 新房建立时冻结 MAP、seed、<code>FirstActorSequenceId</code> 和 actor 模板。
- actor 序号使用 <code>FirstActorSequenceId + actorIndex</code>。
- <code>run.MonsterCount</code> 只作统计，不分配 actor identity。
- 普通 MAP passive object 通常由客户端按 MAP 创建，服务端不得无证据伪造成 START_MAP actor。
- special passive object、hidden actor 和父对象来源必须保留模板身份。
- named monster 跨房过滤使用配置索引和共享房间 clear 状态，不按怪物 code 白名单。
- 进入房间后提交具名 Encounter Start；<code>run.SyncRoot</code> 只负责校验该参与者仍位于目标 room，实际 transition 由 Room 自有 Encounter runtime 提交。当前锁序固定为 Run -> Room，禁止反向获取。

## 十一、统一击杀流程

本地击杀和 party relay 都进入 <code>DungeonKillApplicationService</code> 的同一 typed <code>KillContext</code> 流程。

~~~text
wire death report
  -> parse typed kill fact
  -> identity / actor replay validation
  -> shared room death fact
  -> per-participant experience/drop/task/mechanism
  -> room clear evaluation
  -> optional DungeonClearIntent
  -> death/experience/drop notification
~~~

规则：

- 世界死亡事实只记录一次。
- 个人经验、掉落资格、任务和 Buff 逐参与者计算一次。
- 同一 EventId 重放不重复奖励。
- 不同物理副本实例的同队玩家不接收 relay。
- RewardPolicy 只控制对应奖励，不得阻断死亡动画和共享世界事实。
- 修炼道场仍传播 <code>0x0026</code> 和房间死亡事实，但不产生经验、掉落、任务进度或 clear。

### 掉落来源策略

怪物死亡可组合金币、通用物品、怪物模板物品、地区材料、独立掉落和世界掉落，但并非每类副本都允许所有来源。

~~~text
PVF DGN / ETC
  -> DungeonDropDefinitionCatalog
  -> immutable DungeonDropDefinition + DungeonDropPolicy
  -> DungeonInstance freeze
  -> DropService / DropGenerator

Independent_Drop.etc / IndependentDrop.lst / job mapping
  -> IndependentDropDefinitionCatalog
  -> immutable monster + difficulty + job-group pool
  -> DungeonRun.Selection freezes participant job group
  -> IndependentDropSystem weighted selection
~~~

- Catalog 只依据 PVF/ETC 字段和关系分类，不按 dungeon、monster 或 item ID 建白名单/黑名单。
- Definition 必须在物理实例创建时冻结；组队参与者共享同一份 definition，不得在每次击杀时重新解析 PVF。
- 应显式表达 <code>Gold</code>、<code>GenericItems</code>、<code>MonsterTemplateItems</code>、<code>AreaMaterials</code>、<code>Independent</code> 和 <code>World</code> 等 typed source。
- <code>DropService/DropGenerator</code> 只消费 source policy，不决定副本分类，也不得自行读取 DGN。
- 单人/组队概率差异优先由各自 monster template 和 ETC 词条表达；存在配置时禁止再叠固定倍率。
- <code>Independent_Drop.etc</code> 首行 17 个整数中，5 个概率列按副本难度取值，后 5 个数量列是旧组队逻辑的 1-4 人数量和最大掉落数量。当前 A21 组队掉落按每名玩家独立结算，不再先计算一次再随机分配，因此统一取第 1 个数量列作为本玩家掉落数量。
- 同一 monsterCode 的多条独立掉落配置必须逐条独立 roll；命中种类数可以是 0 到 N，不得合并成单次互斥选择。旧外部池或 job mapping 文件缺失、以及 <code>Independent_Drop.etc</code> 中的箭头分隔符、<code>#</code>/<code>//</code> 注释、单条坏行或 <code>[/independent drop]</code> 之后追加的行，只跳过对应行/池，不得清空主表。
- 独立掉落的内联 <code>listFlag=1</code> 与外部 <code>listFlag=2</code> 是不同 schema：前者按 <code>itemId/weight</code>，后者按 <code>itemId/weight/chronicleDropJobGroup</code>。解析器必须按来源建模，禁止共用步长猜字段。
- <code>chronicleDropJobGroup</code> 由 <code>characterJob + (GrowType &amp; 0x0F)</code> 映射，是参与者个人快照；不得放入共享 <code>DungeonInstance</code>。职业映射缺失时外部职业池 fail closed，不得回退到其他职业。
- 特定物理副本的怪物、难度和职业组共同决定独立池。解析顺序必须保持为 <code>monster + difficulty -&gt; active entry -&gt; external pool -&gt; job group -&gt; item/part + weight</code>；难度可以改变勇者装备部位集合，不能实现成统一装备池乘难度倍率。运行日志应保留 pool index、job group 与实际 itemId，生产代码不得把多个异界副本、怪物、难度池或装备部位合并。
- 异界专属掉落由 DGN <code>[dimension dungeon]</code> 与 <code>etc/dimensiongatedroplist.etc</code> 共同证明。<code>DimensionGateDropDefinitionCatalog</code> 只解析 <code>[chronicle grow type]</code>，按 <code>job + (GrowType &amp; 0x0F)</code> 冻结散件池和套装池；<code>DimensionDropSystem</code> 才消费当前 A21 已确认的精英/BOSS monsterCode 名单。精英怪固定抽 <code>normal+set</code> 合并池 1 件并追加 <code>3311 x1</code>；BOSS 固定抽散件 1 件、套装 1 件并追加两个独立 <code>3311 x1</code> 掉落项。缺少职业池时 fail closed，不得回退其他职业或只发碎片。
- 异界翻牌复用普通 Card pipeline 的选择、扣金币和背包发奖边界，但物品池来自 <code>DimensionGateDropDefinitionCatalog</code>：免费物品卡固定散件，付费物品卡固定套装。金币卡、付费成本和 Card effect checkpoint 仍归普通 settlement owner。
- 怪物死亡独立池与结算翻牌属于不同 effect/definition；除非配置关系明确证明共享，不得把 <code>Independent_Drop.etc</code> 池直接复用于 settlement。
- 新规则至少测试 definition 解析、实例冻结、禁用来源不泄漏、合法来源仍产出、代表性职业在各难度下的装备部位签名，以及普通副本策略不变。

## 十二、统一通关与结算

### 1. ClearIntent

普通副本的默认 Boss、PVF clear condition、任务 NPC、条件 Boss、脚本终点和特殊对象都只能生成 <code>DungeonClearIntent</code>。

DeathTower 是当前明确例外：其楼层和最终结算仍由独立 stage command/runtime 驱动，不进入普通 <code>ClearIntent</code>。该例外必须显式保留在 tower coordinator，不能被复制成其他普通副本的旁路。

禁止直接复制修改 run、发送结算包、发经验/幸运星、生成翻牌或写安图恩权限的流程。

### 2. Clear pipeline

~~~text
mechanism
  -> DungeonClearIntent
  -> identity + reward policy validation
  -> DungeonClearedFact
  -> freeze participant roster
  -> participant clear reservation
  -> Active -> ClearCommitting
  -> clear projection + quest effects
  -> authoritative settlement effects
  -> ClearCommitting -> Cleared
  -> pending/validated SET_PLAY_RESULT presentation
~~~

<code>DungeonClearedFact</code> 是稳定通关事实。<code>SET_PLAY_RESULT</code> 只补充客户端结算展示字段；它在 ClearCommitting 期间到达时进入 pending presentation，不能形成第二个奖励入口。

### 3. Settlement pipeline

~~~text
DungeonClearedFact
  -> Preparing
  -> persistent experience / lucky-star
  -> permission / persistent mechanism
  -> authoritative settlement committed
  -> Cleared
  -> pending result projection
  -> ResultShown
  -> card selection / auto flip
  -> CardsRevealed
  -> Completed
~~~

普通 settlement 的具名步骤使用稳定 EffectId；同一 run 内失败时保留可恢复状态，重试不能重放已经 committed 的步骤。只有已登记到 persistent outbox 的 effect kind 具备跨进程恢复，Card、无 ACK 投影和 DeathTower 不得套用该承诺。

### 4. 难度权限共享

普通副本难度权限属于账号，稳定键为 <code>(accountId, physicalDungeonId)</code>，并通过 <code>0x0005</code> 投影给当前角色。同一账号的不同角色共享同一个物理副本的最高已解锁难度；不同物理副本之间不得传播权限。

~~~text
character clears physical dungeon
  -> accountId + physical dungeonId + requested clear state
  -> DungeonDifficultyPermissionService
  -> monotonic account ledger update
  -> account login projection / incremental 0x0005
~~~

- <code>account_dungeon_permissions</code> 是普通难度权限的账户级真源；主键必须是 <code>(account_id, dungeon_id)</code>，更新只能取更高 <code>clear_state</code>。
- <code>character_dungeon_permissions</code> 只保留角色级机制状态与旧版本兼容数据。安图恩普通征伐链虽然也使用 <code>0x0005</code>，但属于角色机制进度，禁止迁入账户难度账本。
- 登录时先将同账号旧角色记录按相同 <code>dungeonId</code> 取最大值惰性归并到账户账本，再合并当前角色的角色级机制状态；全量投影和结算增量必须使用同一物理 ID 与同一 clear-state 语义。
- DGN 的 <code>[shared difficult dungeon index]</code> 可用于普通/单人异界 definition 与掉落配置配对，但不是难度权限共享关系。普通异界与单人异界是不同物理副本，不能相互解锁或覆盖难度。
- ownership 分类必须返回显式 <code>Unknown/None/AccountDifficulty/CharacterMechanism</code>，禁止用“非任务图”反推账户级。<code>DungeonPermissionDefinition</code> 必须成功取得 DGN、有效路径、脚本根、正文和 maze；普通账户难度还必须同时具备 WorldMap 物理引用与 DGN 显式难度配置。
- task-exclusive 副本为合法 <code>None</code>；安图恩普通征伐为 <code>CharacterMechanism</code>。缺文件、空/损坏路径、解析失败、WorldMap 无法确认或无难度依据均为 <code>Unknown</code>，不得进入客户端投影、legacy 迁移、progression plan 或账户写入。
- scope policy 不保存第二套长期分类缓存；DGN 与 WorldMap 读取复用各自权威 catalog/index。未知结果不能因一次不完整资源判定在进程期固化为账户权限。
- Network builder 只编码已投影条目，不解析 PVF、不访问数据库，也不决定账户或角色 ownership。
- 必测边界：角色 A 提升后角色 B/新角色登录继承、重登保持、低难度重放不降级、不同账号隔离、普通与单人异界互不传播、旧角色记录归并、task-exclusive 排除、安图恩角色进度不串号，以及 Unknown 不投影、不迁移、不生成 plan、不写账户表。

## 十三、Quest-Dungeon 接入

### 1. 进度事实与 activation

~~~text
Dungeon fact
  -> DungeonQuestBridge
  -> DungeonQuestProgressEvent
  -> QuestObjectiveEvaluator
  -> QuestProgressReducer
  -> QuestProgressApplicationService
  -> QuestRepository CAS + event inbox
  -> QuestNotificationProjector
~~~

规则：

- 任务定义必须有效且存在于本局 QuestRunSnapshot。
- <code>character_active_quests</code> 使用 <code>(character_id, quest_id)</code> 唯一约束和 version CAS。
- 每次接取生成独立 <code>QuestActivationId</code>；活动表、QuestRunSnapshot、CAS、完成删除和 event inbox 都必须携带 activation。
- <code>quest_progress_event_inbox</code> 以 <code>(character_id, activation_id, event_id, event_kind)</code> 去重。放弃后重新接取产生新 activation，旧局事件、旧删除 token 和旧掉落快照不得推进新任务。
- client trigger、server kill、clear-map、seeking item 都进入统一进度入口。
- 地图自带被动对象（<code>[enemy reward item]</code> enemyType=3）死亡事实按房间共享账本去重，任务进度与任务物品掉落必须按死亡时点名册逐参与者扇出（<code>DungeonCombatHandler.FanoutPassiveObjectDeathAsync</code>）：名册在 <code>Created=true</code> 后、首个 await 前经 <code>CaptureParticipantRoster</code> 捕获；逐队员以 <code>ForAffectedPlayer(队员 RunIdentity, 队员房间, 队员角色)</code> 投影事件后各自执行 <code>DungeonActorQuestSync.SyncAsync</code> 与 <code>CheckPassiveObjectDrop</code>。过滤只做身份/在线/run 一致性；Tower 只限制掉落，不限制进度同步。重复上报由账本 <code>Created</code> 语义去重，每次被接受的上报恰好扇出一次；队员侧单点失败不重试，Detached 队员无杀怪式的断线重放。客户端物体死亡报文只带 code 与 0xFFFF 哨兵、不含击杀者身份，服务端不得试图还原击杀者。被动物体发放以 <code>PASSIVE_QUEST_DROP</code> 日志逐次留痕。验证入口 <code>--selftest-passive-object-quest-drop-fanout</code>。
- 禁止 <code>INSERT OR REPLACE</code> 覆盖任务槽。
- 禁止按 slot 盲写 trigger。
- <code>QuestTrigger</code> 封装 packed uint，业务层不得重复手写位运算。
- 事件发生时使用冻结的 QuestRunSnapshot；进本后新接任务不得追溯消费旧局事实。

### 2. FINISH 网络合同与服务端授权

网络层去掉 2 字节 echo 后，FINISH body 必须精确为 8 字节：

~~~text
ushort questId
ushort rewardSelection    // 0xFFFF 表示未选择
ushort completionCount
ushort sentinel           // 固定 0xFFFF
~~~

规则：

- body 过短、过长或 sentinel 错误一律拒绝，不补默认字段，不保留第二份 raw parser。
- <code>completionCount=0</code> 拒绝。普通任务只允许 <code>1</code>。
- 只有 PVF 明确为可重复且 type 为 <code>[seeking]</code>、需求列表能完整解析为 item/count 对的任务，才允许 <code>completionCount&gt;1</code>。未闭环的客户端批量资源类型不得授权。
- 批量上限由服务端在当前 owned <code>InventoryLease</code> 中按全部需求重新计算，不信任客户端 count。
- <code>[seeking]</code> 中 <code>itemId=0</code> 是主虚拟金币槽，不是损坏定义；负 itemId 或非正 count 才是非法。虚拟物品必须通过 <code>InventoryService.TryResolveMainVirtualSlotByItemId</code> 解析，不能伪装成实体掉落。
- 普通客户端 FINISH 必须命中当前活动 <code>QuestActivationId</code>。唯一窄例外是当前日已生成的每日挑战条目：只有账本中存在、remaining 已为 0 且尚未领取时，才允许复用同一 FINISH 奖励事务；任意其他非活动任务仍拒绝。server-only hidden/auto completion 若以后需要，必须使用独立 typed command，不得扩大该例外。

### 3. 奖励定义与选择授权

- QST 奖励先解析为不可变 <code>QuestRewardDefinition</code>，Application Service 和 Projector 不得在 FINISH 时重新宽松切 token。
- 当前显式识别 Item、Title、GrowType、AwakeningType、CreatureEvolution、ExpertJob、SlotExpansion、EventCreatureEvolution、Ridable、EventSkill、HellChallenge 和 CrackOfDimension。未知类型、残余 token、损坏 job/grow/count 或类型不允许的额外字段整份 fail closed，禁止默认降级为普通物品。
- 普通物品奖励只接受完整的 <code>itemId count</code> 或 <code>itemId [job] jobId growType count</code>；固定奖励中的 <code>itemId=0</code> 是金币标记，参数允许为非负值，不创建实体物品。
- selectable 数据存在时策略为 <code>Required</code>，不存在时为 <code>Forbidden</code>；索引必须在按角色 job/grow 过滤后的候选中重新校验。Question Quest 的答案授权与奖励选择分离；正常 A21 选择通过 <code>CmdPacketTypeA21.SET_QUEST_TRIGGER</code> 保存答案，<code>CmdPacketTypeA21.FINISH_QUEST</code> 的 selection 字段通常为未指定值。
- 问答活动 trigger 保存从 0 开始的完整 <code>answerIndex</code>，完成 flag 使用 <code>answerIndex + 1</code>，完成 flag 0 保留为未完成。问答 <code>CmdPacketTypeA21.SET_QUEST_TRIGGER</code> 的命令 echo 后正文为 <code>UInt16 questId + Byte type(0) + Byte answerIndex</code>；最后一个字节不是增减标志。<code>QuestService</code> 保留其完整值，<code>QuestObjectiveEvaluator</code> 校验 <code>answerIndex &lt; answerCount</code> 并按绝对值保存，沿用统一进度事务的 activation/version CAS 和 session owner 复验。活动 trigger 是正常完成的答案来源；只有活动值无法解析时才保留既有 FINISH 显式索引兼容回退，事务内重新加载后必须使用与事务前一致的解析和范围校验规则。
- 当前 A21 客户端依据为 SHA-256 <code>1F8244D3F7309BBE2FDE4299E1863A894F6B28D5707BF01732980585B20B00DD</code> 的 <code>DNF.exe</code> 只读进程内存反汇编：<code>0x00E6CF00</code> 在 <code>0x00E6D770</code>、<code>0x00E6D777</code> 将答案序号初始化为 0，<code>0x00E6D818</code> 每项加一；<code>0x0120F100</code> 把该序号保存为答案记录 ID，<code>0x025039D0</code> 返回选中记录的 ID。<code>0x00E73520</code> 的正常问答路径在 <code>0x00E73634</code> 构造上述 SET 请求，<code>0x00E73671</code> 写 type 0，<code>0x00E73681</code> 写答案 ID，<code>0x00E73686</code> 发送；随后 <code>0x00E736AA</code>、<code>0x00E736AC</code> 指定 completionCount 1、selection 0xFFFF，经 <code>0x00E54080</code> 和 <code>0x0107ED10</code> 发送 FINISH。<code>0x0274D310</code> 与 <code>0x0274D2E0</code> 分别写 2B 和 1B；包名及 opcode 归类统一取自 <code>Network/Core/PacketTypesA21.cs</code>，枚举数值本身不证明上述发送顺序。PVF 前置下标不能单独替代这条客户端证据；客户端 UI 与断线时序仍需实机验收。
- <code>[event creature evolution]</code> 按 <code>displayItemId/targetCreatureId</code> 对解析。Ridable、EventSkill、HellChallenge 和 CrackOfDimension 保留独立原生类别，不得伪装成 item；新增服务端持久效果时必须进入 completion plan，不能只增加 chain type 显示。
- 当前冻结任务目录没有 Premium 奖励；任何未来命中的 Premium grant 在具备同事务激活前必须于 plan 阶段拒绝。账户货币奖励继续通过 typed grant 与任务事务共同持久化，不得生成普通背包物品。

### 4. 完成计划与事务

~~~text
validate activation + definition + reward
  -> lock owned InventoryLease
  -> clone inventory and build immutable completion plan
  -> simulate all required/optional consumption
  -> plan rewards against post-consumption capacity
  -> SQLite transaction
       CAS delete active activation
       apply frozen inventory plan
       apply chain/slot/pet/clear-parent effects
       grant EXP/gold
       SaveDirtyInTransaction
       commit
  -> clear dirty state
  -> QuestNotificationProjector
~~~

- 所需物允许跨多个堆叠槽扣除；预检汇总成功但实际只扣第一槽属于禁止实现。
- 消耗、奖励、金币和经验按同一个 <code>completionCount</code> 缩放，并检查 int32/uint32 溢出。
- 背包容量必须在模拟消费后的库存上规划；背包满、材料不足、奖励定义无效、plan/apply 分歧或 ACK 条目超过 byte 容量时整单拒绝。
- 活动任务删除、奖励物品/金币、完成标记、任务链副作用、经验和 <code>InventoryPersistenceService.SaveDirtyInTransaction</code> 保持在同一 SQLite 事务。
- 请求处理期异常必须恢复受影响实体槽、虚拟槽、待持久化账号货币、宠物装备和新建 detail；不得留下“任务已完成但奖励/消耗不完整”。
- 合法零奖励与无效奖励定义必须区分；无效定义 fail closed，不得提交完成。
- 完成后的前置通知、ACK、奖励通知和 <code>0x0015</code> 后继任务投影由 <code>QuestNotificationProjector</code> 统一排序。
- 当前完成事务只承诺进程内串行、SQLite 原子提交和请求期内存回滚；尚无覆盖全部库存 detail 的跨进程 prepared mutation，因此不得宣称进程崩溃后的通用 exactly-once。

### 5. A21 每日挑战账本、进度与协议投影

- <code>DailyChallengeData</code> 只从当前 A21 PVF 的每日挑战分组和 QST 定义生成候选；先按分组和槽位取候选，再用 QST <code>[level]</code> 的最小/最大等级筛选，最后由 characterId、dayId、group 和 slot 稳定选择，不按旧服任务 ID 硬编码。一次生成计划内已经选中的 questId 必须从后续槽位候选中排除，不能生成客户端显示重复、服务端只能按 questId 命中第一条的不可领取账本。不能只筛分组：A21 第一组覆盖 1-100 级，但同一槽内同时包含不同等级段 QST；忽略 QST 等级会让低级角色领取高级任务经验。客户端与服务端当前同一份 <code>Script.pvf</code>（SHA256 <code>19F5FA85FF73CCE94E299E0902269DE2F0164934128F15B8A7B99249C881BE1A</code>）的 <code>etc/dailychallengetable.etc</code> 恰有 5 个普通 <code>[group]</code>，没有 A12 的 <code>[special challenge]</code>；不得迁入 S4A12 的第 6 个领奖位或特殊进度向量。
- <code>DailyChallengeRepository</code> 是每日挑战持久化 owner。登录通过 <code>DailyResetService</code> 的 <code>daily_challenge_generated</code> 日标记保证同日保留、跨日重建；schema v6 新增单条挑战领奖账本和推荐地下城 source-event inbox，组奖励、进度事件和单条领奖都必须幂等。<code>SqliteCharacterStateRepository.SaveFlags</code> 等通用初始化快照保存不得删除或重写挑战 group/entry/tail 表，否则外键级联会清除 entry claim 和 source-event inbox；教程 flag、选项等无关写入必须保持挑战账本原样。
- 推荐地下城通关进度只由普通权威 settlement 使用稳定 <code>run.GetSettlementSourceEventId()</code> 提交；“推荐地下城击杀任意领主”进度只由 <code>DungeonKillApplicationService</code> 已确认的 canonical actor-death event 提交，并复用其稳定 <code>SourceEventId</code>。后者仅接受 PVF 的 <code>dungeon=-3 / monster=-3</code> 规则、当前等级推荐地下城、最低难度和 <code>monsterType=3</code>；同一冻结队伍事件可按参与者投影，但 <code>character_daily_challenge_progress_events</code> 必须按角色、事件和条目去重后才递减 remaining。
- “完成指定 grade 任务”挑战在普通任务 FINISH 的同一 SQLite/Inventory 事务中递减；客户端 <code>SET_TRIGGER</code> 对该类、推荐地下城通关类和推荐地下城领主击杀类挑战只能取得服务端当前值，不能自行推进。领主击杀发生实际递减或同一已提交事件重试时只投影完整 <code>0x0286</code> snapshot，不发送只属于通关边沿的 <code>0x0287</code>；条目已经完成后的全新领主/通关事件不再重复投影快照。
- 单条挑战 FINISH 只有在当前日账本条目 remaining 为 0 且未领取时授权，并与普通 QST 消耗、奖励、完成 flag、entry claim、领奖后完整挑战 snapshot 和 Inventory 保存同事务提交。成功 ACK 及普通任务奖励/后继投影完成后，在线会话必须先投影完整 <code>NotiPacketTypeA21.CLEAR_QUEST_LIST</code>，再投影 <code>0x0286</code>；不能只依赖重新选角初始化恢复“完成”按钮。QST 奖励仍遵循普通任务公式，例如角色 16 级领取 QST 14561 时，当前 PVF 同时定义物品 10099414×1，并由 questParameter 公式计算 31 Exp。组奖励必须持有当前 session-owned <code>InventoryLease</code>，在领取事务内从 <code>characters</code> 读取账号 ownership 和权威等级后选取奖励档位，不得相信会话缓存等级；当前回滚边界只接受实体背包物品和主虚拟数量，其他奖励类型在具备对应事务回滚/通知前 fail closed。重复领取返回已领取而不重复发奖。当前 A21 PVF 的 group 0 省略 <code>[reward challenge num]</code>，客户端将其解释为 2；服务端不得回退成随等级变化的活动槽位总数，否则客户端显示 2/2 时仍会收到 Incomplete。显式配置了该字段的其他组继续使用 PVF 数值。旧生成器遗留的“QST 最低等级仍高于角色等级”账本在下一次初始化重建；角色正常升级后低于当前等级的同日任务仍保留，避免抹掉合法进度。

- 每日挑战接入不得修改无关副本 wire。<code>DUNGEON_INFO</code> 的 bossX/bossY 必须继续投影当前主线已验证的领主坐标；不能为通过陈旧 SelfTest 把所有副本回退成 <code>FF/FF</code>。测试预期与当前协议实现冲突时，应按当前抓包/已合入修复更新测试。
- <code>NotiPacketTypeA21.DAILY_CHALLENGE</code> 投影完整 snapshot，条目顺序固定为 remaining、target。2026-08-21 对 SHA256 <code>1F8244D3F7309BBE2FDE4299E1863A894F6B28D5707BF01732980585B20B00DD</code> 的 A21 <code>DNF.exe</code> 做只读进程内存反汇编，<code>0x0286</code> 注册 handler <code>0x01170F00</code> 依次消费 level、group 列表、三 UInt32 条目和领奖 flag；其状态更新函数 <code>0x00884FB0</code> 对 flag 向量执行 <code>length == 5</code> 硬校验，不等于 5 时直接拒绝初始化。handler 随后立即更新 UI 并返回，A12 的第 6 个 special flag 与 tail-count/tail-id 列表均不得迁移。推荐地下城发生实际递减时，先发完整 snapshot，再发 <code>NotiPacketTypeA21.DAILY_CHALLENGE_CLEAR_DUNGEON</code>；<code>0x0287</code> 注册 handler <code>0x01162BA0</code> 只消费一个 little-endian UInt32 并不解释其值，因此服务端发送稳定的不透明 completion token，不把 dungeonId 或累计次数写成已确认语义。
- 同一 A21 二进制将 CMD <code>FINISH_QUEST</code> 注册到 <code>0x01140810</code>。成功分支先把 Exp 后的 UInt32 局部值初始化为 1，再从包中覆盖读取，并在 <code>0x011417D7</code> 把它连同 questId 投影到完成任务事件，因此该字段是经过校验的 <code>completionCount</code>，不是金币或保留值。普通完成通常写 1；金币仍只通过后续 <code>itemId=0</code> 奖励记录投影。服务端权威挑战进度已在同一事务推进，随后客户端产生的 <code>SET_TRIGGER</code> 只能回读，不能重复计数。
- A21 <code>FINISH_QUEST</code> 的 Seeking/0x19 成功分支在 <code>0x01140B3D</code> 读取 consumed count 和 7 字节消耗条目，在 <code>0x01140C77</code> 另读一个 chainType；chain 为 0 后才在 <code>0x01140D6A</code> 读取 inserted reward count。即使消耗数量为 0，chainType=0 也必须单独写出；否则首个奖励数量会被解释为 chain（例如 1 会进入转职/技能页分支），造成越界消费和客户端闪退。
- <code>0x0287</code> 没有 ACK，transport 写入成功不能证明客户端 UI 已消费。自动回归覆盖 body 宽度、快照顺序、日切、重复事件、FINISH 领奖和 owned lease；客户端动画、断线瞬间与重连 UI 仍需当前 A21 实机验证。

## 十四、新版背包与副本物品

### 1. 在线真源

在线物品真源始终是当前 session 拥有的 <code>InventoryLease -> InventoryService</code>。

禁止：

- 直接写新背包 SQL。
- 绕过 lease 构造第二份在线库存。
- 使用旧 DTO 或旧库存服务。
- outbox 直接修改物品表。

### 2. 统一入口

- 副本拾取和自动任务材料进入 <code>DungeonItemAcquisitionService</code>。
- 批量发放使用 <code>InventoryRewardGrantService</code>。
- 保存使用 <code>InventoryPersistenceService</code>。
- 任务道具按元数据进入任务道具栏。
- 自动任务材料只发送变化槽位 <code>0x000E</code>，不为每次掉落发送完整 <code>0x023F</code>。

### 3. 奖励幂等边界

当前库存奖励具备 owned lease、批量 plan/apply、事务内 SaveDirty 和单进程 effect ledger。

任务 FINISH 额外具备请求期 completion plan 与内存 rollback snapshot；规划库存必须复制实体槽、虚拟槽、list param 和 <code>PendingHappyTokenCeraGrant</code>，否则容量模拟与实际应用状态不一致。该 snapshot 只服务当前请求失败回滚，不等同于持久 outbox。

当前库存奖励不具备通用的跨进程 exactly-once。原因是新版背包尚未提供覆盖主槽、avatar/creature detail、虚拟槽和 dirty 集合的通用 prepared mutation snapshot/rollback token。

在该能力出现前，Card、Quest、DeathTower 库存奖励不得强行加入持久 replay。

## 十五、持久 effect outbox

### 1. 已支持 effect kind

当前只支持：

- <code>settlement-experience-grant</code>
- <code>suitable-dungeon-lucky-star</code>

二者的 SQLite mutation 与 outbox commit 位于同一事务。

### 2. 状态

~~~text
Pending -> Reserved -> Committed
                   \-> Failed
未知 kind/version -> DeadLetter
~~~

记录包含 payload/result version、lease owner、lease timeout、attempt count、last error 和 committed time。

### 3. 恢复

角色选择时调用 <code>RecoverCharacter</code>：

- 已 committed 的 effect 读取持久结果，不重复修改。
- 可恢复记录重新领取 lease 并执行。
- 输入与原 payload 不一致时拒绝。
- 未知 kind/version 进入 DeadLetter。
- 恢复使用 <code>created_at + effect_kind + effect_scope + scope_target + source_event_id</code> 严格全序的 keyset 分页；不得使用 offset，也不得省略 effect 主键中的 scope。
- 每次调用同时受页数和单调耗时预算约束；当前默认每页 64 条、最多 4 页、最多 3 秒。返回扫描页数、扫描记录数、剩余数量、终止原因和最后扫描游标，选角入口在仍有 backlog 时必须记录诊断日志。
- 单项失败不得阻塞同页后项和后续页；本轮游标越过失败项继续扫描，下一次恢复从头重新读取可恢复集合并只重试仍为 Failed/Pending/过期 Reserved 的记录。
- 预算耗尽后的剩余项保留在 outbox，不能伪装成恢复完成；当前没有选角后的后台 drain，剩余项等待下一次显式恢复调用。

### 4. 不支持的承诺

- 库存奖励未覆盖。
- 无 ACK 网络通知未覆盖。
- START_MAP、开门、Buff 和结算 UI 只能作为可重建投影或 at-least-once 发送。
- 内存 journal 不是持久 event store。

## 十六、Timer、结束局与新局隔离

### 1. Timer

新增或重构的参与者级副本延迟使用 <code>ClockService + RunTimerRegistry</code>。当前参与者级生产 key 包括：

- <code>SettlementCardAutoFlow</code>
- <code>CombatDeathRespawn</code>
- <code>GentInfiltrateTimeout</code>
- <code>TournamentRewardAutoSelect</code>
- <code>DeathTowerRankingToReward</code>、<code>DeathTowerRewardToEplp</code>、<code>DeathTowerReturnToTown</code>
- <code>BloodAltarRankingToReward</code>、<code>BloodAltarRewardToExit</code>、<code>BloodAltarReturnToTown</code>、<code>BloodAltarSettlementRetry</code>

<code>RunTimerRegistry</code> 是 timer registry 类型，不单独决定 owner。默认参与者级 owner 是单个 <code>DungeonRun</code>；祭坛的 <code>BloodAltarDungeonRuntime.Timers</code> 是物理 <code>DungeonInstance</code> 的共享 owner，持有 <code>BloodAltarWaveSchedule</code>、<code>BloodAltarDifficultySelection</code> 和 <code>BloodAltarFinalRound</code>。需要共享 timer 的新机制必须先定义 Instance/Room owner、唯一 registration 和 fan-out，禁止为每个参与者复制一份世界回调。

安图恩运行时 timer 由 <code>RaidHandler</code> 以 <code>RaidSnapshot.InstanceId</code> 为攻坚队共享 owner，通过既有 <code>ClockService</code> 保存绝对 UTC deadline。注册键同时包含 instance、timer type、dungeon 和 purpose；callback 在写状态或发包前复验 instance、phase 和 version。成员 detach、重连或离开仍存活的攻坚队时不取消共享 timer；重连只按原 deadline 重投剩余时间，不重新开始倒计时。阶段结束、解散和同 RaidId 的实例替换必须取消实例/阶段 registration，使旧 callback no-op。该 registry 是进程内运行态，不承诺跨服务端重启恢复。

timer key 至少由 mechanism 和 purpose 构成。回调捕获 Run identity、Room identity（房间行为）和 SourceEventId。

玩家参与级 timer 必须保存绝对 UTC deadline，并显式声明 detach policy：

- <code>Cancel</code>：网络断线时终止，不允许重连恢复。
- <code>SuspendUntilResume</code>：网络断线时取消旧 handle、推进 ticket generation，但保留原 deadline。

可恢复 timer 使用 <code>Begin(key, deadlineUtc, policy)</code> 注册，并用同一 ticket 挂接绝对时间调度。网络 detach 只调用 <code>SuspendForNetworkDetach</code>；真正 EndRun、换局和主动取消仍调用终止型 cancel。重连必须在业务投影恢复后调用 <code>TryResume</code>，以新 ticket 和原 deadline 重排；deadline 已过期时进入立即到期调度，不得重新开始完整时长。

目标合同是回调只投递 typed 事件，不直接信任旧 session 状态；当前参与者级生产 callback 仍有 coordinator 捕获 session 的过渡实现，祭坛实例级 callback 不依赖断线参与者继续在线。所有 callback 必须在每个不可逆动作前复验 Instance/Run identity、ticket generation、room identity 和当前 attachment。实例结束由 <code>DungeonInstanceMechanismRuntimeSet.OnInstanceEnding</code> 取消祭坛共享 timer；取消 handle 不能召回已经由 <code>ClockService</code> 出队的异步 callback。通用 typed timer event dispatcher 和跨进程 timer 恢复均未完成。

### 2. EndRun

所有退出路径进入：

~~~text
EndRun(reason, expectedRun)
~~~

原因包括 ReturnToTown、DeathRespawn、TutorialExit、PartyLeave、SessionTeardown、CharacterSwitch 和 ReplacedByNewRun。

<code>CombatDeathRespawn</code> 到期不是无条件 EndRun。死亡入口先通过 typed death-deadline decision 询问机制：没有专用策略的普通副本返回 <code>ReturnToTown</code>，Tournament 返回 <code>PresentTournamentRewards</code> 并取消死亡回城 timer，失效 run/ticket 返回 <code>Ignore</code>。Handler 只能消费决定，禁止识别 Tournament dungeon ID。复活币在 deadline 前取消同一 timer 后继续本局，不得提前冻结失败结果。

组队过门由当前物理房间的参与者共同决定，不能仅因 <code>CmdPacketTypeA21.MOVE_MAP</code> 的发送者已经死亡而拒绝整个队伍。客户端的死亡队长仍可能代存活队友发送请求。Handler 从 InstanceRegistry 冻结同房间 roster，并排除断线、非 Active、旧 run identity 和已换房的会话；<code>DungeonInstance.CanParticipantMoveMap</code> 在生命状态锁内确认发送者在该名单中，且至少一名已登记参与者存活。不得用整个副本中的异房间参与者、未知 identity 或旧 generation 代替此条件。通过后沿用原 START_MAP、机制校验和加载屏障，死亡标记保持不变；单人死亡、全员死亡和已提交团灭仍拒绝过门。

死亡条件导致的过门拒绝必须向当前 run 发送 <code>CmdPacketTypeA21.MOVE_MAP</code> 失败 ACK，正文为 <code>result UInt8(0) + error UInt8(0)</code>，不能静默返回。当前 A21 客户端证据为 SHA-256 <code>1F8244D3F7309BBE2FDE4299E1863A894F6B28D5707BF01732980585B20B00DD</code> 的 DNF.exe 只读代码：<code>0x00C32C1C</code> 发送过门请求后，<code>0x00C32C24</code> 将地图对象 <code>+0x11EC</code> 置 1；<code>0x00C32242</code> 检查该位并阻止重复请求。失败 ACK 消费函数 <code>0x01105E10</code> 在 <code>0x01105E3C</code> 调用 <code>0x00C2E740(0)</code> 清除此位，error 0 走通用失败分支；<code>NotiPacketTypeA21.DIE_STATE</code> 消费函数 <code>0x0114F420</code> 的复活路径不会清除此位。生命判定、团灭 generation 和真实 TCP ACK 由 <code>--selftest-party-death-map-move</code> 覆盖；多客户端过门动画及死亡跟随仍需实机验收。

结束顺序：

~~~text
validate expected identity
  -> 在同一生命周期锁内进入 Ending 并 compare-and-clear CurrentRun
  -> 逐项执行具名 cleanup checkpoint
     (registry / timer / exp / tower / mechanism / pet)
  -> finally 进入 Ended
  -> project town state only if generation still matches
~~~

每个 cleanup operation 使用单局稳定 end event id 和 effect ledger。已提交项在同一 run 对象上重放为 no-op，某一项失败不得阻止后续项或领域终态。旧结束流程不得把已经建立的新 <code>CurrentRun</code> 置空。

当前 <code>EndRunAsync</code> 在执行 cleanup 前已经 compare-and-clear <code>CurrentRun</code>，并在 finally 将旧 run 标为 Ended。失败 checkpoint 只保留在该内存 run 对象中；自测或显式持有该对象的调用可以定向重跑 executor，但生产没有 failed-cleanup scheduler，也不会从已置空的 <code>CurrentRun</code> 自动找回旧 run。进程退出或旧对象丢失后无法恢复。

组队副本中的参与者通过 <code>GIVEUP_GAME</code> 主动回城时，实时 Party 的成员移除必须保留进本时冻结的 <code>PartyId</code> 和所有存活成员槽位；离开的成员若为队长，由最低已占槽位在原 Party 代际内接任。不得在仍有参与者留在原 DungeonInstance 时压缩槽位或创建替代 PartyId，否则客户端持有的副本、地面掉落和队伍投影会跨代际失配。城镇中的显式 <code>LEAVE_PARTY</code> 继续使用普通离队语义，不继承这项副本内约束。

## 十七、断线 attachment 与重连

### 1. attachment 状态

~~~text
Active -> Detached -> Active
                  \-> Cancelled
                  \-> Expired
                  \-> Terminated
~~~

默认 hard timeout 为 10 分钟，idle timeout 为 2 分钟。

### 2. 协议

- <code>NOTI 0x02A7 DISCONN_DUNGEON_INFO</code>：
  <code>int32 partyId + int32 reservedInt32 + byte uiState</code>。
- 第二个 int32 当前保持命名 <code>reservedInt32</code>，值为 0，不猜测业务语义。
- <code>NOTI 0x02A8/0x02A9</code>：participant userId 投影。
- <code>NOTI 0x02AA REJOINABLE_DUNGEON</code>：<code>int32 partyId</code>。
- <code>CMD 0x02D7</code>：<code>int32 partyId + int32 targetParticipantUserId</code>。
- <code>CMD 0x02D8</code>：<code>int32 partyId</code>，取消重连。

### 3. 应用流程

1. Registry 按 account、character、participant、party 和 generation 查候选。
2. Coordinator 为当前 session 建立 offer。
3. 接受/取消请求通过 per-offer operation gate 串行。
4. 接受时先恢复 registry attachment，再恢复实时队伍、离城并挂接 run。
5. 实时队伍恢复失败时只回滚 registry resume；run attach 失败时回滚已恢复的 party 和 registry。离城是会话投影，失败只记录日志并继续，不存在可逆的 town 领域事务。
6. 成功挂接后，participant effect 恢复失败不会撤销合法 attachment；未完成 journal 保留到下一次有效重连，当前请求记录错误后仍返回重连成功。
7. 恢复顺序固定为 participant kill、participant clear、pending SpecialDungeon effect plan、DeathTower settlement、pending settlement presentation、Blood Altar、Tournament、Card timer、death-respawn timer、Gent timer。Blood Altar 先由 pending presentation 补建 participant settlement，再按当前 phase 重投专用 UI 和恢复原 deadline；活动波次从实例 schedule/actor 快照补投，不重开轮次。Tournament Champion 若发现所有启用奖励均已提交，必须以该 run 的稳定 settlement source event 恢复唯一 clear pipeline；Eliminated 只恢复失败终止 checkpoint，不创建 clear fact。presentation 重投若已重建 Card timer，后续 timer resume 必须 no-op。
8. 重复接受通过 registry generation 与 per-offer gate 收敛，不得重复挂接、恢复队伍或离城。

### 4. 当前限制

- 只支持原 <code>PartyManager</code> 队伍仍存在的参与者恢复。
- 全队同时断线导致实时队伍解散时不能恢复。
- 无有效 PartyId 的单人局不能恢复。
- Registry 和物理实例仍在进程内，服务端重启后不能恢复。
- participant kill/clear、SpecialDungeon plan、pending presentation、DeathTower/Blood Altar/Tournament runtime 与奖励 checkpoint、timer checkpoint 都依赖原 Instance/Run 仍在 registry 中；它们不是 durable attachment saga。

这些限制必须在 UI 和运维说明中明确，不得宣称“所有副本均支持跨重启重连”。

## 十八、特殊地下城机制

### 1. Definition/Runtime 分离

- <code>SpecialDungeonDefinitionCatalog</code> 在 GameWorld 解析 PVF/ETC。
- <code>SpecialDungeonRuntime</code> 只接收冻结 Definition。
- Runtime 不读取 PVF，不修改共享 Definition。
- <code>SpecialDungeonModule</code> 只保留单局 transition，不再承担 tokenization。

### 2. 应用与通知分离

~~~text
typed DungeonCommand / lifecycle fact
  -> SpecialDungeonMechanismApplicationService
  -> SpecialDungeonEffectIntent
  -> SpecialDungeonEffectRouter
  -> SpecialDungeonNotificationSender
~~~

Application Service 在锁内只改变状态和生成 intent。Router 在锁外按顺序执行 I/O。Sender 只发已确认协议。

当前物理位置必须保持清楚：<code>SpecialDungeonMechanismApplicationService</code> 和 plan journal 位于 <code>Game/Dungeon</code>；<code>SpecialDungeonEffectRouter</code> 与 <code>SpecialDungeonNotificationSender</code> 位于 Network。<code>SpecialDungeonNotifier</code> 只做兼容编排，不拥有另一份 runtime。

一次性机制效果必须进一步满足：

- runtime transition 与 effect plan 登记处于同一段 <code>run.SyncRoot</code> 短临界区；锁内禁止 await、发包或持久化。
- plan 保存稳定 operation、原始 <code>DungeonEventEnvelope</code> 和深拷贝后的有序 typed intents；不得在重试时根据已消费 runtime 重新生成效果列表。
- 每个 plan item 复用 <code>DungeonEffectLedger</code> 执行 <code>reserve -&gt; execute -&gt; commit</code>；失败标记为 <code>Failed</code>，重试跳过已 committed 前项，从首个失败或未提交项继续。
- monster kill 使用 canonical <code>SourceEventId</code>；单局命令和条件召唤使用稳定 operation；EndRun 清 Buff 使用稳定 end event id。
- START_MAP gauge、minimap 等可重建状态属于纯投影，不得伪装成一次性消费计划。
- 旧 run、旧 generation 或已失去 run ownership 的 session 必须 fail closed，不得执行 pending plan。
- 当前 plan journal 为进程内恢复能力；无协议 ACK 的投影不得据此宣称 exactly-once，服务重启后也不能恢复。

### 3. 接入原则

- 遗忘之森、时空裂隙、陷落的村庄、黄金王、特快列车、哈尔特山等机制以 PVF/ETC 词条触发。
- 赫拉斯研究所使用 TimeSpiral 配置和共享房间事实。
- 斯洛特发电站复用条件目标、召唤、开门和 ClearIntent。
- 安图恩普通征伐使用独立 application/repository/sender，不与 raid 混用。
- 黄龙、青龙、黑龙大会使用第十八章的独立 Tournament definition/runtime，不并入按图分支的 <code>SpecialDungeonNotifier</code>。
- 无限的祭坛、极限的祭坛使用第十八章的独立 Blood Altar definition/runtime；守护者祭坛属于暂不启用范围。
- 不得按显示名或单个 dungeon/monster/item ID 复制机制。

## 十九、专用子系统分层

### 1. Card

- <code>DungeonRun.Settlement</code> 保存卡牌计划、选中槽、已发放标记、pending presentation 和 Card timer 状态；展示、预留与发放必须复用同一份 <code>CardRewards</code>。
- <code>CardRewardRules</code> 只负责选牌、effect id、reserve 条件和完成状态投影。
- <code>CardRewardService.Deliver</code> 通过 <code>DungeonPersistentEffectApplicationService</code> 在 session-owned <code>InventoryLease</code> 上执行 durable card effect；同一 SQLite 事务包含付费金币扣除、可直接入包奖励、一次 <code>SaveDirtyInTransaction</code>、Devil Contract 次数和 effect result。
- 普通物品仅在批量规划返回 <code>InsertPlanFailed</code> 时转入 transaction-bound 永久系统邮件；金币仍直接进入虚拟金币槽。邮件成功才允许提交 card effect，邮件失败或 plan/apply/persist 失败时恢复在线背包并把 outbox reservation 标为 Failed，Coordinator 只在 durable <code>Committed</code> 后投影 run 状态和真实槽位更新。
- <code>CardRewardCoordinator</code> 负责客户端命令、展示 gate 和 Card timer；<code>CardRewardNotificationSender</code> 只负责协议。

Card 的库存、邮件和 effect result 已在 persistent effect outbox 的同一事务内闭环；重复执行读取已提交结果，不重复发奖或发信。run 内存 effect 和客户端投影仍属于进程内状态，事务提交后到 run journal 投影之间的进程退出不能保证当前局 UI exactly-once；发包失败也不会回滚已持久奖励。

### 2. DeathTower

- <code>tower of boss</code> 复用塔的 stage、actor UID、run 生命周期与库存事务边界；<code>DungeonFile.RandomTowerStages</code> 保留各次重复的 <code>tower stage</code>、候选地图及权重，<code>DeathTowerData</code> 冻结只读池，<code>DeathTowerSession</code> 建局时抽取并冻结整局地图。缺失、乱序、零权重或负权重必须拒绝，不得用第一张图替代随机配置。
- 领主之塔的 INFO/MAP/REWARD/EPLP 使用 <code>NotiPacketTypeA21</code> 中对应的 BOSS_TOWER 类型，INFO 是 8B，MAP 是 11B 头、14B actor 行和空的初始场景物品段，REWARD 必须包含客户端读取的八组物品；不发送死亡之塔排行包。字段依据当前 CN A21 客户端 SHA256 <code>1F8244D3F7309BBE2FDE4299E1863A894F6B28D5707BF01732980585B20B00DD</code> 的 <code>0114E590/0115BA20/01147910/01147C00</code>，stage command 仍沿用既有塔命令。
- 领主之塔只有权威 blocking actor 全部死亡才可清层；未知 actor、重复清层和迟到的开战包不能跳层或撤销清层。普通怪物掉落、拾取和消耗品走真实背包服务，不进入死亡之塔临时库存。门票与次数继续走 <code>EntryAdmission</code> 和既有入场次数服务，不按 ID 直接扣物品。
- 领主之塔结算读取 <code>etc/global_bosstower.etc</code>，按已完成楼层计奖励，首层未清死亡为零完成层。复用当前塔结算 gate、事务和返城 timer，保留其既有恢复边界；新协议的客户端入场、层间推进和最终奖励需实机验收，不能只凭自测宣称闭环。
- <code>DeathTowerSession</code>、stage models、map loader 和塔内 inventory 是独立 definition/runtime。
- 塔会话创建时冻结选图 cohort 与当前玩家的非零 UID；最终楼层 actor 列表截取到 wire 容量后，由 <code>DeathTowerSession.AssignMonsterSequences</code> 一次性分配连续编号，整段避开玩家 UID。同一塔会话内单调分配、不跨层回收；耗尽 UInt16 空间时拒绝生成，不得回绕或下发部分编号。分配必须先于掉落来源绑定、战斗房间同步与协议投影，三者消费同一份编号；普通怪物、固定 APC 和随机 APC 不得独立计号。
- 塔类建局仍使用 <code>DungeonRun</code> identity 和 EndRun，但击杀在 <code>DungeonKillApplicationService</code> 的 tower 分支处理，不进入普通房间 participant kill journal。
- 楼层推进和最终结算当前由客户端 stage command 进入 <code>DeathTowerCoordinator.HandleStageCommand</code> 驱动；<code>commandType=2</code> 会标记楼层完成，最后一层再通过 <code>tower.TryBeginSettlement</code> 做当前塔会话内防重。它不经过普通 Boss endpoint、服务端 Encounter 完成事实或普通 clear pipeline。
- <code>DeathTowerSettlementService.Grant</code> 先在 SQLite 事务中提交经验，再在 owned inventory lease 中发金币和物品；这两部分不是同一个原子事务。当前实现没有 Card 式完整库存快照，也没有 persistent effect outbox。
- 结算通知在奖励处理后发送，发送异常只记录日志，不回滚已提交经验或库存状态。
- <code>DeathTowerPacketBuilder</code> 只负责塔协议。
- <code>NotiPacketTypeA21.START_DEATH_TOWER_MAP</code> 必须按当前 A21 客户端布局投影：<code>UInt16 stage + UInt32 seed + UInt32 mapId + Byte monsterCount</code>，随后是每怪 <code>14B</code>、<code>Byte itemCount</code> 和每物品 <code>18B</code>。2026-08-23 对 SHA256 <code>1F8244D3F7309BBE2FDE4299E1863A894F6B28D5707BF01732980585B20B00DD</code> 的 A21 <code>DNF.exe</code> 做只读进程内存反汇编，<code>0x008F</code> 注册 handler <code>0x01159850</code> 明确以 <code>UInt32</code> 消费 mapId；不得迁移 86JP 的 <code>UInt16 mapId</code> 布局。mapId 缩成 2B 会让客户端把怪物计数拼入地图编号，并将首个怪物字段误读为零怪物，表现为黑屏并立即上报清层。

因此 DeathTower 当前是“专用链路已隔离”，不是“已并入统一 clear/settlement 恢复合同”。新增塔机制必须沿该专用 owner 修复，不能回落到普通 Boss endpoint 猜测；后续若迁入统一 ledger，必须先解决经验与库存的跨边界原子性。

### 3. AntonNormal

- <code>AntonNormalConquestApplicationService.TryApplyClear</code> 从当前图生成“当前完成、下一图解锁、预览图显示”批量更新。
- <code>SqliteCharacterStateRepository.ApplyDungeonPermissionBatch</code> 在同一 immediate SQLite 事务内执行 monotonic upsert、重读完整权限并提交；同一通关的多项权限不会再分三次独立写入。
- <code>AntonNormalConquestNotifier</code> 校验当前 session/run 后调用 application，再由 <code>AntonNormalConquestNotificationSender</code> 投影协议。
- DB 已提交但本次通知失败时，不回滚征服进度；下次进入选图界面由 <code>RestoreBeforeSelectAsync</code> 从角色权限重建完整状态。通知本身无 ACK/outbox，不承诺 exactly-once 动画投影。
- 普通征伐是角色级 <code>CharacterMechanism</code> 权限；账户难度共享不得覆盖它。普通征伐与攻坚团本使用各自的状态与奖励流程。

#### 安图恩攻坚团本

- <code>RaidManager</code> 与 <code>RaidAggregate</code> 是攻坚队成员、团长、编队、准备名单及阶段状态的真源；<code>PartyManager</code> 继续拥有实际四人队伍。联动修改必须通过带当前成员与会话校验的 commit 回调完成，不能只改团本展示名单或只改普通队伍。
- 申请加入必须建立待审批请求，只有当前团长的有效确认才能加入。申请绑定双方 session、角色、团本实例和团长版本，超时、拒绝、离线或版本失效均不能隐式加入。团长转让和实时编队需要校验 <code>InstanceId</code>、<code>LeadershipVersion</code> 与 <code>AssignmentVersion</code>。
- 退出普通队伍后，角色仍可保留在攻坚队中，但必须成为未编队单人，团队目录和成员列表同步该状态，不自动补入其他小队。发起下一阶段时才按当前有效成员和实际队伍发起准备；准备过程冻结名单，旧 <code>PreparationGeneration</code> 的应答不得推进新阶段。
- 城镇加载、离开赛利亚房间和团本返城时，先完成当前会话的场景成员投影，再发送 <code>NotiPacketTypeA21.RAID_USER_FINISH_LOAD</code>、团长人物上下文及团本对象/目录。当前会话的团本刷新不得等待无关玩家的慢列表广播；返城续段逐次复验角色对象、run generation 和团本实例。购买物品后仅对仍为原角色的会话刷新门票状态。
- 选角色的 <code>EventInfoBodyBuilder</code> 保留已配置活动并保证存在团本入口活动；已有该活动时不得重复添加，总记录数遵守 UInt16 上限。协议包名与编号使用 <code>PacketTypesA21.cs</code>；成员列扩展只对明确协商版本的会话发送，原生客户端保持对应基本布局。
- 总攻坚倒计时到期后必须失败并解散攻坚队，清理成员索引和在线投影。攻坚与阶段准备 timer 绑定团本实例及当前版本；旧实例、旧阶段、旧准备代际的回调不得推进当前攻坚队。该状态和计时仍为进程内能力，不承诺跨服务端重启恢复。
- 门票消费使用当前 session-owned <code>InventoryLease</code> 与 <code>RaidEntryCostCommitService</code> 的全队事务，任一成员失败时回滚全部扣票；奖励通过 <code>RaidRewardCommitService</code> 及现有在线库存提交边界落库。失效 lease 不能扣票或发奖；发包失败不能据此重复已提交奖励。
- 二阶段 <code>squad_item</code> 在已识别的纯金牌奖池中将金牌总权重调整至 100%，保留各金牌子池的相对权重；混合或无法识别的奖池保留资源原权重。四人牌使用实际奖励物品及对应图标标志。牌面金币数量遵守原生 UInt16 宽度：12 万金币正常全额到账时牌面显示 65,535，额外 54,465 和合计 120,000 由通知说明；达到携带上限时所有提示依据实际提交金额，不能宣称未到账的金币已发放。
- 团本地下城通过现有 <code>DungeonRewardPolicyData</code> 分类禁用随机精英，保留原始普通怪、固定精英和 Boss 数据。团本/团长聊天仅投递至同频道的当前有效成员，团长模式需校验当前团长权限；实际发送人物上下文和消息前均复验当前会话及接收者黑名单，不得绕过普通聊天的屏蔽规则。
- 自动化验证入口为 <code>--selftest-a21-raid-protocol</code> 和 <code>--selftest-raid-persistence</code>，包含协议布局、真实处理器的多会话审批与刷新、阶段推进、退队单人、奖励重复点击和事务回滚。客户端按钮、弹窗、动画及跨网络条件的视觉行为仍需实机确认。
- 安图恩团本 <code>[raid phase clear]</code> 任务按 PVF 中的三元组“阶段索引、所需次数、范围”解析；当前范围值必须为 <code>-1</code>，每阶段剩余次数占一个 9 位触发器通道。团本成功完成阶段奖励状态提交后，仅以该阶段冻结的合格成员名单逐角色提交任务进度；团本 <code>InstanceId + PhaseIndex</code> 生成稳定事件 ID，经任务进度 inbox 按任务 activation 去重。失败阶段、未参与成员和客户端 <code>SET_QUEST_TRIGGER</code> 不得直接增加该进度。旧版已接取、仍为错误初始值 <code>1</code> 且没有此任务阶段事件记录的任务，在首次有效阶段完成时修复初始值，再递减对应阶段；通知失败不得重发已提交进度。聚焦自测入口为 <code>--selftest-anton-raid-phase-quest</code>。
- 连续副本的 group、顺序、完成态、入口前置、受限怪物和 clear reward capability 统一来自 <code>etc/sequential_dungeon_info.etc</code>，由进程级 <code>SequentialDungeonDefinitionCatalog</code> 解析并按 primary、entrance、rewardable 等语义索引。生产逻辑不得按 243-247、key 41 或固定 route mask 重新维护一套范围；能力索引冲突必须 fail closed。当前 PVF 恰好把安图恩觉醒解析为 group 41、顺序 243-247、完成态 3 和四个入口前置，这些数值只用于资源兼容性断言。
- 角色每日进度由 <code>AntonAwakeningDailyProgressService</code> 统一拥有，持久化复用 <code>character_dungeon_permissions</code> 和动态日标记 <code>sequential_progress_v1:{groupKey}</code>，不新增 schema。登录恢复、连续副本查询、通关写入和入口准入均把 catalog 中同一份 Definition 传给 Repository，并在一个 immediate SQLite 事务内用单一 UTC 锚执行 <code>DailyResetService</code> 日切；北京时间 06:00 后首次访问只删除当前角色、当前 Definition 的 dungeon 行并领取新日标记。旧 <code>anton_awakening_progress_initialized</code> 仅在 catalog 能唯一识别同一安图恩 Definition 且旧日锚仍有效时迁移，不能继续充当生产真源。
- <code>SEQUENTIAL_DUNGEON_INFO</code> 的 <code>routeMask</code> 按 Definition 中有序 <code>PrerequisiteDungeonIds</code> 分配 bit；只有达到 Definition 的完成态才置位，解锁态和预览态不得充当通关条件。任一 Definition 内目标副本的入口前置是其在有序 <code>DungeonIds</code> 中之前的完整前缀：首图无前置，后续每图均要求逐一完成此前所有图，禁止只对最终图应用整组前置。入口预检必须逐参与者重读当日状态并按 Definition 顺序列出确切缺失前置，任一队员缺项时整队用 <code>MissingPrerequisite(memberSlot)</code> 拒绝；rewardable 最终阶段保留原生 <code>00-07-00</code>，普通非 rewardable 阶段使用静默 <code>00-09-00</code> 后跟 <code>SERVER_NOTICE_MESSAGE</code>。玩家通知必须从当前 PVF DGN <code>[name]</code> 解析目标与全部缺失前置，不能显示内部副本 ID；任一名称不可用时整体回退到不含 ID 的通用提示，ID 仅保留在结构化事实和诊断日志中。该路径不得冒充 <code>00-AD-slot</code> 的次数/权限失败；协议选择只能依赖结构化失败事实和 catalog capability，不得解析 <code>FailReason</code>、维护 ID/名称硬编码表或按副本 ID 特判。检查必须早于迷宫和背包租约获取、门票/次数准备及所有成本提交；日切不主动刷新已打开 UI，但旧 UI 发起进入仍必须由服务端 fail closed。当前 A21 客户端已实机确认静默拒绝与 PVF 名称通知组合能正确展示失败队员、全部缺失前置和目标地下城。
- 配置在 Definition <code>monster_id_list</code> 中的怪物使用 <code>SequentialDungeonDailyLootGuard</code> 按 <code>characterId + groupKey + monsterId</code> 独立门控，counter key 为 <code>sequential_monster_drop_v1:{groupKey}:{monsterId}</code>，日界沿用北京时间 06:00。同组不同 monster 互不屏蔽；掉落一旦成功生成任意 item 或正金币就立即计数，不等待捡取或通关。无 item 且无金币时不占次数；counter 提交失败必须回滚本次已注册 item，并 fail closed 返回空结果。退出重进不能绕过已生成掉落的 monster 次数，clear-time 不再写掉落标记。
- 特殊奖励先从 Definition 的 <code>[clear reward item]</code> 取得外层 <code>weight / rewardGroupItemId / state</code>，再加载对应 <code>stackable.lst</code> 条目的 <code>[int data]</code>（当前资源类型为 upgradable legacy），按内层 <code>itemId / weight / count</code> 抽取最终物品和数量。所有外层组和内层池必须在第一次随机前完整校验；缺文件、类型错误、空池、非正权重/数量或溢出均 fail closed。每个冻结参与者独立消费一次外层和一次内层 <code>ServerRandom</code>，最终 <code>itemId / quantity / PVF state</code> 冻结在 <code>DungeonInstance.Mechanisms.AntonAwakeningReward</code> 的 clear-event 计划中，重试不得重抽，也不得让全队复用一次随机结果。
- 普通翻牌拥有独立的共同绝对 deadline 和实例级屏障。每个当前有效参与者必须达到 <code>FreeCommitted</code>，并在 deadline 前完成 <code>PaidCommitted</code> 或在 deadline 时原子转为 <code>PaidSkipped</code>；deadline 前已经原子占位的付费请求允许完成，deadline 后的新付费请求必须在扣费前拒绝。断线参与者不阻塞仍有效成员，同一 run 恢复时失效旧付费占位并按原 deadline 续接；手动选择免费牌只取消普通 auto-flow timer，不得取消特殊屏障 deadline。
- 屏障满足后只构建一次按冻结 party slot、userId 排序的多成员 <code>0x0319</code>，再构建一次正文为四个零字节的 <code>EXERCISE_MODE_CLEAR(0x00FF)</code>。<code>PartyPacketSender.SendToPartyAsync</code> 把同一不可变两包批次并发发送给每个在线有效成员；单成员超时或失败不得中断其他成员，重试只发送 journal 尚未 committed 的接收者。<code>0x0319</code> 为 <code>UInt32 count</code> 后跟每项固定 15 字节的 <code>UInt16 userId + Byte cardType + UInt32 flags + UInt32 itemId + UInt32 quantity</code>；<code>cardType=0</code>、<code>flags=PVF state</code>、item/quantity 取各自冻结的最终奖励。服务端不接管普通 <code>SELECT_CARD</code>，也不保存特殊四卡的客户端点击状态。
- 每名接收者的 <code>0x0319 + 0x00FF</code> 批次发送成功后，必须冻结不可替换的 <code>projectionUtc + 11 秒</code> 绝对 deadline，并在其 <code>DungeonRun.Timers</code> 注册 <code>SuspendUntilResume</code> 的 generation-safe timer。网络 detach/重连只恢复原 deadline；投影已发送但 journal 提交失败时复用原 deadline 完成 checkpoint，不重发投影。投影发送、数据库发奖和背包刷新不得持有 Instance/Run 状态 gate；创建 timer 必须与 run 生命周期线性化，<code>EndRun</code> 之后不得重新挂旧局 timer。到期后重新校验 Instance/Run/Generation、当前 session 和 session-owned <code>InventoryLease</code>，再以 <code>anton-awakening-auto-reward</code> participant effect 发奖。
- 特殊奖励在线写入必须由 <code>OnlineInventoryMutationCommitCoordinator</code> 在同一 SQLite 事务内先占用动态 <code>sequential_reward_v1:{groupKey}:{rewardableDungeonId}</code> 每日计数、再调用 <code>InventoryRewardGrantService.TryCreateAndInsert</code> 并保存 dirty inventory；普通物品仅在 <code>InsertPlanFailed</code> 时改由 transaction-bound 永久系统邮件投递，邮件成功与直接入包都视为 committed，邮件失败必须回滚计数并恢复在线背包，已达每日上限按 committed no-reward 处理。邮件路径不生成虚假槽位刷新。该 UI 通知没有客户端 ACK；11 秒是当前用户确认的校准值，目标是在已观测约 13.2–13.3 秒的四卡流程结束前约 2 秒提交，实际视觉时序仍须受控实机验收。participant journal、实例奖励计划和 timer 只提供原进程内恢复，没有跨进程 prepared token，不承诺跨进程 exactly-once。当前 A21 客户端双端实机已确认 <code>10157834/state=1</code> 呈现金卡，其他 state 仍必须按 PVF 原值投影。

### 4. Tournament

- PvfLib 忠实解析 DGN 的 Tournament 标记、入场物品、逐轮 EXP、疲劳、浮点金币倍率、<code>[result card]</code> 结果矩阵及其嵌套 <code>[reward item rate]</code>，以及 MAP 中保序的候选敌人和重复起点；<code>TournamentDungeonDefinitionCatalog</code> 只生成不可变定义。结果键 <code>0..5</code>、非负权重、每行正总权重和材料数量权重必须完整有效；格式损坏、MAP owner 不一致或候选不足时 fail closed，生产代码不得按大会名称、dungeon/MAP 或门票 ID 分类。
- <code>DungeonInstance.Mechanisms.Tournament</code> 保存共享 16 强 bracket、四轮玩家路径、当前轮、<code>PathActors</code>、<code>EventId -&gt; sequence</code> 账本及显式 <code>Active/Eliminated/Champion</code> 终止结果。轮次只消费 canonical room death fact；同一配对重放为 no-op，EventId 复用于其他 sequence 或越轮死亡必须在世界死亡账本前拒绝。死亡 deadline 只能将 Active 原子冻结为 Eliminated，完成轮数取 <code>CurrentRound - 1</code>；终止态不可回退，重复 deadline 为 no-op。
- <code>DungeonRun.Settlement.Tournament</code> 保存参与者已完成轮数、是否冠军、EXP 和两组奖励的选择、Reserved/Failed/Delivered 状态。奖励通过统一金币/库存服务提交；网络投影失败不能回滚已持久奖励，也不能重新开放已 Delivered 项。没有完整四轮胜利时下排 card count 必须为 <code>0</code>，不得仅隐藏 UI 后继续接受或发放下排奖励。
- 入场物品按 Definition 在进图时通过统一背包入口扣除并持久化，失败同时恢复实体主背包槽与主虚拟槽；回城、失败或放弃不返还。没有 required item 的 Definition 不得捏造门票。扣票或 definition 准备失败必须以 expected identity 原子结束仍处于 Selecting 的 run，并以原回城锚点创建新的 <code>DungeonSelectionContext</code>；不得调用无身份 teardown，也不得让失败后角色同时失去 run 与 selection。拒绝原因和 ACK 统一遵守第八章 Dungeon Admission 合同，大会代码不得认识协议错误码。
- <code>0x01CA/0x01CB</code> 必须经 typed parser/dispatcher；<code>0x01CA</code> ACK 固定投影 <code>success + 2 reward types * 4 party slots</code>，不得发送单组短包。<code>0x0183/0x0184/0x0185</code> 只能由 builder 投影已冻结 runtime/reward state。成功响应 <code>0x01CA</code> 后，<code>TournamentRewardAutoSelect</code> 以三秒绝对 deadline 注册为 <code>SuspendUntilResume</code> 的参与者级 timer；超时只为每个启用且尚未选择的组选择最低可用索引，手动 <code>0x01CB</code> 与 timer 必须进入同一 reserve/deliver/commit 入口。所有启用奖励 Delivered 后，Champion 才以 <code>run.GetSettlementSourceEventId()</code> 创建稳定的 <code>DungeonClearIntent</code> 并进入唯一普通 clear pipeline；Eliminated 只完成 Tournament 失败终止，禁止生成 <code>DungeonClearedFact</code>、任务清图进度、难度权限或普通卡牌结算。
- 完整四轮胜利上排使用 DGN 结果键 <code>4</code>，下排使用额外键 <code>5</code>；失败上排使用冻结完成轮数键 <code>0..3</code>，下排 count 必须为 <code>0</code>。结果行按 <code>goldWeight/itemWeight/emptyWeight</code> 抽取。金币基数由普通 <code>ClearRewardGenerationContext</code> 的 canonical kill facts 生成并在参与者计划中冻结，随后直接乘 DGN <code>[tournament clear reward gold rate]</code>；当前三张冻结大会 DGN 的 <code>16</code> 是 <code>16x</code>，不是百分比。所有金币结果卡复用同一冻结金额，材料数量只从该图的 <code>[reward item rate]</code> 权重表抽取。
- 三张大会 DGN 与 <code>etc/chn_tournament.etc</code> 均没有“死亡不回城”独立字段；死亡策略来自已解析的 Tournament 类型，不得捏造 PVF/ETC 标签或按 <code>120/121/122</code> 分类。原服通用流程同样在 Tournament 失败时进入专用奖励并跳过普通出本。
- <code>TournamentDungeonCoordinator.RecoverAsync</code> 可在原 Instance/Run 仍存在时重投奖励界面；Champion 在“奖励已提交、clear 尚未提交”窗口恢复同一 clear intent，Eliminated 只恢复失败结果。若三秒 timer 在 detach 时仍未完成，重连后必须以原 deadline 恢复；deadline 已过期时立即补选，不能重新给三秒。runtime、奖励 journal 和 UI 均不持久化，服务端重启后不保证恢复。
- <code>round fatigue</code> 当前只解析，不在没有统一权威疲劳消费服务时自行扣除。

### 5. Blood Altar

- PvfLib 忠实保留 DGN 的 <code>[blood dungeon]</code> 类型和 MAP 中的怪物/轮次/phase 配置；<code>BloodAltarDungeonDefinitionCatalog</code> 将其冻结为 dungeon、map、round、phase、monster Definition。格式损坏、MAP owner 不一致、索引越界或空波次必须 fail closed；生产逻辑不得按无限/极限祭坛的显示名、dungeon ID 或 MAP ID 分类。守护者祭坛当前不在该目录的启用范围。
- <code>DungeonInstance.Mechanisms.BloodAltar</code> 是共享世界真源，保存当前 MAP/room identity、全局完成轮数、schedule generation、待投递波次、A/B prompt version、active dynamic sequence 和实例级 timer。<code>DungeonDynamicActorRegistry</code> 只提供统一 actor 解析；死亡仍进入 canonical kill、冻结 roster、participant journal 和 party fan-out，不建立第二套死亡账本。
- 祭坛动态 actor 的当前 policy 明确关闭普通怪物经验、随机掉落、任务击杀、普通机制、房间清怪计数和击杀统计。若 PVF/真机证据要求开启某项，只能修改 definition/policy，禁止在公共 kill handler 增加祭坛副本 ID 分支。
- <code>0x0102</code>、<code>0x00FF</code>、<code>0x013D</code> 必须经 typed parser/dispatcher；正文分别为严格空正文、<code>byte count + count * ushort sequence</code>、单 byte <code>1/2</code>。祭坛 START_MAP 使用 <code>0x00D3</code> 替代普通 <code>0x001D</code>；<code>0x00D2/0x00D7/0x0129</code> 只投影冻结 runtime。当前 MAP 未完成时由 application service 阻止换房，不得在 MOVE_MAP handler 识别祭坛 ID。
- 波次、难度超时和最终轮延迟由实例 runtime 的 timer registry 所有；participant detach 不暂停共享世界。回调必须复验 instance/run/room、schedule generation 和 timer ticket。最后参与者结束导致物理实例进入 Ending 时，由 <code>DungeonInstanceMechanismRuntimeSet.OnInstanceEnding</code> 取消实例 timer。
- 最终 canonical death 的 <code>DungeonEventEnvelope</code> 同时作为唯一 Blood Altar <code>ClearIntent</code> 来源，使世界死亡事实、participant kill effect、<code>DungeonClearedFact</code> 和 participant clear effect 共享同一 EventId。祭坛仍复用普通 clear 的任务清图、权威经验和持久机制提交，但展示由 <code>DungeonClearPresentationKind.BloodAltar</code> 分流，禁止普通 <code>0x001F</code>、Card 和 <code>SET_PLAY_RESULT</code> 成为第二结算入口。
- <code>DungeonRun.Settlement.BloodAltar</code> 保存参与者 <code>Prepared -&gt; RankingShown -&gt; RewardShown -&gt; Committing -&gt; Committed -&gt; ExitReady -&gt; Ending -&gt; Ended</code> 状态、绝对 deadline 和投影 checkpoint。结算时序为 <code>0x00D0 -&gt; 8 秒 -&gt; 0x00D1 -&gt; 8 秒 -&gt; 提交金币 -&gt; 0x0104 -&gt; 60 秒返城</code>。金币通过 session-owned <code>InventoryLease</code>、统一奖励服务和一次 <code>SaveDirty</code> 提交；持久化失败恢复内存快照并回退到可重试 phase。
- EPLP 与 60 秒自动返城共用 <code>TryBeginExit</code> 原子 gate。命令所有权由实例 Blood Altar runtime 判定，不由 participant settlement 是否已建立决定；未到 <code>ExitReady</code> 时消费并 no-op，非祭坛局才允许进入普通 Card EPLP。普通 <code>SELECT_CARD</code> 和 <code>CARD_START_REQUEST</code> 在 Blood Altar presentation 下同样消费并 no-op。
- <code>BloodAltarDungeonCoordinator.RecoverAsync</code> 只能在原进程、原 Instance/Run 与 registry attachment 仍存在时恢复：Active 阶段重投 START_BLOOD_MAP、当前波次和难度 UI；settlement 阶段按 checkpoint 重投并以原 deadline 恢复参与者 timer。实例 runtime、dynamic actor、奖励 journal 和 UI 均未持久化，无 ACK 投影不承诺 exactly-once，服务端重启后不能恢复祭坛局。

## 二十、PVF/ETC 解析规范

- 重复字段必须保留顺序。
- 缺失值与合法 0 必须分开表达。
- parser 只解析存在的字段，不捏造标签。
- 原始字符串 tokenization 上移 PvfLib/GameWorld。
- LST 的路径字段在 <code>LstFile</code> 边界统一恢复为正斜杠；PVF 字符串中的 CR/LF/TAB 路径转义分别恢复其 <code>r/n/t</code> 段首字符。禁止按 LST id 或文件名修补漏载项，也不得把该规则应用到普通脚本正文。
- MAP、Boss、warp、条件怪物和任务连接第一次决议后冻结。
- Tournament 的重复起点、候选顺序、MAP owner、入场物品和逐轮奖励必须在建局前冻结；共享资源目录按 MAP `[dungeon]` owner 选择，不能取目录第一项。
- 解析失败时记录 dungeon、maze、map、tag、路径和候选。
- 多候选无法唯一决议时 fail closed，不从全目录随机兜底。
- ID 只可出现在自测 fixture、协议证据或 PVF 关系断言中，不可成为生产业务分类器。

## 二十一、协议规范

协议证据优先级：

1. 当前客户端 DNF.DMP 和 handler 反汇编。
2. 当前版本实机抓包。
3. 当前 PVF/ETC。
4. 受控枚举测试。
5. 旧台服服务端仅作语义对照。

规则：

- 协议名称和编号以当前 <code>PacketTypes.cs</code> 为准。
- Parser 将 raw body 转为 typed command。
- Builder 不读取在线状态。
- Sender 不决定业务。
- Coordinator 不手写 byte body。
- 未知字段使用 reserved/opaque 命名，并保留原宽度。
- 未确认 handler 前不得把同号 CMD ACK 与 NOTI handler 混用。
- 无 ACK 的通知不能宣称 exactly-once。
- 任务 FINISH 的 parser 合同固定为去 echo 后 8 字节：<code>questId/rewardSelection/completionCount/0xFFFF</code> 四个 ushort；测试和内部调用也必须经过同一 typed parser，不得构造 6 字节兼容体。
- 协议中的 count、selection、hit count 或 result 字段只提供输入，不自动获得业务权威；Definition、当前 activation、库存和运行态必须独立重算可接受范围。

新增逆向脚本必须在文件头注明用途、输入、输出、扫描地址范围和适用客户端版本；优先扩展现有只读工具，避免重复造脚本。

## 二十二、并发与锁

- <code>run.SyncRoot</code> 只保护短状态转换。
- Instance、Room、effect ledger、registry 和 inventory lease 各自维护所有权。
- 锁内禁止 await、发包、数据库、PVF 解析、文件日志和长循环。
- 不得同时持有两个玩家 run 锁执行组队广播。
- reserve 在锁内，执行在锁外，commit 再回到所属 ledger。
- 当前 Encounter application 在 <code>run.SyncRoot</code> 下校验参与者仍属于该 run/room，并在同一同步调用中进入 Room 自有 runtime lock 提交 transition；共享 Encounter 的 owner 仍是 Room，不得把 run 锁解释为共享房间状态真源，也不得引入 Room -> Run 的反向加锁。
- Repository 事务不得回调 Network Handler。
- 重连每个 offer 使用独立异步 gate，重复点击串行化。

## 二十三、错误、重试与诊断

### 1. Fail closed

以下情况必须拒绝业务：

- identity/generation/room 不匹配。
- 无效任务定义。
- 无效奖励定义。
- 非当前 session 的 inventory lease。
- 未知 persistent effect payload version。
- 无法唯一解析的任务 MAP。

### 2. 可重试错误

- 内存 effect 标记 Failed 后可用同一 EffectId 重试。
- persistent effect 使用 lease、attempt count 和持久结果重试。
- 重连在 run attach 前失败时按第十六章回滚 party/registry；attach 后 participant effect 恢复失败只记录错误并保留 attachment 与 journal，不伪装成整局回滚。

### 3. DungeonDiagnosticJournal

- 每个 DungeonInstance 容量 512。
- 记录单调 sequence、SourceEventId、run/room identity、Encounter transition、ClearIntent 和 ClearCommit 摘要。
- <code>ReplayEncounter</code> 可从当前保留记录重建具名 Encounter 终态并报告 divergence/truncation。
- 当前 typed Encounter 只支持 Start/Succeed/Fail，并由 START_MAP、普通清房和 ClearIntent 等生产点调用；它不携带开门、召唤、奖励或协议 effect payload。
- journal 是进程内有界诊断轨迹，不是业务 event store、effect outbox 或断线恢复真源，也不承诺跨重启恢复。<code>ReplayEncounter</code> 只能验证已保留状态记录的一致性，不能重新执行外部效果。

### 4. 问题记录

每次出现逆向结论被推翻、构建/测试失败、工作目录/PVF/包表选错、生产修复完成或待真机边界变化时，必须立即记录。

## 二十四、标准接入流程

### 1. 新增配置型机制

1. 在 PvfLib 解析真实字段，保留顺序和来源。
2. 在 GameWorld 建 immutable definition。
3. 在选本或建房时冻结 definition/template。
4. 定义 typed lifecycle fact 或 DungeonCommand。
5. 在 Application Service 中做纯 transition 并返回 effect intent。
6. 在 Router/Sender 执行网络或外部效果。
7. 需要通关时只生成 ClearIntent。
8. 增加真实 PVF、自身重放、旧 generation 和组队 scope 测试。

### 2. 新增任务地图

1. 补 <code>QuestRelationIndex/QuestTargetIndex</code>。
2. 由 <code>DungeonSelectionPlanner</code> 在进本时冻结。
3. 组队只生成一份共享选择。
4. 玩家任务进度进入 <code>DungeonQuestBridge</code>。
5. 任务完成后入口权限重新投影。
6. 测试有任务、无任务、已完成、队员任务不同和重访。

### 3. 新增副本命令

1. 在 Network/Parsers 定义 typed parser。
2. 注册到 <code>DungeonCommandReceivedDispatcher</code>。
3. 校验完整 run/room identity。
4. 领域层不得接收 raw header/body。
5. ACK 和 NOTI 由 Sender/Builder 生成。

### 4. 新增奖励

1. 明确 Player 或 Persistent scope。
2. 创建稳定 EffectId。
3. 库存奖励走 <code>DungeonItemAcquisitionService/InventoryRewardGrantService</code>。
4. 非库存 SQLite mutation 可评估 typed persistent outbox。
5. 展示、预留和提交复用同一结果。
6. 测试背包满、重试、重复包、断线和事务失败。
7. 副本经验仍统一使用 <code>CharacterExperienceService</code>。基础升级奖励由共同等级写入原语记录持久事实并消费，kill、clear、Tower、Tournament 和各结算 handler 不手工重复触发邮件。普通杀怪 participant effect 必须分别记录经验已应用和统计已应用，后续通知、任务处理失败时不能让已完成的阶段重新发放；经验写库在 journal 锁外执行，失败保留重试资格。原有 EXP、属性和任务通知继续保留；新经验来源提交后自然进入同一升级事件链路。

### 5. 新增 Timer

1. 先确定 timer scope：Participant timer 才使用 <code>RunTimerRegistry</code>；Instance/Room 世界 timer 必须由共享 owner 持有，不能复制到每个 run。
2. 使用 mechanism + purpose 组成的具名 key。
3. 以绝对 UTC deadline 注册；Participant timer 明确选择 <code>Cancel</code> 或 <code>SuspendUntilResume</code>，禁止依靠副本 ID 在重连时重新计算整段时长。
4. 捕获相应 instance/run/room identity、ticket generation 和 SourceEventId。
5. callback 只投递 typed 事件；过渡实现必须在不可逆动作前复验当前 attachment/session。
6. 网络 detach 只挂起参与者可恢复项；EndRun、新局创建或共享 owner 终止时淘汰旧 callback。
7. Participant timer 在统一重连恢复入口接线，不得由业务模块自行监听登录并建立第二套 registry。
8. 测试替换、主动取消、旧句柄、detach/resume 新 ticket、剩余 deadline、过期立即投递、跨局失效，以及共享 timer 不随单个参与者离开而取消。

### 6. 新增或修改任务完成

1. 在 <code>QuestCompletionDefinition</code> 中定义可验证的 grade/type/需求语义，不按 quest ID 授权批量。
2. 由 <code>QuestRewardDefinition</code> 严格解析奖励类型、完整 token、选择策略和 job/grow 条件；未知或损坏定义整单拒绝。
3. raw FINISH 只在 Network parser 解析一次，Application Service 只接收 <code>QuestFinishCommand</code>。
4. 先验证当前 <code>QuestActivationId</code>、完成条件、奖励定义、选择授权和服务端批量上限。
5. 在 planning inventory 上先消费后规划奖励，冻结跨槽消费和所有奖励槽位。
6. 在同一事务内执行 activation CAS、库存 SaveDirty、完成标记、成长副作用与经验金币。
7. 请求失败恢复内存；commit 后只做协议投影，不在 projector 新建第二奖励入口。
8. 至少测试精确包长、bad sentinel、零次数、普通任务多次、required/forbidden selection、批量上限、跨槽材料、虚拟金币、满背包、重复包和并发重放。

## 二十五、禁止新增的写法

- 按单个 dungeon、MAP、monster、NPC、item 或 quest ID 修通用机制。
- 用中文显示名决定机制。
- 用 Party、RoomKey 或坐标代替实例身份。
- 本地击杀与 party relay 维护两份副作用清单。
- Handler 直接写任务 SQL、奖励 SQL或状态枚举。
- 为每个通关来源复制 settlement。
- 用 bool 表示完整生命周期。
- 锁内 await、发包、数据库或解析 PVF。
- timer 保存裸 session 后直接回调。
- 旧 run cleanup 无条件执行 <code>CurrentRun = null</code>。
- outbox 直接写新背包表。
- 任务失败后仍提交完成。
- 为 FINISH 保留第二份 raw body parser、缺字段补默认值或把客户端 count 直接当倍率。
- 把 <code>[seeking]</code> 的 <code>itemId=0</code> 当非法实体物品，或通过实体物品创建接口生成金币。
- 无 ACK 通知宣称 exactly-once。
- 在未确认协议字段时用枚举猜测长期上线。
- 自动测试未通过或真机未验证便写“完成”。

## 二十六、P0/P1/P2 当前工作树完成矩阵

本矩阵描述当前权威工作树，并以生产调用链、失败边界自测和冻结 PVF 回归共同判定。类型或入口存在但缺少恢复合同的能力只能标为“部分落地”；自动回归不等于协议已完成真机验证。

### 1. P0 已闭环（当前进程 / 请求事务边界）

- 物理实例与玩家参与状态分离。
- Run/Settlement/Room/Encounter 独立状态。
- Instance、ParticipantRun、Room、ParticipantRoom identity 和 generation。
- DungeonEventEnvelope。
- 内存 effect ledger。
- SelectionSnapshot 与 QuestRunSnapshot。
- typed ClearIntent 和唯一 DungeonClearedFact。
- Kill/Clear 冻结参与者 roster、participant checkpoint fan-out、断线补发和跨房屏障。

- EndRun expected-run compare-and-clear、逐项 cleanup checkpoint 与 finally Ended。
- settlement 持久业务 effect 与会话投影 effect 分离；detach 时前者不重复、后者可在 rejoin 重投。

### 2. P1 已完成的生产收拢

以上只表示生产入口已经收拢；每条链路能恢复到什么边界，以第 3 节为准。

### 3. P1/P2 当前生产接线与恢复边界

状态词必须按以下含义使用：

- **当前进程已闭环**：同一服务器进程、原 Instance/Run 仍存在时具备唯一入口和幂等 checkpoint。
- **请求事务已闭环**：单次请求中的 SQLite/Inventory 变更具备事务或 rollback；不自动包含进程崩溃恢复。
- **进程内可恢复**：detach/rejoin 可从原内存 journal 续跑；服务重启后丢失。
- **持久子集**：只有明确注册到 SQLite outbox 的 effect kind 可跨进程恢复。
- **专用链路**：已与普通路径隔离，但尚未并入普通 clear/settlement 恢复合同。
- **扩展/诊断**：提供 typed 状态或重放校验，不代表外部效果、持久恢复或协议已接线。

### 4. 副本进入次数限制

- `DungeonEntryLimitService` 位于 `Game/Dungeon`，是有限进入次数的应用服务入口。`Network/Handlers` 只能调用它的 typed 结果，不得直接写 `dungeon_limit_*` 或 `character_dimensiongate_records`。
- `dungeon_limit_config` 与 `dungeon_limit_records` 只对应 A21 `USERINFO mode=1` 中的特殊副本计数表；`dungeon_limit_config` 预置真实抓包确认的 26 个 `dgn_id` 和默认 `limit_count`，USERINFO 投影中每项 `value1` 固定写 0、`value2` 写当前剩余次数。`scope_type` 只允许 `charac` 或 `account`。
- `character_dimensiongate_records` 只对应 `DIMENSION_GATE_ENTRANCE_INFO(0x0326)` 的异界进入次数，状态语义为 `current_count`、`extra_count`、`used_count`；0x0326 body 顺序为 `u32 current_count`、`u32 extra_count`。暗精灵遗迹或 LICENSE_DUNGEON 家族确认后另建专表，不复用本表。
- 所有限次状态使用 `DailyResetService.TodayId()` 的北京时间 06:00 日切键。读取时旧 `day_id` 视为默认次数；真正进本扣次时必须在同一 SQLite 事务中更新当前/额外/已用次数。
- 未配置的副本按“不受该服务限制”处理；配置存在但当日 `current_count + extra_count` 不足时拒绝进入。客户端协议投影由对应 builder/sender 负责，服务本身不拼包。

### 5. 当前明确限制

- DungeonInstance、attachment registry 和诊断 journal 仍为进程内状态；服务端重启后不能恢复物理副本。
- 全队实时 Party 已解散或单人局没有有效 PartyId 时不能重连。
- 持久 effect outbox 只覆盖已登记的非库存 effect kind；库存奖励和无 ACK UI 投影不具备通用跨进程 exactly-once。
- persistent outbox 的单次选角恢复有 4 页/3 秒预算且没有会话内后台 drain；超过预算或本轮失败的 backlog 只保证保留并可观测，等待下一次显式恢复。
- Card 的库存、溢出邮件和 persistent effect result 同事务提交并可按已提交结果幂等读取；run journal、客户端展示及通知没有跨进程 exactly-once 恢复。
- EndRun cleanup checkpoint、timer registry、participant journal 和 SpecialDungeon effect checkpoint 均未持久化；进程重启后不能恢复。
- Tournament bracket/runtime、终止结果、奖励 checkpoint 与 Champion clear 前恢复均依赖原 Instance/Run；服务端重启后不能恢复，且当前无 ACK 的大会 UI 投影不承诺 exactly-once。
- Blood Altar MAP/round/wave runtime、动态 actor、participant settlement 和 timer checkpoint 均依赖原 Instance/Run；服务端重启后不能恢复，无 ACK 的祭坛 UI 投影不承诺 exactly-once。
- Sequential Awakening 的动态 progress、monster-drop 和 reward counter 可跨重启按 06:00 日切并阻止同日重复，但冻结抽奖计划、普通翻牌屏障、participant projection checkpoint 和 11 秒 timer 不持久；提交成功到内存 journal commit 的崩溃窗口没有通用 prepared recovery。<code>10157834/state=1</code> 金卡视觉已由当前 A21 客户端双端实机确认，但这不扩展为其他客户端批次或未知 state 的协议结论。
- DeathTower 最终结算仍是专用入口，经验事务、库存奖励与网络投影没有统一 effect ledger；不得将普通 settlement 的恢复结论套用到塔类。
- Encounter directive 和诊断 replay 只验证内存状态转换，不能用于重建外部效果或物理副本。
- 完整 reward definition 必须严格解析并覆盖当前 <code>quest.lst</code> 权威目录；当前仍不支持把 Premium 激活作为任务完成事务的一部分，因此未来命中该类别必须 fail closed。原生非库存类别若新增服务端持久效果，仍需单独接入 completion plan。
- 黄金王 SeizeMoney 已拒绝客户端 hitCount，但可信服务端受击 fact 的生产来源尚未接入，因此当前奖励保持 fail closed。
- FINISH completion transaction 具备请求期回滚和 SQLite 原子提交，但进程在 commit 边界崩溃时仍没有通用 prepared inventory mutation 恢复协议。
- <code>DISCONN_DUNGEON_INFO</code> 第二个 int32 仍为 <code>reservedInt32</code>，固定投影 0，不猜测语义。
- 自动回归不能替代真机对协议时序、UI、断线重连、组队竞态和长时间 timer 的验证。

## 二十七、验证门槛

任何修改副本、任务、结算或背包共享路径的变更，至少满足：

1. 使用隔离 artifacts 构建，禁止污染工作树输出。
2. 明确记录 PVF 资源标识和 SHA256；自测必须显式设置 <code>PVF_ARCHIVE_PATH</code>。
3. 运行受影响的聚焦自测，失败时先区分生产缺陷、测试夹具缺陷和环境错误。
4. 运行 <code>--selftest-all</code>，不得只用聚焦测试替代共享路径回归。
5. 运行 <code>git diff --check</code>，不提交临时回归数据库、日志、转存或隔离构建产物。
6. 完成真机测试前，只能写“自动测试通过”，不得写“功能完成”。

构建、自测和实机验证结果应写入提交或 MR 描述，包含资源指纹、实际命令、通过与失败项以及未覆盖范围。规范正文不保留单次运行记录或机器路径；换分支、换 PVF 或修改注册表后必须重新验证。

## 公会地下城接入边界

`GuildDungeonCatalog` 提供只读 PVF 定义，`GuildDungeonService` 与 `GuildDungeonRepository` 负责准入和持久化。共享入场链路先校验成员、周期和前置进度，再走既有 `EntryAdmission`；冻结事实属于 `DungeonSelectionState.GuildDungeon` 和 instance mechanism，不得另建 Handler 缓存或在 `DungeonRun` 根对象扩散字段。

通关使用既有权威结算 effect `guild-dungeon-clear`，以 `GetSettlementSourceEventId()` 和角色编号形成持久化幂等键。进度、贡献、奖励邮件与台账同事务提交，通知在提交后发送；重试通知不得导致重复奖励。周期和成员关系在事务内重验，过期 run 不能推进当前周期。公会进度单位是通关次数，百分比由 PVF 的 gauge 增量与上限计算；客户端通知必须发送次数。

周期政策、协议证据和 schema 版本见《服务端业务开发规范》的公会地下城段落。测试必须覆盖入口拒绝、前置解锁、持久化恢复、并发重复结算、邮件及贡献回滚、跨月与离会边界，并串行执行全量自测。单人和组队客户端体验、周特殊奖励与重复通关加成不能以基础通关自测代替验收。

## 二十八、任务前置与冲突定义接入规范

任务前置、问答分支和冲突任务属于任务目录定义，不得在副本 Handler、选本入口或单个任务调用点内自行解释。所有入口必须使用同一个不可变目录定义和同一个 typed evaluator，保证列表展示与事务接取的判断一致。

### 1. 权威来源与定义对象

1. 生产任务目录只认 PVF 的 <code>n_quest/quest.lst</code> 及其解析到的任务文件。递归扫描出的历史、孤儿或未被 <code>quest.lst</code> 引用的 QST 文件只能用于诊断，不能扩大生产任务集合。
2. <code>PvfLib.QuestFile</code> 负责保留原始标签分组和顺序；重复的 <code>[pre required quest]</code>、<code>[pre required quest answer]</code>、<code>[collision quest]</code> 与 <code>[account collision quest]</code> 不得互相覆盖。
3. <code>GameWorld.QuestPrerequisiteDefinition</code> 是 immutable catalog definition，负责解析、验证和保存前置组、答案要求、角色冲突及账号冲突。业务层不得重新读取 raw PVF token。
4. 定义必须带有明确的 <code>IsValid</code> 结果和失败原因。未知任务引用、非正 ID、自引用、非数字 token、问答奇数 token 或其他结构损坏均为无效定义。
5. 显式存在但内容为空的前置或冲突标签是合法的无约束占位，不得误报为坏定义；空标签之外的异常仍必须 fail closed。

### 2. 统一语义

1. 多个 <code>[pre required quest]</code> 组之间使用 OR；同一组内的任务使用 AND。只有至少一组全部完成，普通前置才满足。
2. <code>[pre required quest answer]</code> 按 <code>questId + answerIndex</code> 成对解析，并与持久化的完成 flag 精确匹配；缺失、错误或无法解析的 flag 一律拒绝。
   <code>answerIndex</code> 从 0 开始，匹配的完成 flag 为 <code>answerIndex + 1</code>；不得把 PVF 答案下标直接当作持久化完成 flag。
3. <code>[collision quest]</code> 同时检查已完成和进行中的角色任务。任意冲突任务处于 cleared 或 active 状态，都不得接取目标任务。
4. <code>[account collision quest]</code> 必须使用真实账号级完成快照。调用方没有账号快照时不得猜测为未完成，必须 fail closed；不得把角色完成状态冒充账号完成状态。
5. 无效定义、未知引用和缺失所需状态必须返回 typed deny reason，不能降级为“无前置”或普通开放。
6. 以上规则只由定义和状态决定，禁止按任务 ID、中文名称、副本 ID、地图 ID 或文件名增加特判。

### 3. 统一接入边界

1. <code>QuestPrerequisiteCatalog</code> 构建目录定义；<code>QuestRelationIndex</code> 的可接列表、successor/question 索引和入口投影只能消费该目录定义。
2. <code>QuestPrerequisiteEvaluator</code> 是唯一前置/冲突评估入口。列表展示只用于投影，不能替代接取时的事务重验。
3. <code>QuestAcceptanceApplicationService</code> 必须在同一事务中重新加载活动任务、完成 flag 和所需账号快照，再调用 evaluator；客户端列表、缓存或进本时旧快照不具备授权效力。
4. 任务副本的入口权限、任务地图和 <code>QuestRunSnapshot</code> 只冻结已通过统一评估的任务事实。完成、放弃或重新接取后，入口权限必须重新投影；旧 activation、旧副本事件和旧任务掉落不得推进新 activation。
5. 任务前置判断不得写入 DungeonRun 根对象或 Handler 私有缓存。需要跨副本使用时，传递 typed decision、<code>QuestActivationId</code> 和 <code>QuestRunSnapshot</code>。
6. 任何未来的账号冲突调用点必须显式提供账号状态来源；在该来源接入前，保留定义但拒绝生产授权，不得通过单元测试夹具伪造已完成语义。

### 4. 必须覆盖的验证矩阵

- 权威 <code>quest.lst</code> 目录数量、有效/无效定义数量和暴露口径与冻结 PVF 一致。
- OR/AND 前置、问答答案匹配、空占位、重复标签保留和 malformed fail-closed。
- collision 对 cleared/active 两种状态均拒绝；account collision 无快照拒绝、有快照时按账号状态判断。
- 可接列表与事务 ACCEPT 对同一任务返回一致结论；并发接取不能绕过事务重验。
- 任务链、任务物品承接、任务地图冻结、放弃后旧 activation 隔离和重新接取新 activation。
- 目录基线必须绑定实际使用的 PVF SHA-256；聚焦测试核对 <code>quest.lst</code> 的去重 ID、顺序和路径，输出有效/无效及问答前置定义数量，并验证无效定义不会取得授权或出现在可接列表。不得复用其他资源批次的目录数量。
- 自动回归必须使用冻结 PVF 并显式设置 <code>PVF_ARCHIVE_PATH</code>，串行运行 <code>--selftest-quest-chain-availability</code>、<code>--selftest-quest-question-branch</code>、<code>--selftest-quest-run-snapshot-accept</code> 与 <code>--selftest-all</code>。问答测试须覆盖各答案、分支隔离、重复完成、事务回滚、旧 session 拒绝、放弃重接后的旧 activation 隔离和重新加载后的完成投影；进本接取测试须覆盖快照增量合并、旧 activation 覆盖、跨局隔离、过滤日志与触发器通道递减不下溢；构造的服务端输入不能替代当前客户端请求证据。自动测试通过后，仍需真机核验任务接取、入口显示、任务地图、客户端 UI 和断线时序。
