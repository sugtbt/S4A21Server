# A21 决斗场业务实现

本文定义决斗频道、房间生命周期、结算、战绩、账号队伍和独立技能的当前实现。通用约束见[服务端业务开发规范](服务端业务开发规范.md)，完整角色信息布局见[USERINFO1 客户端消费结构](USERINFO1客户端消费结构.md)。

## 1. 协议和资源基线

- 协议名称与 opcode 以 `Network/Core/PacketTypesA21.cs` 的 A21 枚举为唯一入口。下文地址和资源数值只适用于该基线；包序由消费者与协议自测约束，不由枚举排列决定。
- 源码路径以 `Server/DfoServer/` 为根，资源路径以 PVF 为根。

## 2. 所有权与持久化

| 数据或职责 | 唯一所有者 | 边界 |
|---|---|---|
| 频道目录与准入 | `GameNetworkConfig`、`PvpChannelInfoHandler` | 保留频道号和类型；开关统一控制监听、选择器与登录 |
| 房间与比赛状态 | `FreeDuelRoomRegistry`、不可变 `FreeDuelRoom` | 按 listener、session、room generation 和 match generation 隔离 |
| 请求、发布和阶段推进 | `PvpRoomHandler`、`CharacterTransitionCoordinator`、既有发布队列 | 房间发布锁串行；异步发送复验当前身份 |
| 基础等级、称谓 | `characters.pvp_grade/pvp_rating_grade` | `PlayerContext` 为在线投影；外观刷新保留值，返回选角清除 |
| 经验、胜负与积分进度 | `SqlitePvpRecordRepository`、`character_pvp_records` | 级内经验持久化，累计经验仅作协议投影 |
| 比赛与逐人结果 | `SqlitePvpRecordRepository`、`pvp_matches/pvp_match_results` | 整局结果、双方进度和角色等级同一事务；联合 room/match generation 防重 |
| 账号三人队伍 | `SqlitePvpTotalMatchTeamRepository`、`account_pvp_total_match_teams` | 存储角色 ID；列表索引只用于请求和显示 |
| 独立技能 | `SqlitePvpSkillRepository`、`SkillStateService` | 独立已学技能，共用点数账本 |
| 战绩查看 | `CharacterSelectHandler` | 同频道唯一在线目标与发送时权限复验 |

数据库由当前基线及连续迁移管理：schema v27 引入进度和账号队伍，v28 引入比赛账本；运行时不隐式建表。尚无业务所有者的排位匹配、认证推进、称谓授予、双杀/全杀奖励与历史赛季导入不生成模拟数据。

## 3. 战绩查询

### 3.1 第二、三季查询

个人信息按钮 `2397E90` 的 button 108/event 13 调用 `2741810`，发送 `CmdPacketTypeA21.FAIR_PVP_SCORE`。请求固定 8B：

| 请求偏移 | 类型 | 含义 |
|---:|---|---|
| 0 | u16 | 目标 userId |
| 2 | u8 | 是否查询自身，0/1 |
| 3 | u8 | 视图模式，调用方模式加 1；个人信息按钮为 3 |
| 4 | i32 | 目标 actor 索引，未匹配为 -1，否则为 0..2 |

`27448F0` 通过专用回调注册 `2743B80`。响应使用同一 CMD；公共派发器先消费成功字节，成功回调再读取以下字段，并打开或刷新窗口 470。它不使用 USERINFO subtype3 或 subtype7。

| 响应 body 偏移 | 类型 | 含义 |
|---:|---|---|
| 0 | u8 | 成功标记 1 |
| 1 | u16 | 目标 userId |
| 3 | u8 | 回显视图模式 |
| 4 | u8 | 详细记录开关，仅值 1 使客户端读取可选块 |
| 5/6 | 2×u8 | PvP 等级、分级字节 |
| 7/11 | 2×u32 | 个人胜场、擂台胜场 |
| 15..17 | 3×u8 | 最近十场胜、负、平 |
| 18/22/26/30 | 4×u32 | 当前连胜、双杀、全杀、最高连胜 |
| 34 起（开关=1） | 7×u32 + u8 count + 14×count B | 个人负/平、擂台负/平、团队胜/负/平；职业条目为 job、growType、胜/负/平 |

基础响应共 34B；详细响应为 `63+14×count` B。`FA49F0` 用 `19DEEE0(grade)` 绘制等级，并在分级大于 0 时用 `19DEEE0(rating+20)` 绘制分级标记，确认响应中的两个字节用于段位显示。

`2743B80 -> FA6D60/FA93D0` 的字段消费顺序对应上表。`CharacterSelectHandler.HandleFairPvpScore` 通过 `FairPvpScoreResponseBuilder` 返回详细分支。`SqlitePvpRecordRepository.LoadSeasonScore` 从第三季已提交比赛聚合统计，双杀/全杀尚无可信事件 owner，保持零；第二季没有导入历史时返回空统计。不能从账号副本次数推算，不能跨赛季复制战绩。

| 51 | u32 | 累计胜场 |

## 4. 等级与称谓

当前中文资源按 `19DABC0(index) -> 文本 ID 1207+index` 提供等级名称，`19DEEE0(index)` 选择对应图标。基础等级 `PvpGrade` 直接作为索引；战斗力称谓 `PvpRatingGrade` 大于 0 时使用 `rating+20`：

| 字段和值 | 当前中文显示 |
|---|---|
| 基础等级 0 | 入门 |
| 基础等级 1..4 | 青铜 1..4 星 |
| 基础等级 5..8 | 白银 1..4 星 |
| 基础等级 9..12 | 黄金 1..4 星 |
| 基础等级 13..16 | 钻石 1..4 星 |
| 基础等级 17..20 | 泰拉石 1..4 星 |
| 战斗力称谓 0 | 无特殊称谓 |
| 战斗力称谓 1..9 | 武者、斗士、高手、强者、达人、大师、至尊、天王、武尊 |

- 个人信息 `239B0A0` 的徽章控件 192 调用 `19DBA10(data, 1)`：称谓非零时优先返回 `rating+20`，否则返回基础等级。单个徽章只能显示其中一个。
- 战绩窗口 `FA49F0` 始终绘制基础等级，并在称谓非零时额外绘制称谓图标；两项数据不互斥。
- `134D280` 绘制的“战斗力等级 / 等级”是包含全部示例的说明浮层，不能将它的两列解释为角色必须二选一。
- 基础等级仅使用 0..20；特殊称谓使用独立字段。共用图标表中的称谓索引不能写入基础等级。
- 文本 36558 明确区分按战斗力排名授予的特殊称谓与按累计决斗经验获得的初阶等级。传统频道胜负可推进初阶经验等级；战斗力排名、特殊称谓授予和赛季奖励尚无结算 owner。

## 5. 经验和 RP/GP

个人信息 `239B0A0` 分别比较 RP 和 GP 的认证进度。阈值来自 `E419E0 -> E3FC00`；资源加载器将 `etc/matchingmode.etc` 的 `[elo weight] / [warm up games]` 写入配置 `+0xC8`，当前资源值为 **20 场**。它与两个等级字节相互独立。

`NotiPacketTypeA21.PVP_RECORD` 的 `1165CB0` 消费链确认以下字段：

| 通知 body 偏移 | 类型 | 客户端用途 |
|---:|---|---|
| 0/4 | 2×u32 | 胜场/负场计数，参与总场数与胜率显示 |
| 8 | u32 | 当前累计决斗经验 |
| 12/16 | 2×u32 | 当前等级的经验下界/上界；顺序由 `1839E50` 的目标字段确认 |
| 20/21 | 2×u8 | 基础等级/战斗力称谓 |
| 22 | u32 | 先前等级，`FFFFFFFF` 表示沿用当前等级、不触发升降级动画 |
| 26/30 | 2×u32 | RP / 最高 RP |
| 34 | u32 | 经 `183FED0` 写 actor `+0x3928` 的安全整数；`183FE30` 读取 RP 认证进度 |
| 38 | u8 | 等级变更状态；初始化为 0 |
| 39 | u32 | 传入 `183A450`，业务名和持久化来源待确认；当前为 0 |
| 43 | u32 | 经 `19DB2C0` 写角色记录 `+0x52C`；`19DB2B0` 读取 GP 数值 |
| 47 | u32 | 经 `19DB2A0` 写角色记录 `+0x528`；`19DB290` 读取 GP 认证进度 |

基础 body 完整长度为 **51B**。当前房间的 vtable `+0x30` 判定为真时，reader 还会读取三组 26B 成员数据；普通初始化只能在该房间上下文建立前发送基础形态。

经验条 `1368FA0` 使用 `累计经验 - 下界` 作分子，`上界 - 下界` 作分母；缺少初始化会留下 `0/0` 和非法百分比文字。`29FE8B0` 按资源索引存储阈值；零级从零开始，一级下界为 12000。`19E3B30` 使用 `[pvp experience loss]` 的最大基础等级 20 决定 `MAX`，资源第 21 条阈值是正数上界哨兵，与特殊称谓字节无关。把共用图标索引 25/27 直接写入基础等级，会同时造成称谓和 MAX 条件误判。

当前服务端由 `PvpExperienceRules` 读取 `etc/pvp_ref.etc` 的递增经验阈值，等级 g 的区间使用 threshold[g] 到 threshold[g+1]，threshold[0]=0。`experience_in_grade` 只表示区间内进度，发包时换算累计经验。传统频道按资源 `[pvp grade point]` 的胜负值推进经验。入门 grade 0 在可获经验的胜局中，累计经验至少达到 grade 1 下界（当前 12000）；客户端 `1368FA0` 在入门分支显示文本 191“只要胜1场即可升为青铜1星”，其他等级显示经验值。失败、平局、练习和超出每日经验次数的结果不触发入门晋级。基础等级封顶 20；每日次数按北京时间 06:00 划分游戏日，超过 50 胜或 10 负不再改变经验。排名称谓与此独立。

| RP 进度 | GP 进度 | 中文文本分支 |
|---|---|---|
| 小于 20 | 小于 20 | 31665：两项均显示“实力认证中” |
| 达到 20 | 小于 20 | 31666：显示 RP 及上限，GP 显示“实力认证中” |
| 小于 20 | 达到 20 | 31667：RP 显示“实力认证中”，显示 GP |
| 达到 20 | 达到 20 | 31668：显示 RP、RP 上限及 GP |

当前持久化 owner 为 `SqlitePvpRecordRepository` / `character_pvp_records`，包括级内经验、胜负、RP、最高 RP、两种认证场数和 GP；两个等级由 `characters` 保持唯一所有权。选角在第二次 `USERINFO0` 和 `HOTKEY_OPTION` 之后发送 `PVP_RECORD`，使用保存的进度覆盖客户端缓存。缺少记录时统计与级内经验为零，显示“实力认证中”符合上述条件。自由房间不增加排位认证或奖励，不能据此声称认证玩法已实现。旧 subtype0 模型的 `PvpStatA/PvpRankPoint/PvpWinStreak` 名称也不能作为真源证据。

## 6. 频道准入

`--free-duel-channel-listener` 统一启用资源目录中的类型 8/13/24 决斗频道，控制监听、选择器可见性和登录准入。未启用时这些频道不可进入；频道类型来自 `channel_info.etc` 的 server group 1，不以单一频道号代替类型判断。

`PvpChannelInfoHandler` 对未开放 listener 的 `CmdPacketTypeA21.PVP_CHANNEL_INFO` 请求返回失败 body `00 00`。`1119FB0` 仅把失败码 `0x15` 转到 `1585060` 的佣兵出战提示；普通失败进入 `26BAC60` 的频道选择回退路径。

`26BAC60` 请求频道目录并通过 `26BAB00` 显示加载状态；后续 `26BAB90 -> CF1C80` 检查是否存在可用 PvP 频道，没有时由客户端显示文本资源 **70077：“无法连接到决斗场频道”**。70077 是文本资源 ID，不是线上错误码。此路径不需要服务端发送带自定义文字的通用告示。

未带 `--free-duel-channel-listener` 时，频道目录隐藏相应 PvP listener，出现该提示符合客户端回退行为。启用开关后，目录可见性、listener、登录环境与 PvP 选角初始化必须一致；仅回成功状态不能代替这些条件。

决斗场入口 `PVP_CHANNEL_INFO` 是独立链路，其失败码 `0x15` 会由客户端 `1119FB0` 进入佣兵提示，未启用入口使用普通失败回退 `00 00`。当前频道目录使用的类型 8/13/24 均被 A21 `2AF33F0` 判为 PvP；`LOGIN` 成功 body `+3` 经 `110F1F0 -> 163D5B0` 保存频道环境。服务端按目录类型选择登录环境、独立技能和大厅快照，不能仅识别单一频道号。

## 7. 大厅、房间与邀请

`town/town.lst` 将城镇 10 指向 `Fair_PVP.twn`；gate 区域 0 的出生锚点为 `(474,234)`，地图为 `Fair_PVP/Gate_Hendon.map`，其出口连接城镇 10 区域 1。PvP listener 选角必须使用该场景，退出房间也回到当前决斗城镇区域；不能继续使用持久化的普通城镇 gate。位置是频道临时状态，切回普通频道后由持久化城镇恢复。

| 通知 | 当前 A21 消费结构 | 客户端 reader |
|---|---|---|
| `PVP_ROOM_INFO` | u16 房间数；每房 u16 ID、u8 名称类型（0 时附 Dstr）、u8 状态、u8 房主座位、i16 地图索引、u8 模式、8×(u8 座位状态+u16 UID)、u8 密码标志、i32 匹配类型 | `1173790` |
| `PVP_SEAT_STATE` | u16 房间 ID、u8 模式、u8 变更数；每项 u8 座位、u8 状态、u16 UID | `1165950` |
| `PVP_READY_STATE` | u8 座位、u8 准备标志 | `1160520` |
| `PVP_ROOM_STATE` | u16 房间 ID、u8 状态、u8 房主座位、i16 地图索引、u8 模式、i32 匹配类型，共 11B | `1160360` |
| `START_PVP` | u8 选中地图索引、u8 模式 | `1173BD0` |

座位记录没有额外位置字节；添加该字节会将后续座位和密码标志读错。空密码即使请求带密码字段，也必须按无密码房处理。参与者准备后，房主通过同一准备命令开始。

`13AD8E0` 发送 `SET_PVP_MAP_INDEX` 的 i16 索引，`13B4E00` 使用 `29E77B0` 从 `etc/pvpmapbasicdata.etc` 加载的 `[pvp map order]` 保留零基索引；当前可选地图为 1..5，0 为随机。线上值不是 map.lst 中的地图 ID。更改成功由 ROOM_STATE 广播；当前 CMD 注册入口没有地图更改的专用回包处理器。

退出房间的顺序为：撤销成员/移交房主或销毁房间，恢复 `UserState=0` 与城镇可见状态，发送当前决斗场 USER_AREA，再由现有 `TownHandler` 发送 AREA_USERS 和同屏角色。构建房间 USERINFO1 时只能在 body `+18` 替换 UID，不能覆盖 body `+3` 的成长胶囊字段。

大厅的 USERINFO0 名册由 `u8 subtype + u16 count` 开头，**每条**记录先写 38B 头再写 u16 UID（单条包为 body `+41`）。`13E7340` 建立的角色记录是 `13E6370` 完整信息、`11896E0` UDP 地址通知和 `118C640` 邀请通知的前提；缺少记录时这些消费者直接返回。名册合并只能去掉单条包的外层 3B，不能从 body `+3` 读取 UID，也不能去掉每条 38B 头。

后到大厅的玩家必须先收到所有在线玩家的身份，再收到包含已有房间的 ROOM_INFO。进入房间时，参加者先收到包含自己和已有成员的 USERINFO0 名册，再消费 USERINFO1、UDP 和座位通知；已有成员先收到新成员的 USERINFO0，再收到其完整信息、UDP 和座位变化。统一使用当前会话 UID，不能将数据库角色 ID 误当作包内另一种身份。

决斗邀请使用 `REQUEST_PEER` 的 `u16 inviterUid + u8 type=2 + i32 peerToken`，共 7B。服务端在该通知前补充邀请者 USERINFO0。接受按钮 `2532D70` 发送同样的 7B `RESPONSE_PEER` 请求；`2535A30` 的拒绝分支对 type 2 仅关闭弹窗，不发送普通组队的 9B 拒绝形态。服务端校验 pending invite 的双方 session、listener、token、room generation 和期限，过期或重复接受不得加入房间。邀请和入房继续复用现有发布队列与角色切换门禁。

`AREA_USERS` 的 `1193590 -> 19E4EF0/19E1CD0` 清理场景列表；UID 查找 `19E2EF0` 使用管理对象 `+4` 的角色表，两者不是同一容器。不能仅因出现区域加载就重复发布整个大厅或跳过角色注册前提。

## 8. 结算与回放

`FreeDuelRoom` 在开战时冻结参战角色、UID、座位和队伍；断线撤销会话与座位，保留本局归属、死亡和击杀。`DIE_PVP_CHARACTER` 的 5B 请求依次是受害者 UID、攻击者 UID 和属性比较标记。仅当前受害者会话能报告自身死亡，攻击者必须是当前存活对手；未知、自身或同队来源不计击杀。兼容的 2B 请求只含受害者 UID，仅在唯一存活对手存在时归属击杀。末字节不控制击杀许可。

阶段按等待、战斗、等待排名确认、等待结果确认推进。最终排名确认或超时回调在 registry 接受阶段变更前提交整局事务；失败保留可重试的排名阶段。旧 room/match generation 不得调用结算。数据库提交后更新在线等级，再发布结果；断线角色通过正常登录重新读取持久进度。无客户端 ACK 的结果通知不保证动画恰好播放一次。

战斗中的断线先撤销服务端成员、记录死亡并在终局时发起排名确认；死亡和排名请求只发给该房间成员，不广播给大厅或其他房间。仍有对立存活方时继续本局，擂台换人回调必须同时匹配 room/match generation 与战斗阶段。

客户端战斗和结果场景仍引用本局的角色记录。本房间的座位变化及本局 UID 的 `USER_LEAVE` 按接收者延后到真实 `END_PVP_RESULT`、返回等待后的就绪请求或已发布的回城导航；服务端 ACK 看门狗转回等待不能代替客户端场景退出，看门狗后的再次断线、正常离房与踢人也必须遵守接收者的未结束状态。好友离线仍发布上下线通知，但 PvP 的 UID 删除统一交给决斗生命周期。延迟发布在发送前复验当前房间、比赛和成员；旧会话 UID 已被重登复用时不能删除新记录。按 UID 更新地址的 UDP 通知及无关大厅 UID 的离线清理保持正常投递，不因某场比赛的延迟清理而阻断。

`END_PVP` 的 `1170310` 将首字节作为赢家座位解析，再读取胜点、接收者等级、经验增量和参战人数。每名参战者为 `u16 UID + i32 击杀数 + u8 等级 + i32 累计经验 + i32 RP + i32 最高 RP`，共 19B。击杀数由 `25DE910` 保存到结果条目 +4，再由 `25DD770` 绘制。末尾固定部分为两个 u16 获奖者标识、i32 奖励经验、u8 平局、u8 事件状态、i32 事件值和 u8 道具奖励数；零奖励时完整 body 为 `26+19×人数`。

结果人数及逐人条目必须使用开战冻结的参战名单，包括已断线者；不能按当前连接成员截断，否则客户端结果消费者缺少原比赛角色条目。断线不改变整局结算的事务或防重归属。

传统频道类型 24 的结算在同一事务内持久化比赛与双方进度，联合 room/match generation 防重，成功后 `END_PVP -> PVP_RECORD` 同步结果与经验条。自由练习类型 13 保留已有进度，不记录胜负，不增加经验；类型 8 的自由房间不冒充排位匹配。`116C3A0` 发送的 `RES_PVP_RANK` 为 70B（11×u16、11×u32、2×u16），`2703950` 的 `END_PVP_RESULT` 请求没有 body。它们只确认已有终局的阶段，不提供奖励数值。尚未提交的物理比赛不能跨服务重启恢复。

自动回放录制由客户端 `START_PVP` 的 `1173BD0 -> 2740C10` 驱动；`163D320/163D330` 分别检查环境 8/13，传统环境 24 不调用录制入口 `109BA90`。后者还检查客户端录制选项 22/23 和本地录制状态，再由 `109B600/109B820` 保存参战信息。`END_PVP` 的 `109AC80` 只终结已启用的录制。服务端战绩账本不是回放文件，不伪造频道环境来开启传统频道回放。

## 9. 总力战队伍配置

`545D80/5435D0` 发出 `CHECK_PVP_TOTAL_MATCH_TEAM_NAME` 的 Dstr。`110D6A0` 对 `01` 启用确认并显示可用名称，`00 03` 显示重名，`00 9F` 显示非法名称。`545800` 发出 `SET_PVP_TOTAL_MATCH_TEAM` 的 Dstr 与三个 u8 角色列表索引；`110D890` 成功回包为 `01 + 三个索引`。`1164630` 消费 `PVP_TOTAL_MATCH_TEAM_INFO` 的 `Dstr + 三个索引` 并建立队伍对象，无队伍时不能随意发送空名或假成员。

`teamnamepopup.xui` 限制 12 字符；服务端复用严格 GBK、禁词和字符规则，最多 24B。`13E8600` 把 roster 的 grow_type 拆为低四位职业和觉醒位，`545800` 比较 `(job, 职业)` 对，觉醒阶段不同不能绕过相同职业限制。

入口允许 town-ready 城镇及当前会话所属的同 listener 决斗等待房间（`UserState=2`、`WaitingRoomState`、`WaitingSettlementPhase`）。房主和成员均只能配置自己的账号队伍；配置不改变房间座位，战斗和结算阶段拒绝。校验和事务持有既有房间发布锁，与开战串行；发送时复验账号、角色、当前连接和场景。成功先发 `PVP_TOTAL_MATCH_TEAM_INFO`，再发 CMD 确认。

`account_pvp_total_match_teams` 按账号持久化唯一名称与三个角色 ID。CHECK 不保留名称；SET 在 IMMEDIATE 事务里重新检查唯一性、归属、未删除状态和成员组合。重登及排序变化后重新换算客户端索引，角色被删除时不将旧索引套用到其他角色。已有队伍可更新成员；付费改名属于独立命令及道具事务，SET 不提供免费改名旁路。

## 10. 独立技能和点数

`SKILLINFO` 的 `11783A0` 分别读取两页 SP u16、各页技能条目，最后读取两页 TP u16。`EXP` 的 `1178CD0` 通过相同的 SP/TP setter 更新四项余额；65535 没有“无限技能点”的特殊消费条件，只会显示为数值。

独立决斗技能由 `SqlitePvpSkillRepository` 的 `character_pvp_skills/character_pvp_skill_state` 持有，普通技能仍由 `SqliteCharacterProgressRepository` 持有。`SkillStateService.LoadPvpAndSync` 统一从决斗技能列表计算两页余额并写协议镜像。选角、SKILL_INIT、房间 USERINFO1 和满级成长胶囊 EXP 必须选择同一频道的技能来源；不能用普通技能余额覆盖决斗初始化。

当前总点数沿用唯一账本 `SkillPointLedger`：SP 为 `Etc/spTable.etc` 的等级累计值加角色 `bonus_sp`，TP 为既有等级规则加 `bonus_tp`，各页分别扣除免费基线以上的已学技能成本。购买校验真实 SP/TP 成本，退款和后续刷新重新派生余额，不持久化第二份余额，也不绕过成本检查。u16 协议镜像会饱和到 65535；角色已有超大 bonus 时必须检查其存档来源，不能为了改变显示擅自清除 bonus。

专用公平竞技技能点表 `etc/pvpskillpoint.etc` 的等级/职业索引尚未确认，暂未接入；当前总点数按上述共享账本派生。
